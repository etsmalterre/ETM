# ETM

## Project Overview

ETM is the next-generation ERP system for **ETS Malterre**, a French textile/knitting manufacturing company (bonnetterie/tricotage). This project migrates the legacy WinDev/HFSQL application to a modern web-based solution.

> **Note**: this project was called `MPS_NG` during the early migration period. It was renamed to **ETM** (the company's short code — `IDsociete` 1 = ETM, sister of **TRM** = 2) on 2026-07-30: repo, folder, and docs. Two things deliberately kept the old name because they are deployed infrastructure, not the project identity: the production hostname `mpsng.malterre` and the workspace package scope `@mps/*`.

- **Company**: ETS Malterre — https://etsmalterre.fr
- **Industry**: Textile manufacturing (bonnetterie/tricotage — knitting)
- **Owner**: Vincent Malterre
- **Legacy system**: `C:\Mes Projets\MPS\` — WinDev (PCSoft) + HFSQL, French UI, 204 tables, 318 windows

## MPS — the platform, and why the API is not "ETM's"

**MPS = Malterre Productive System**: the shared platform every Malterre app runs on —
the HFSQL `MPS` database and the **MPS API** (`mps-api.service`, `/home/debian/mps_api`,
package `@mps/api`, `/api/health` answers `"app": "MPS API"`). The code has always called
it that; only the prose used to call it "the ETM API", and that one word did real damage —
see the ⚠️ in `etm_deploy` §Deploy ownership and in TRM's `trm_deploy` §Scope.

- **ETM and TRM are two *clients* of the platform, not owner and guest.** They are peers:
  ETM is `IDsociete` 1, TRM is 2, and the MPS API serves both from the same tables.
- **Planned clients**: the régleur mobile app, the bonnetier mobile app, the pointeuse, and
  the atelier display screens. Each is another consumer of the same API — so any sentence
  of the form "the API belongs to <app>" will age badly. Write "the MPS API" and say which
  *repo* it lives in if that's what you mean.
- ⚠️ **`apps/api` lives in this repo for historical reasons — that is a file location, not
  ownership.** ETM was `MPS_NG`, the first client, so the platform API was built inside it
  and never moved. Consequences that are easy to get wrong:
  - A change needed by a TRM screen (or, later, a mobile app) is a **normal change to this
    repo**, landed through an NG worktree like any other. It is not a favour to another team.
  - Deploying the MPS API from `/etm_deploy` deploys it **for every client at once** — it
    restarts one service that `mpsng.malterre`, `trm.malterre` and every future app share.
    Smoke-check more than the app you happen to be standing in.
  - Whoever is asked to ship an app is responsible for the platform half that app needs.
    "That's the other repo's job" is never the answer; walk over and deploy it.
- **If the platform ever outgrows this arrangement**, the move is to extract `apps/api` into
  its own `MPS` repo with its own deploy, leaving ETM and TRM as pure frontends. Not done —
  the pair is small enough that one deploy is simpler than two. Revisit when a third client
  ships, because that is the point where "which repo do I branch from?" stops being obvious.

## Navigation Structure

Mirrors the legacy WinDev main menu (top → bottom):

1. **Tableau de bord** (`/`) — widgets per-user permission-gated (`dashboard_*` keys); toggled in Paramètres › Utilisateurs. **Several dashboards per user**: they are the submenu tabs of "Tableau de bord" and come from the user's profile, not from `navigation.ts` — "Principal" always exists and is routed at `/`, the ones the user creates live at `/tableau-de-bord/<id>` (`Header.tsx` reads them via `useDashboardTabs`, sharing the layout query's cache). Create / rename / delete sit in the edit-mode "Tableaux" menu; the primary can be renamed but never deleted, and creating one carries the in-progress draft into the same write. Each dashboard holds its own layout, and the merge rule differs by tab: a widget the layout doesn't mention is appended **visible on the primary** (a stale layout must never hide a newly granted widget) and **hidden on the others** (a new widget must not gate-crash a curated dashboard) — so a new dashboard starts empty, every widget in the tray. Storage is `dashboards: [{id, name, layout}]` in `data/user-profiles.json`; profiles written before tabs carry a bare `dashboard` array, migrated read-time into the primary tab and rewritten on the first save. **The endpoint is scoped per app** (`?app=etm|trm`, default `etm`): the sister TRM app renders this very screen (`@etm/pages/Dashboard`) with its own registry, so a user's TRM arrangements live in a separate `dashboards_trm` field — the two catalogs share no key. That sharing is why `useDashboardLayout.ts` imports the registry and types through `@/components/dashboard/…` (in TRM that resolves to TRM's registry, `DASHBOARD_APP = 'trm'`) and why `WidgetDef` is defined in `types.ts`, not `registry.tsx`; keep both that way. **Permission decides availability, the user's layout decides display**: "Personnaliser" enters an edit mode with **direct manipulation only — no per-widget control panel**. The desktop grid is **`react-grid-layout` v2** (`GridLayout` + `verticalCompactor`): every widget has a real **(x, y) position** plus size (`width` 1-12 cols, `heightPx`), the whole card is the drag handle (`dragConfig.cancel: '.widget-no-drag'` exempts the hide-eye), edges/corner resize (`resizeConfig.handles: ['e','s','se']`, gold bars styled in `index.css` under `.dashboard-grid`), and dragging shows the library's live placeholder while vertical gravity compacts everything upward — which is what lets a widget sit in the right column under a short neighbour while a tall one fills the left (the earlier order-based flow model could NOT express that; don't regress to it). Hide via the hover-revealed eye; re-show by clicking the tray chip. Below `lg` the grid is bypassed: plain single-column stack ordered by (y, x) with **definite** pixel heights (with `auto` a scrolling widget body never engages and the card grows to its full content). Persistence: `x`/`y` stored per widget (optional in the API schema — pre-positional layouts are shelf-packed at load); saved layouts are normalised through the same vertical compaction so loading isn't already "dirty". **Vite gotcha**: react-draggable inside RGL reads `process.env.DRAGGABLE_DEBUG` — `vite.config.ts` defines it, else the browser throws "process is not defined" on first drag. The trigger and the edit-mode buttons live in the **app header** via the screen-actions slot (`contexts/HeaderActionsContext.tsx`, `mps_designer §3`) — zero vertical cost, and the header is sticky so Enregistrer survives scrolling; right-click on the dashboard background is a secondary accelerator (gated to the background so widget text stays copyable). Saved per user in `data/user-profiles.json` (`GET`/`PUT /api/user-profiles/me/dashboard`); a layout equal to the defaults is stored as `null` so the user keeps tracking future default changes. Adding a widget = **one entry** in `apps/web/src/components/dashboard/registry.tsx` — a widget the saved layout doesn't mention is appended visible, so a stale layout can never hide a newly granted one. Widgets render `<WidgetFrame>` (shared gold header + edit strip) and read `useWidgetChrome()` for their height preset. **Chiffre d'affaires** (`dashboard_ca`, gated on the API too — confidential): ports legacy *Comparatif CA* + *Rapport CA/Client*. Formula reverse-engineered from the data (WinDev sources are PCS-compressed): `CA = Σ round2(ligne_facture.quantite × prix)` over `facture` with `IDsociete = 1`, **`facture.TYPE = 2` (avoir) negated**, accumulated in integer centimes. Route `apps/api/src/routes/rapports.ts` (`/ca-clients`, `/ca-mensuel`); regression check `apps/api/src/scripts/check-ca-legacy-parity.ts`. The widget adds two controls the legacy screen had no equivalent for: a **comparison period** (`period=full|ytd` — `ytd` cuts BOTH years at today's MM-DD so a partial year isn't compared against a full one, and is the **default since 2026-08-26** at the user's request; « Année complète » stays one click away and is the right read on a closed exercise, where the two coincide anyway) and a **view** picker over the client table (classement CA / progressions / baisses / nouveaux / perdus). Progressions and baisses rank on movement in the **ranking**, each dropping the category that has its own view (nouveaux have no rank to climb, perdus left the ranking). **Analyse financière** (`dashboard_finance`, own permission, gated on the API): ports legacy *Analyse Financière*. Cumulative curves (CA, marge brute, charges fixes, charges variables) + the figures of the last upload. ⚠️ **Tout est borné au périmètre de l'EXPLOITATION** — charges = PCG classes **60 à 64**, produits = classes **70 à 74** (`isChargeExploitation` / `isProduitExploitation` dans `finance-common.ts`) : l'EBE se calcule avant le financier, l'exceptionnel et les dotations, donc découper le plan sur « classe 6 = charge / classe 7 = produit » est trop large et fait entrer dans le calcul des postes qui n'y ont rien à faire. Corrigé 2026-08-26 en confrontant le widget au bilan : l'EBE 2025 était gonflé de **6 100 €** (escomptes obtenus 8 011 €, escomptes accordés 1 562 €, dons 350 €) et celui de 2024 de **40 040 €** (compte 768000, 33 896 € de produits financiers). Le périmètre s'applique **aux deux surfaces**, série ET balance de Rapports › Finance, pour que l'invariant « le widget suit l'écran » tienne : les comptes hors exploitation ont donc aussi quitté le tableau du rapport (ETM 665000 / 670000 / 671200 / 671300, TRM 661000 / 670000 / 671200 — 1 914 € et 146 € sur 2025). Le CA n'est plus `upload_compta.produits` (qui somme toute la classe 7) mais un recalcul sur `releve_compta`, ce dernier ne servant plus que de repli quand aucune balance n'est déposée à la date de l'arrêté ; vérifié que le recalcul, borne relâchée, reproduit `upload_compta.produits` au centime sur les 57 arrêtés ETM et les 58 de TRM. Le **fixe/variable split est recomputed** from `releve_compta` bucketed by `compte_compta.frais_variable` — the same arithmetic as the Rapports › Finance screen — and NOT read from `upload_compta.frais_fixe`/`.frais_variable`. ⚠️ Those two columns are a snapshot the accountant's WinDev routine **freezes at write time**, so they encode the classification in force that week: reclassifying a compte restated the report instantly and never reached the chart, while the next upload adopted the new split and stepped the curve mid-year (measured on the dev copy: 7 of ETM's 57 uploads and 30 of TRM's 58 carry a stale split, up to 531 k€). `marge brute = produits − charges variables`, `EBE = marge brute − charges fixes` (provisions stay out); EBE is untouched by a reclassification, since total charges are. Guard: `check-finance-analyse-buckets.ts`, which pins the widget's charges to the report's own `lignes` totals on every société × year, **plus le périmètre** (aucune ligne hors 60-64 dans le rapport, CA de l'analyse strictement égal aux comptes 70-74 de la balance). Uploads are cumulative YTD, so a month's point is the **last upload of that month**, never a sum; the year's first upload is dropped when it's the accountant's close of the previous exercise (early January, dwarfs the next one).

⚠️ **Le point de fin d'année reste un solde d'AVANT CLÔTURE, et ce n'est pas rattrapable.** Le dernier arrêté d'un exercice est celui de fin décembre (22/12/2025 pour 2025) ; les écritures de clôture de l'expert-comptable — cut-off, régularisations, variation de stock définitive, subventions — ne remontent **jamais** dans l'ERP, et l'upload de début janvier porte encore les mêmes chiffres. Sur 2025 cela laisse **32 944 €** d'écart avec le compte de résultat (CA ERP +10 360, charges d'exploitation −26 584, subventions 4 000 absentes). Limite acceptée (décision Vincent, 2026-08-26) : le widget estime en continu, le bilan fait foi. **Calage de référence** : sur l'exercice 2024, clos et donc comparable, l'EBE calculé donne **269 613 €** contre **269 982 €** au compte de résultat — 369 € de résidu. C'est ce calage qui valide le périmètre ; toute retouche de la formule doit le refaire.

⚠️ **Ces figures excluent les provisions** — `upload_compta` ne les porte pas — tandis que **la variation de stock, elle, y EST incluse par estimation** (§Variation de stock estimée). Une mention permanente disait les deux sous les tuiles ; **retirée le 2026-08-26 à la demande de l'utilisateur** — elle annonçait un montant (« variation de stock estimée à 57 622 € et intégrée ») que rien d'autre sur la carte ne permettait de recouper, et coûtait une ligne sur un widget déjà dense. Le calcul est intact et porte toujours l'EBE affiché ; ne pas réintroduire la mention sans lui donner une surface où le chiffre se lit vraiment. Voir §Valorisation du stock widget pour le chiffre manquant. ⚠️ **Ne jamais y réintroduire la « production stockée » : ETM n'en a pas.** La case **FM** du 2052 est vide en 2023, 2024 **et** 2025 (vérifié sur les liasses). Les 178 359 € de 2024 que ce document et le libellé du widget lui attribuaient sont en réalité la case **FP, reprises sur amortissements et provisions** — mention retirée de l'écran le 2026-08-26. Ce qui manquait réellement à l'EBE intermédiaire, c'est la variation de stock du compte de charge **603700**, pas un compte 71, et elle est désormais estimée (voir §Variation de stock estimée). Route `/rapports/finance/analyse`; the hand-rolled SVG chart's palette is validated with the `dataviz` skill's `validate_palette.js` (solid = produits, dashed = charges, the second channel its CVD WARN requires). **Notifications** (`dashboard_notifications`, gated on the API — the cards name client orders and stock levels): ports legacy *FI_Notifications.wdw* + its gear window *FEN_Abonnement.wdw*. See §Notifications widget below

### Notifications widget (tableau de bord)

Legacy model, reverse-engineered from the data (the `.wdw` sources are PCS-compressed): **`abonnement_notif`** is the catalog of subscription types (`nom`/`description`/`icone`), partitioned by `IDsociete` — which is why the société-2 "FNC" entry never appears in an ETM user's list; **`abonnement_user`** is `IDutilisateur × IDabonnement`; **`notifutilisateur`** holds the generated alerts (`hash`/`Titre`/`Description`/`icone`/`visible`), rebuilt periodically by a WinDev routine that deletes rows whose condition has cleared. (`notif_token` is unrelated — FCM push tokens for the Android terminals.)

ETM **shares the catalog and the subscriptions** (same tables, so subscribing here subscribes in the WinDev app) but **computes the alert list live** on every read instead of persisting rows: legacy's `hash` is an opaque SHA-1 whose formula could not be recovered, so any row we inserted would show twice in the legacy app — and the WinDev routine rebuilds that table anyway. Consequences:
- `visible = 0` has no row to live on, so **hiding a card is per user** in `data/notification-hidden.json` (an improvement — legacy's flag hid a card for the whole company). Stale entries are pruned on read, scoped to the detectors that actually ran, mirroring legacy deleting the row outright. The per-card control is an **eye** (`EyeOff` = hide, `Eye` = restore, icon shows the action like `WidgetFrame`'s own hide button), and legacy's "Afficher tout" checkbox is the §41 counter pill in the body toolbar — kept off the navy band so the eye means exactly one thing in this widget.
- **Subscriptions outside this app's catalog are carried over untouched on write.** An ETM user can be subscribed to a société-2 row (real case: user 1 → "FNC") that the dialog never shows and therefore never sends back; rewriting from the payload alone silently unsubscribes them in WinDev. Guarded by `check-abonnements.ts --write`.
- The 8 detectors live in `apps/api/src/lib/abonnements.ts`, keyed by `IDabonnement_notif`; routes `abonnements.ts` (`/api/abonnements*` — **not** `/api/notifications`, which is the unrelated *email*-subscription feature); widget `components/dashboard/NotificationsWidget.tsx`. The header icon is **Tricobot**, not a bell — `components/icons/TricobotMascot.tsx` renders `/tricobot/tricobot-mascot.png` frameless, straight on the navy band (`WidgetFrame` gained an optional `iconBleed`: no gold plate, no ring, for icons that are background-free artwork). That asset is prepared from the **official transparent render** on the shared drive (`Malterre Drive/ETM/Eléments Graphique/TricoBot/3D/no bg better res.png`, 1024², no glow or shadow baked into the alpha) by trimming to its alpha bbox, squaring and downscaling to 512². **Do not** try to key him out of the older opaque `tricobot-wave.png` (still used full-size by the Clients › Commandes pricing nudge) — that was tried and it is a trap: he is a *white* yarn cone on near-white, so only connectivity separates them, the yarn texture lets any gradient fill walk through his silhouette, and his cast shadow cannot come off without eating the cone. Detector 5 is validated exactly against the legacy rows ("Lot de fil N° 10430" is `stock_fil.lot`, **not** the PK; predicate `IDref_fil_commande = 0 AND stock > 0`), and detector 7 keys on the **client order line**, not the ennoblisseur affectation (legacy notified a roll carrying `IDref_commande_affectation = 143`). Both TM detectors scope to the canonical "écru rolls in stock" population from `stock-ecru.ts`, or they would walk ~52k historical rows.
- Volumes are legitimately four-figure (~1k unaffected écru rolls), so the widget caps rendering at 150 cards and **says what it dropped** plus offers a per-type filter. Detection is memoised for 60 s; the header refresh button clears it. Guard: `apps/api/src/scripts/check-abonnements.ts`

### Évolution du CA widget (tableau de bord)

Monthly CA as one line per year with the last 5 years as toggleable pills, plus an **Annuel** bar mode. Permission `dashboard_ca` (same confidential figure as the CA table, enforced on the API); endpoint `GET /api/rapports/ca-evolution?years=N`; widget `components/dashboard/EvolutionCaWidget.tsx`.
- Its own endpoint rather than N calls to `/ca-mensuel`, which returns the whole per-client matrix when the chart needs twelve totals. Same `caForYear` aggregation underneath, so it agrees with the CA table to the centime (cross-checked: 2026 = 663 818,60 € in both). Years are fetched **sequentially** — each is a full-year scan of `facture` on the shared HFSQL server and firing five at once is the burst that upsets the bridge.
- ⚠️ **`caAvailableYears()` counts DOWN from the newest year.** Assuming ascending and taking `.slice(-5)` silently served the five *oldest* years (2020-2024 instead of 2022-2026). The endpoint now sorts explicitly instead of trusting the helper's order.
- For the **current year only**, months after the last invoiced one are emitted as `null`, not `0` — otherwise the line crashes to the axis for the rest of the calendar. Past years keep real zeros (2020's empty first nine months are a fact).
- Chart work follows the `dataviz` skill. Palette **validated, not eyeballed**: `node scripts/validate_palette.js "#3B7DC9,#C2410C,#17915B,#B8860B,#7C3AED" --mode light --pairs all` → all pass with one WARN (`#B8860B↔#17915B` ΔE 6.5 protan) in the 6–8 band, which is legal **only with secondary encoding**; four alternative palettes were validated and all scored worse. So each year also carries a distinct **dash pattern** and the **year pills above the chart** name every year next to its colour — identity is never colour-alone. Colour is keyed on the year's **recency** inside the *full* list (newest = style 0), never on its rank among the *visible* ones, so toggling one off never repaints the survivors.
- **The running year leads the chart** (2026-08-26): newest year = style 0, solid accent blue, `STROKE_LEAD` 3.25 against `STROKE_BACK` 1.75 at 0.72 opacity for the others, and drawn last so it sits on top. Before that it took whatever style the ascending list had left over — a dashed violet, the least legible of the five — and the reader had to hunt for the line that matters most.
- **No legend under the chart** (2026-08-26, user request): it restated what the pills already say and cost a whole row on a 420 px card. Hovering a month opens a **tooltip** listing every visible year's CA for that month, **ranked** — the read becomes « ce mois-ci, qui fait quoi » instead of « voici les couleurs ». It is positioned in the plot's own pixel space (the SVG is drawn at real size, so SVG units *are* CSS pixels), flips side past the middle and clamps vertically, so it never leaves the card at any width. "Annuel" has no pills, so each bar now carries its total above it — the number the legend used to hold — and hovering gives the exact centime over a full-height hit target.
- Axis ticks come from the shared `lib/chart-scale.ts` (`niceScale`, extracted from `AnalyseFinanciereWidget`) so both charts tick at round numbers rather than the raw maximum.
- The SVG is drawn at the container's **measured pixel size**, never a `viewBox` + `preserveAspectRatio="none"` — that stretches month labels horizontally as the card is resized.

### Valorisation du stock — calcul ACTIF, widget EN SOMMEIL

Valeur d'achat et valeur dépréciée du stock, taux de provision, détail par type. Permission `dashboard_stock_valorisation` (**gated on the API** — c'est un poste de bilan) ; endpoint `GET /api/rapports/stock/valorisation` ; calcul `apps/api/src/lib/valorisation-stock.ts` ; composant `components/dashboard/ValorisationStockWidget.tsx`.

⚠️ **`valorisation-stock.ts` N'EST PAS DU CODE MORT, malgré l'absence d'écran.** `variation-stock.ts` l'appelle (`valoriserStockCache()`) pour estimer la variation de stock injectée dans l'**EBE** — Analyse financière **et** rapport Finance. Le supprimer ferait retomber l'estimation à zéro **sans erreur**, et l'EBE intermédiaire redeviendrait faux de plusieurs dizaines de milliers d'euros. Garde : `check-valorisation-stock.ts`.

⚠️ **Le widget a été retiré du tableau de bord le 2026-08-26** (une entrée commentée dans `registry.tsx`, rien d'autre supprimé). Il répondait à « combien vaut mon stock » — question de **bilan**, à cadence annuelle — et affichait un taux de provision **sans point de comparaison**, donc ininterprétable au quotidien. Décision Vincent : « j'attends que le besoin s'exprime vraiment ». **Le rétablir = rétablir cette seule entrée** ; endpoint, permission, composant et guard sont intacts. La clé de permission reste (elle garde l'endpoint) mais son libellé dit « widget retiré », sinon un admin la coche et ne voit rien apparaître. **Si le besoin revient, viser la « falaise », pas le niveau** : `valoriserStock(asOf)` accepte une date et vieillit le stock courant, donc « à périmètre constant » se calcule sans requête nouvelle — mesuré au 26/08/2026 : **−108 597 € de valeur nette à 6 mois, −182 103 € à 12 mois** si rien ne bouge, ce qui est une liste de priorités de vente et non un chiffre de bilan.

**Pourquoi il existe.** `upload_compta` ne porte pas les **provisions**, donc l'Analyse financière ne les voit structurellement pas — un stock passé de 37 % à 49 % de provision entre 2024 et 2025 n'apparaissait nulle part. (Une version antérieure de ce document invoquait aussi la « production stockée » : ETM n'en a pas, la case FM du 2052 est vide sur les trois derniers exercices — voir §Analyse financière.) Le mécanisme légataire, **`inventaire_compta`** (un arrêté mensuel par type, `prix_achat` brut + `valeur_deprecie` net), **a cessé d'être écrit le 28/06/2025**.

**Populations** (toutes en état courant) : fil = `stock_fil.stock > 0` **et `IDclient = 1`** (Ets Malterre — le fil confié est dans nos murs mais pas à notre bilan : 46 lots / 8 201 kg exclus) ; TM = écru ETM non expédié et sans enfant `stock_fini`, scindé par **`IDref_commande_affectation`** (≠ 0 → en ennoblissement) — ⚠️ **pas** par magasin, MATEL apparaît dans les deux inventaires imprimés ; fini = `IDligne_expedition = 0 AND IDetat_stock_fini = 3`.

**Coûts** : fil = `ref_fil_commande.prix_unitaire` (prix réellement payé), repli `ref_fil.prix_kg` ; écru = fil + façon tricotage (`ligne_commande_sous_traitant.prix`, repli `ref_ecru.prix`) ; fini = + ennoblissement (prix réel commandé, sinon forfait `tranche_tarif_ennoblissement` à 200 kg). Le poids vient de **`stock_ecru.poids`**, pas de `stock_fini.poids`.

- ⚠️ **L'escrime n'est pas couvert** — pas d'inventaire dans l'ERP. Fin 2025 : **57 600 € brut / 13 935 € net**, soit l'écart exact entre le total des quatre types et le bilan. Manque chiffré, pas inconnu ; le widget l'affiche.
- ⚠️ **Ne peut décrire que MAINTENANT** : colonnes d'état courant + dépréciation depuis la date du jour. Un arrêté passé n'est pas rejouable, donc les 14 mois manquants d'`inventaire_compta` ne sont pas récupérables.
- ⚠️ **`asso_fil_matiere` et `matiere_premiere` ont des identifiants ACCENTUÉS** (`IDMatière`, `IDmatière_première`) que le pont Linux refuse → `SELECT *` + résolution par préfixe (`pickKey`), jamais nommés en SQL. À l'inverse `stock_fil` porte des memos binaires → colonnes nommées explicitement (`SELECT *` y renvoie 0 ligne sur Windows). Vérifié en exécution sur le serveur de prod.
- ⚠️ **`asso_fil_matiere.pourcentage` est une FRACTION** (0,31 = 31 %), pas 0-100 — contrairement à `composition_ecru.pourcentage`. Une ref est « 100 % élasthanne » si toutes ses matières le sont et que la somme fait 1.
- ⚠️ **`date_saisie` / `date_entree` reviennent en TIMESTAMP** (`"2020-10-04 00:00:00.000"`). `sst-shared.dateDigits` exige `/^d{8}$/` et renvoie donc `''` sur **toutes** les lignes ; une chaîne vide perd toute comparaison `>` et range l'intégralité du stock dans la tranche la plus vieille à 90 % — un chiffre plausible, pas un plantage. Le module a son propre `d8()`. Garde : `check-valorisation-stock.ts`, qui échoue si un type n'a qu'une tranche peuplée.

### Variation de stock estimée (compte 603700)

L'écriture de variation de stock est **annuelle**. Onze mois sur douze le compte reste à zéro, le compte de résultat porte donc le coût complet de la production *y compris ce qui dort en magasin*, et l'EBE intermédiaire est amputé d'autant — c'est ce qui a fait lire l'EBE de juillet 2026 (88 k€) comme un effondrement alors que 59 k€ de stockage l'expliquaient. Calcul `apps/api/src/lib/variation-stock.ts`, injecté dans `finance-common.ts` (les deux surfaces à la fois).

- **Le compte est `603700`, seul compte de variation de stock du plan ERP, et c'est une charge VARIABLE** — un montant négatif y remonte donc marge brute et EBE. Historique : 81 083 € (2024), 59 092 € (2025), 0 € (2026).
- ⚠️ **L'estimation ne s'applique QUE si la valeur comptabilisée est à zéro.** Le jour où l'expert-comptable passe l'écriture, le vrai chiffre reprend la main tout seul et le badge disparaît — rien à nettoyer, aucun risque d'écraser une écriture réelle. C'est la propriété de sûreté centrale du dispositif.
- **Niveau exact, forme approchée.** Le montant vient de deux photos réelles du stock (dernier arrêté `inventaire_compta` de N-1, et `valoriserStockCache()` aujourd'hui) : les deux bouts sont justes. La répartition mensuelle suit les kilos physiques accumulés (écru produit − écru/finis expédiés), **bornée à [0, montant]** — la forme brute ignore les achats de fil et la valeur ajoutée écru → fini, donc son pic dépassait le point d'arrivée de moitié (−178 538 € au mois 2 pour un total de −114 556 €). Assumé comme outil de pilotage, pas comme écriture (décision Vincent, 2026-08-25).
- ⚠️ **La base DOIT être une clôture d'exercice** (décembre de N-1), jamais le dernier arrêté venu : une série arrêtée en juin ferait porter à l'année suivante une variation de quatorze mois — un chiffre faux qui a l'air juste. Sans clôture, aucune estimation et l'écran montre le vrai zéro (cas de la copie dev, qui n'a pas l'arrêté 2025).
- ⚠️ **Le dernier mois actif se lit sur les MOUVEMENTS, pas sur le cumul** : un cumul reste non nul une fois démarré, donc le chercher là-dedans renvoie toujours décembre et l'estimation s'étalait sur des mois qui n'ont pas encore eu lieu.
- **ETM seulement** (`scope.societe === 1`) : `inventaire_compta` et la valorisation n'existent que pour cette société ; TRM lit son compte tel quel.
- **Amorçage de la série** : `seed-inventaire-compta.ts` (`--write` / `--revert`, idempotent) a posé l'arrêté du 31/12/2025 depuis les quatre inventaires imprimés ; celui du 28/12/2024 était déjà en base. Contrôle bilan **avant** écriture, sinon refus. ⚠️ Déviation assumée : le type Fini était stocké en **métrage** (`unite = 3`) par WinDev ; ce métrage est irrécupérable au 31/12/2025 (reconstitution depuis les numéros de pièce : 17 570 kg retrouvés sur 21 039), donc l'arrêté amorcé est **en kilos pour les quatre types**.
- Garde : `check-valorisation-stock.ts` (base = clôture, deux bouts justes, interpolation bornée, signe constant, pas de mois futur) et `check-finance-analyse-buckets.ts`, qui prouve que l'estimation atteint le rapport ET le widget avec la même valeur.

### Charges widget (tableau de bord)

Charges fixes and charges variables for the current exercice, each read as a **rythme**: how much of last year's whole envelope is already spent, against how much of the year has actually been lived. Widget `components/dashboard/ChargesWidget.tsx`.
- **No new endpoint and no new permission**: it calls the report's own `GET /api/rapports/finance` (82 comptes ≈ 15 KB — small enough that a dedicated endpoint would only add a second place for the aggregation to drift) on the **same React Query key** `['rapport-finance', null]`, and is gated on **`view_rapport_finance`**, which that endpoint already enforces. A separate `dashboard_*` key could only produce a state where the widget shows and the data 403s.
- It sums the endpoint's `lignes` by `variable` **exactly as the report's totals bar does**, not the pre-computed `totaux.frais_fixe`/`frais_variable` buckets. They agree today, but the screen is what users read, so the widget follows the screen. Verified against the report: fixes 111 604,54 / 478 967,27 → 23 %, variables 610 431,35 / 2 175 473,81 → 28 %.
- ⚠️ **The card no longer shows the raw N/N-1 ratio as its verdict** (2026-08-26). The user's own framing: « si les charges fixes sont à 50 % à la moitié de l'année, on est bon ; moins, c'est encore mieux ; plus, il y a un problème à investiguer ». So the number that matters is the ratio **minus the share of the year elapsed**, in points — because a raw « 23 % » in March means nothing on its own. That écart is the pill; the gauge draws both quantities at once (fill = consumed share of the N-1 envelope, vertical navy tick = the repère), so everything left of the tick is money not yet spent. Scale is fixed 0→100 % of N-1 on both cards, or they would stop comparing to each other; an overrun fills the gauge and the pill carries the amplitude.
- ⚠️ **The repère is measured at the ARRÊTÉ date, not at today.** The last upload can be months old (23/03 while today is 26/08), and it is the date of the *amounts* that must bound the comparison — using today would make the rythme look falsely good. UTC arithmetic throughout: a local-midnight `Date` slips a day around a DST boundary, and the repère with it.
- ⚠️ **Fixes and variables do NOT share a verdict scale, on purpose.** Charges *fixes* carry the alert ladder (±3 pts tolerance = « au rythme », up to +10 amber « à surveiller », beyond red « à investiguer », below green « sous le rythme »). Charges *variables* carry **none**: they follow activity, so above the pace means the company produced more — the user said as much — and they wear an informative sky blue. Painting both red would teach the reader to ignore the colour on both cards. Thresholds are in points of percentage, not euros, so they read the same on a 600 k€ poste and on a 10 k€ one.
- The report's own per-compte pill **stays** the raw N/N-1 traffic light (`lib/depassement.tsx`, `<100 %` emerald / `≤120 %` amber / `>120 %` red, nothing when N-1 is empty) — « ce compte a-t-il dépassé l'an dernier ? » is a different question from « sommes-nous dans les clous à cette date ? ». Two readings of the same two numbers: do not unify them without deciding which one the report should be asking. TRM's dashboard has the same widget over its own partition — the component and `depassement.tsx` are verbatim mirrors there, so improve them **here** and re-copy.
- The footer names the tick and carries the **arrêté date**, not just the year: `upload_compta` rows are cumulative YTD, so an amount only means something alongside the date it was stopped at.

### BFR / bilan — hors de portée, et pourquoi (constat 2026-08-26)

Question posée : un widget **BFR** (besoin en fonds de roulement) pour ETM. Réponse
mesurée sur la base vivante, pas déduite : **non, pas en l'état**, et le raccourci
évident est fermé. Consigné ici pour qu'une prochaine session ne refasse pas l'enquête.

BFR = stocks + créances d'exploitation − dettes d'exploitation. Chaque terme demande un
compte de **BILAN** (classes PCG 3, 4, 5), alors que toutes les surfaces finance
construites jusqu'ici ne touchent que les classes 6 et 7.

- ⚠️ **`compte_compta` ne contient AUCUN compte sous 600000**, ni pour la société 1 ni pour
  la société 2. Les sous-classes présentes sont 60-64, 66, 67, 70, 75, 76, 77 — et rien
  d'autre. Les 84 lignes de `releve_compta` au dernier arrêté ETM (20260323) sont toutes en
  classe 6 ou 7. **Ce que l'expert-comptable dépose est un compte de résultat, pas un
  bilan** : pas de 411 clients, pas de 401 fournisseurs, pas de 3x stocks, pas de 512.
  C'est le même constat qui explique pourquoi l'EBE s'arrête où il s'arrête.
- ⚠️ **L'ERP n'enregistre aucun règlement.** `facture` a exactement 14 colonnes —
  `IDadresse, IDfacture, IDclient, date, IDmode_paiement, IDtva, num_tva, IDecheance, type,
  IDsociete, numero, IDcode_comptable, IDexpedition_divers, IDcommande_client` — et pas une
  n'est un paiement. Un encours client ne peut donc être que **théorique** (« si chaque
  client paie pile à l'échéance »), ce qui sous-estime précisément les mauvais payeurs.
  Matière première disponible pour ce calcul : `echeance` est structurée
  (`TYPE` / `nb_jours` / `jour`, 26 lignes, T1 = à réception ou acompte, T2 = net à N jours
  date de facture, T3/T4/T5 = variantes fin de mois) et `facture.IDecheance` est renseigné.
- ⚠️ **Aucune facture fournisseur dans les 204 tables**, et `fournisseur` n'a que 7 colonnes
  (`IDfournisseur, nom, tel, fax, commentaire, est_visible, IDsociete`) — même pas de
  conditions de paiement ; `sous_traitant` non plus. Le poste dettes fournisseurs n'a
  **aucune source**, et ce n'est pas un arrondi : les achats et services extérieurs
  (comptes 60→62) pèsent 669 857 € au 23/03/2026.
- Seul terme réellement **mesuré** : les stocks, par `lib/valorisation-stock.ts` (brut ET net
  après dépréciation) — voir §Valorisation du stock, y compris son trou connu de
  13 935 € net d'escrime hors ERP.

**Conséquence : ne pas publier un widget étiqueté « BFR ».** Il afficherait un nombre qui
n'en est pas un, et faux dans le sens dangereux — gonflé, puisqu'il manquerait tout le
financement fournisseur.

Trois sorties possibles le jour où le sujet revient, de la meilleure à la moins bonne :
1. **Demander à l'expert-comptable d'inclure les classes 3/4/5 dans son export.** Le BFR
   devient exact, chaque terme mesuré, sur la machinerie `finance-common.ts` déjà en place.
   C'est une demande à une personne, pas du code — et de loin le meilleur rapport.
2. **« BFR estimé » calibré sur le dernier bilan** : stocks mesurés + créances = run-rate CA
   × DSO + dettes = run-rate achats (60→62, déjà dans `releve_compta`) × DPO, les deux
   constantes venant de la liasse du dernier exercice clos et rafraîchies à chaque clôture.
   Le widget devrait alors afficher les paramètres ET leur millésime.
3. **« Encours d'exploitation »** — stock net + encours client théorique, deux tuiles, mention
   explicite « hors dettes fournisseurs ». Constructible sans intrant extérieur, mais ne
   répond qu'à la moitié de la question.

⚠️ Note de méthode : la **copie dev s'arrête au 24/03/2026 pour `facture`** (et au 23/03 pour
`upload_compta`), alors que les commandes y vont jusqu'au 24/08. Un encours théorique calculé
sur la copie dev sort donc à **0 €** — artefact du jeu de données, pas du calcul. Toute
vérification de ce genre doit se faire sur la prod.

Endpoint `GET /api/commandes-client/du-jour?date=YYYYMMDD` (**declared before `/:id`**; `?date=` exists for testability and a future "hier" control, defaulting to today); widget `components/dashboard/CommandesDuJourWidget.tsx`.

Ports legacy *FI_Suivi_pièce.wdw*: type a piece number → its life story (écru → transferts → rouleaux finis). - **`stock_ecru.IDref_commande_source` / `IDref_commande_affectation` hold a `ligne_commande_sous_traitant` id, NOT a commande id.** Legacy prints the parent commande — the piece stores ligne 8437 and the screen says "Commande source : 8461 - Tricotage Malterre" — so both are resolved up through `ligne_commande_sous_traitant` → `commande_sous_traitant` → `sous_traitant`.

  - A piece has **two** expedition paths: `stock_fini.IDligne_expedition` (the client shipment) and `stock_ecru.IDligne_expedition_ETM/_TRM` (a TRM-knitted piece ships to ETM before dyeing).
- **Presentation is reverse-chronological** (newest at top) with a header strip answering "where is it now" (état pill pushed right), and it distinguishes **objects** (tombé de métier / rouleau fini — solid cards, coloured left edge) from **events** (transferts, expéditions, commandes — dashed frames). Order: expédition client → fini → commande ennoblissement → transferts → expédition écru → tombé de métier → commande tricotage (+ its OF/machine) → fils. The écru badge reads **"Tombé de métier"**, not "Écru". The two production orders share one `CommandeCard`, tinted to the stage they *produce* — **green dashed = ennoblissement**, **amber dashed = tricotage** — so each order sits with its output.
- Both roll cards carry the **défauts / observations hover icons** of Clients › Commandes (red triangle incl. "2e choix", blue speech bubble), read-only. Sources differ by stage and that matters: the écru side uses `stock_ecru.observations` + structured defects via the file's own `fetchDefectsByEcru`/`defautSummary`; the **fini side uses the roll's own `observations` + `observation_sst` + `second_choix`** and deliberately does NOT touch `defaut_qualite` — see the ambiguity note in §HFSQL rules. Both stage cards use the same shape: **reference as the title, designation as the subtitle**. The tricotage card deliberately shows neither OF nor machine (noise beside the order itself) — the OF is still what the yarn list is read through, just not displayed.
- A shipped roll's **location is its customer**, not `IDmagasin`: once expédié, `stock_fini.IDmagasin` still points at the last internal depot (often `0` = Ets Malterre) and would claim a delivered roll is still in the building — the header takes `expedition.client` instead. Transferts show **no "non validé" tag**: `bon_transfert.est_valide` doesn't gate the movement (legacy applies a bon to stock immediately), so flagging it read as a problem where there is none.
- Facts are placed by **which stage they're true of**, not by which table they live in: the écru card shows no magasin and no ennoblisseur (`stock_ecru.IDmagasin` is where the record sits *today* — a fact about the finished roll, already in the header; the ennoblissement order is the step that *ended* that stage, so it has its own card), and the fini card drops its magasin once shipped, since the expédition above already says where it went. Expéditions render **sender → recipient**, the sender coming from `expedition.IDsociete` (1 Ets Malterre / 2 Tricotage Malterre / 3 Confection) — printing only the client made the TRM→ETM écru leg look like it went nowhere. Guard: `apps/api/src/scripts/check-suivi-piece.ts` (pins the legacy screen's piece **and** the enrichment joins on a complete chain)
2. **Prospects** (renamed from legacy "Marketing") — **Demandes** (`/prospects/demandes`; catalogue requests from the `prospect` table; master-detail, implemented)
3. **Clients** — Commandes, Devis, Facturation, Gestion

    **Clients › Gestion — compte client** (`client.compte`, the chart-of-accounts code): mandatory and format-checked. "+ Nouveau" opens a **création dialog** (nom / secteur / activité) rather than inserting a `Nouveau client` placeholder — knowing the name before the INSERT is what lets the code be derived from it. Generation lives in `apps/api/src/lib/compte-client.ts` (`pickCompte`), mirrored client-side by `apps/web/src/lib/compte-client.ts` for live validation; guard `apps/api/src/scripts/check-compte-client.ts` replays it over all 654 clients. **Generation emits `411` + 3 alphanumerics, validation accepts `411` + 3-or-more** — the legacy table holds 388 four-char codes that must stay editable (225 are three-char, 36 are other shapes). Mnemonic candidates come from the name's significant words, skipping legal forms (SARL/SAS/SOCIETE…) and industry-generic words (BONNETERIE/TRANSPORTS/ATELIER…) exactly as the accountant did — "Bonneterie Gautier" → `411GAU`; collisions fall through consonant squeezes then numeric variants (`411SO2`), with an exhaustive base-36 sweep as the guaranteed last resort. Uniqueness is **not** scoped by `IDsociete` (the code identifies the company in the ledger) and is enforced **only on values that change** — 10 duplicate codes already exist in legacy data and must stay saveable. The duplicate check runs **live as the user types**, on both the dialog and the Info tab: `GET /clients/comptes` returns every code in use and `useComptesPris()` caches it under one query key (React Query dedupes, so the InfoTab call costs nothing extra), which greys out Créer / Enregistrer instead of ambushing the user after the click. Server-side re-validation on POST/PUT stays the authority — the cached set can go stale if someone else creates a client meanwhile. Entering edit mode on a client whose compte is empty or malformed auto-fills a suggestion (snapshot updated too, so the pre-fill alone isn't "dirty"); an invalid value blocks the save and the exit via `useUnsavedGuard`'s `shouldBlockExit` (`mps_designer §28.5b`). Only the `edit_client_info` scope writes the column, so validation is gated on that permission — a user who cannot edit it is never blocked by it.
    **Clients › Gestion — SIREN** (`client.siren`, ticket #1088): 9 chiffres, dans la carte Facturation sous le N° TVA. **Facultatif** — la colonne se remplit client par client, donc seule une valeur non vide est contrôlée (sinon 400 `siren_invalide` + exit bloqué via le même `infoIssue` que le compte). ⚠️ **La clé de Luhn est un AVERTISSEMENT, jamais un refus** : le registre a porté des identifiants qui ne la vérifient pas, et bloquer une saisie légitime coûte plus cher que la faute de frappe qu'on attrape. **Colonne détenue par la fiche ETM seule** — `clients-trm.ts` ne la nomme pas (invariant ci-dessous), l'ajouter côté TRM demandera de la nommer là-bas. **Elle ne part sur aucun document** : la facturation électronique reste à faire. Helpers `lib/siren.ts` (API + miroir web), garde `check-siren.ts` (`--roundtrip`).
    **TVA — the rate belongs to the CLIENT, never to the société.** Every customer-facing document takes it from `client.IDtva` → `tva.valeur` via `apps/api/src/lib/tva.ts` (`loadClientTvaRate`, falling back to the société-1 `est_defaut` row **only** when the client has no row). Each société has an "Exonération" row at `valeur = 0` used for export customers (Maroc, hors UE): a 0 rate is a real value, not "unset", so it must never fall through to the default. A 0 rate also **collapses the totals block** — no TVA line, no TTC line, the document ends on `TOTAL HT` (the sub-total row survives only when a remise or frais de port makes it differ). Applies to the confirmation de commande, the devis, the proforma and the facture; a `facture` additionally **stores its own `IDtva`** copied from the client at creation, so an old invoice keeps the rate it was issued with. Guard: `check-tva-exoneration.ts`.
    **Clients › Gestion — the `client` table has TWO ledgers.** `client` is partitioned by `IDsociete` (1 ETM / 2 Tricotage Malterre / 3 Confection), so this API serves two fiches: `routes/clients.ts` (`/api/clients`, ETM) and `routes/clients-trm.ts` (`/api/clients-trm`, consumed by the TRM app — its screen lives in the sibling repo and is deliberately NOT an `@etm` shared screen: the two fiches show different fields). Shared plumbing lives in **`lib/clients-common.ts`** — SQL/format helpers, `requirePermission`, `repairNames`, `countClientActivity`, the accented-flag helpers `setClientFlag`/`readClientFlag` (`archivé` + `bloqué`, delete + positional reinsert on Linux), and `registerContactAdresseRoutes()` (`contact`/`adresse` are polymorphic on `IDclient` and NOT partitioned, so both mounts register them verbatim). **The invariant that keeps the two fiches from wrecking each other: a router must never NAME a column the other fiche owns** — an unnamed column keeps its stored value on `UPDATE`, a named one is zeroed on every save. ETM owns `client_interne` / `IDsecteur_activite` / `IDactivite` / `journal_commercial` / `dernier_contact` / `inclureRapportQualite` / `pct_ajeol`; TRM owns `rib` / `domiciliation` / `IDtransporteur` / `bloqué` (its « Attente paiement facture » checkbox). **`tva` and `code_comptable` are partitioned too** — serving ETM's rows to a TRM screen would silently rewrite a client's VAT to another company's row on the next save. Full detail: `claude_doc/implemented_screens.md` § Clients TRM.
    **Clients › Commandes — le prix d'une ligne écru/fini dépend du CLIENT, jamais du seul catalogue.** `lib/tarif-client.ts` (extrait de `routes/clients.ts`, partagé avec la fiche client) résout le mode tarifaire de la paire (référence × coloris) via `designation_client` → `ref_client_colori`, et `calcLignePriceClient` en tient compte : **contrat actif** → le `prix_saisi` négocié (€/Ml, converti en €/Kg par le rendement pour une ligne Kg) et un nudge Tricobot restreint aux tranches que ce contrat cote ; **coefficient fixe** → la marge du client à la place de la dégressive ; **standard** sinon. ⚠️ **Un contrat expiré ne retombe PAS sur la grille standard** — la référence n'est plus vendable tant qu'un nouveau contrat n'est pas établi (même règle que la fiche client) : l'endpoint renvoie `blocked` + `blocked_reason` dès le choix du coloris, le dialogue affiche le bandeau rouge et grise Enregistrer, et POST/PUT `/lignes` répondent **409 `contrat_expire`**. Le PUT ne bloque que sur un changement **commercial** (référence, coloris, quantité, prix) : une ligne prise quand le contrat était valide reste modifiable pour sa date et son commentaire. Bug d'origine (30/07/2026) : l'auto-pricer ne recevait pas le client, donc une commande C2TEC est passée un mois après l'expiration du contrat #475, sans rien à l'écran — et un client sous contrat actif était coté 12,00 €/Ml au lieu de 3,81 €/Ml négociés. Garde : `apps/api/src/scripts/check-contrat-tarif-ligne.ts` (épingle le cas C2TEC + rejoue tous les contrats actifs et coefficients de la base).

    **Clients › Commandes — le sélecteur de coloris est limité au catalogue du client.** `/lookups/colori-ecru|colori-fini` acceptent `client` (+ `current`) et ne proposent alors que les coloris enregistrés en Gestion pour cette (client × référence) via `ref_client_colori` — une référence teinte pour des dizaines de clients offrait sinon **389 coloris là où le client en achète 71**. Trois états, et les deux derniers **retombent sur la liste complète** (jamais de sélecteur vide, qui rendrait la référence non commandable), chaque ligne portant alors `hors_catalogue: true` pour que l'UI le dise : catalogue exploitable → liste restreinte ; aucun `ref_client_colori` (13 des 2 025 entrées fini actives) → repli ; **catalogue disjoint de la liste affichée** → repli aussi (cas réel client 202 / ref 1426 : les rcc pointent des `colori_ecru` d'un `ref_ecru` que le fini ne référence plus). `current` (le coloris d'une ligne existante) est toujours conservé et marqué — **381 des 7 062 lignes historiques sont hors catalogue** et perdraient sinon leur coloris à l'ouverture du dialogue. ⚠️ **Sans `client` la liste reste complète** : c'est ce dont Clients › Gestion a besoin, puisque c'est l'écran où le catalogue se construit. Garde : `apps/api/src/scripts/check-coloris-client-scope.ts`. Le même angle mort existe encore sur **Devis** (`/devis/lookups/colori-*`).

    **Clients › Commandes — lignes divers** (`ligne_commande_client.TYPE = 3`) price off the **`tarif_divers` grid**, never the roll-tranche tariff of écru/fini: the shared resolver `GET /expeditions/divers/lookups/prix?ref&v1&v2` (exact combo → `(v1,0)` → `(0,0)` → `ref_divers.prix_unitaire`), the same one the Expéditions article dialog uses. Two data facts drive the UX: a **two-axis reference has no `(0,0)` row** ("Tissu Voltige" = 533 cells keyed couleur × taille), so the price is legitimately undefined until *both* axes are picked — an empty field mid-form is not a bug; and ~417 of 1 836 existing divers lines point at refs with **no grid entry at all**, so manual entry must stay open — this field carries **no padlock and no `deverrouiller_tarifs` gate**, unlike écru/fini. A saved line keeps its own `prix` as an order-time snapshot (replaying the grid over legacy lines reproduces 1 346 exactly and differs on 59 that pre-date a price change) — never re-derive an existing line's price; only a stored `0` gets refilled.
    **Clients › Facturation — « Générer les factures » balaie DEUX registres d'expédition, avec deux groupements** (`POST /factures/prov/generate`). **Formelle** (`expedition`) : un proforma **par client**. **Divers** (`expedition_divers`) : un proforma **par expédition** — groupement de legacy, imposé par le schéma, le lien retour étant la colonne d'en-tête `IDexpedition_divers` qui ne tient qu'un id (535 factures legacy, une expédition chacune, jamais mêlée à une ligne formelle). Ce back-pointer est écrit sur `facture_prov` puis recopié à la conversion, et `wipeOpenProformas` s'en sert pour rouvrir l'expédition ; ⚠️ **ce n'est PAS un « marqueur de conversion »** — un ancien commentaire l'affirmait, 0 ligne en base l'utilisait ainsi. Divers = ETM seulement (pas de colonne `IDsociete`) → passe **sautée sur le montage TRM**. Les règles de ligne, reconstituées puis validées sur le registre définitif, sont commentées dans `factures.ts` ; les deux contre-intuitives : **un même article réparti sur plusieurs cartons ne fait qu'UNE ligne** portant le total, et `unite = 4` s'imprime **« Pièce »** sur une facture là où le bon de livraison dit « unité ». Frais de port : **une fois par commande pour tout le run**, garde partagée par les deux passes. Garde : `check-divers-facturation.ts` (rejoue les 496 expéditions facturées ; échoue sur toute divergence au-dessus de l'avis 575 — en dessous les factures ont été saisies à la main). Bout-en-bout avec rollback : `e2e-divers-generate.ts`.

    **Divers › Stock — `stock_divers` is SPARSE, and that drives the whole screen.** It is not a grid of every combination: it is a log of the combinations someone has touched (1 466 theoretical combos across the 505 references vs 276 rows stored — Tissu Voltige alone has 551 possible and 117 stored), and **214 of those 276 rows sit at quantité 0**. So the list **hides zero rows unconditionally** — no toggle, no filter control — leaving the ~62 lines that actually hold stock; a zeroed row is meant to be indistinguishable from a combination that was never created. A **negative** quantity is NOT hidden (data error, must stay visible). Consequence for writes: `POST /stock-divers` is an **upsert**, because 214 invisible rows would otherwise 409 "modifiez la ligne existante" for a line the user cannot find — it fills an **empty** row silently (the user's mental model is "I added a line"), but a combination that **already carries stock** still 409s and names the quantity, since silently overwriting a visible figure would destroy real data. `create_stock_divers` alone gates the upsert: it can only ever turn a 0 into a quantity. The create dialog therefore refuses quantité 0 (the line would vanish on creation), and the drawer says so when a row is zeroed. One duplicate combination exists in legacy data (ref 535 / variation 558, both rows at 0) — the upsert picks the lowest `IDstock_divers`, and refuses if *any* row of the combo carries stock.

    **Envoyer la FNC = a handover, not just a mail.** `POST /dossiers-qualite/:id/fnc/envoi` (and `…/fnc/email`, which does the same once the mail has actually left) stamps `envoiFNC` **and creates the `retour_client` row** that opens the dossier on the destination company's side — TRM reads it in its Qualité › Retour client screen. Until 2026-08-26 the button was an "En developpement" dialog, so a FNC sent from here reached nobody. Rules: **idempotent** (a second send never opens a duplicate dossier for the atelier); only `IDSociétéFNC = 1` (Tricotage Malterre) can be handed over (Confection's `retour_client_confection` is a different table with no screen — a FNC aimed at it still mails, and says `handover: 'unsupported_societe'`); the handover runs **after** the send, so a failed mail never opens a dossier nobody was told about. The answer comes back the other way through **`writeFncReponse()`** — the only writer of `reponseFNC` outside this file's own PUT, exported so the `"<libellé>\r\n<commentaire>"` encoding has one owner. ⚠️ `dossier_qualite.IDclient` is ETM's END client; the TRM mirror names *its* client (Ets Malterre), resolved by société name in `lib/retour-client-trm.ts` — which raises rather than guessing, since a silent fallback would file the complaint under whichever client happens to be id 1. Table primitives live in that lib (not in either route file) precisely because both routers write `retour_client`. Guard: `scripts/check-retour-client-trm.ts`.

    **Qualité › Actions** ports legacy `FI_Action_Qualité.wdw`. An *action qualité* (`action_qualite`) is a tracked quality topic owning *mentions* (`mention_qualite`) — automatic comments that print on every matching bon de commande sous-traitant — each accumulating *conformité* verdicts (`conformite_action`, one per (sst order line, mention): `Non_Contrôlé` / `Conforme` / `Non_Conforme` / `Aucun`). Data layer + matching rule: `apps/api/src/lib/actions-qualite.ts`; routes `actions-qualite.ts`; screen `QualiteActions.tsx` (Fiche). Verdicts are entered from **Suivi lots › onglet Actions**; mentions surface read-only on **Sous-traitants › Commandes** and in a red `MENTIONS QUALITÉ` block on the bon de commande PDF. Key facts:
    - **Matching rule** (validated: reproduces all 248 legacy `conformite_action` rows): a mention applies to a `ligne_commande_sous_traitant` when `lcs.type = IDtype_sst` AND `lcs.IDreference = mention.IDreference` AND (`mention.IDsous_traitant = 0` OR = the commande's sst) AND (`mention.IDColoris = 0` OR = `lcs.IDColoris`). `0` is legacy's "tous" **wildcard** here, not missing data. The mention's ref/coloris are polymorphic exactly like the line's (type 1 → `ref_ecru`/`colori_ecru`; type 2 → `ref_fini` + the `avec_teinture` coloris rule).
    - **Mentions are never persisted onto the commande** — legacy didn't either (no order `commentaire`/`journal` contains a mention's text). Resolved live so editing an action updates every future bon de commande. Single source: `GET /commandes-sous-traitant/:id/mentions-qualite`, shared by screen + PDF.
    - **`mention_qualite` has an accented PK *and* accented parent FK** (`IDmention_qualité`, `IDaction_qualité`) — no ASCII handle exists for a `WHERE`. Linux writes therefore rewrite the whole **`IDreference` bucket** (delete by the ASCII `IDreference`, positional re-insert preserving each row's PK and parent). `conformite_action`'s PK is ASCII thanks to the legacy typo **`IDconfomite_action`** (conf-**o**-mite, no `r`) — mis-reading that column name makes every PK parse as `0`, so `max+1` collapses to `1` and the next write silently overwrites real row 1. `assertPk()` guards every computed-PK site.
    - **Archiving is manual, by explicit product decision.** The per-action *objectif de conformités* (stored in `data/action-qualite-targets.json`, not HFSQL) only lights up an "objectif atteint" cue — it must never auto-close an action.
    - Guard: `apps/api/src/scripts/check-actions-qualite.ts` (`--write` for the round-trip). Its `--linux` flag **refuses to run off a Linux host**: `queryB64Text` is a passthrough on Windows, so simulating the bridge there reads mangled text and writes it back over neighbouring rows.

13. **Paramètres** — Utilisateurs (**admin-only**: per-user permissions + per-user email for Gmail impersonation). **TRM has its own permission catalog + store** on this API — `lib/permission-keys-trm.ts` / `lib/permissions-trm.ts` (`data/permissions-trm.json`) behind `/api/permissions-trm` — deliberately separate from `/api/permissions`: each admin screen saves by replacing the user's whole grant list filtered to its own catalog, so one shared file would let either app strip the other's grants. It now takes an explicit **`PermissionScope`** (`ETM_PERMISSIONS` / `TRM_PERMISSIONS`) with **no default**, the third instance of the `FinanceScope` / `FacturesScope` shape: any guard or factory serving both companies must carry the store, and must never default it. ⚠️ **A key used by a TRM screen but absent from `TRM_PERMISSION_KEYS` fails silently and unrecoverably** — the admin tab renders no toggle (it is built from `GET /permissions-trm/keys`), the PUT drops it as unknown, `/me` never reports it, so the button is invisible to every non-admin with no way to grant it, and it reads as a deliberate restriction. Guard: **`check-permission-keys-trm.ts --web <abs path to TRM apps/web/src>`** — the mirror of `check-screen-access-trm.ts` (there the API manifest follows the web's nav; here the web's `useHasPermission` literals must all exist in the API catalog). Nothing in the type system can catch it: `requirePermission` types its key as the *union* of both catalogs, which stops a typo but not a key belonging to the other app.

**Menu / screen visibility is per user** (`claude_doc/auth_permissions.md` §Screen access). Second axis next to the action catalog, managed in the **Écrans** tab of Paramètres › Utilisateurs: a **menu is a grant, default closed** (`screen_<menu>`), a **screen inside a granted menu is a hide** (`hide_<menu>_<screen>`) — so a newly shipped screen appears for everyone who already has its menu instead of being invisible until an admin ticks it per user. A menu with no visible screen left disappears. Keys derive from the href; the API manifest `apps/api/src/lib/screen-keys.ts` mirrors `navigation.ts` and `check-screen-access.ts` diffs them. ⚠️ Hide keys are **negative** keys: read them via `hasRaw()` (no admin bypass), never `has()`, or the admin sees no menus. Enforcement is the nav surfaces + one route guard in `AppShell` — **a curtain, not a lock**: endpoints are shared across screens, so confidentiality stays with server-enforced action keys (`view_rapport_finance`, `dashboard_ca`…). Grandfathering script: `seed-screen-access.ts --write`, **run on the server** (`data/permissions.json` is gitignored and lives beside the running API), idempotent, and also the way to hand a new menu to everyone.

## HFSQL rules (footguns — always apply)

Full details in `claude_doc/hfsql_odbc.md`. These are the non-negotiable rules for every route that touches HFSQL:

- **No parameterized queries**: `?` placeholders fail. Use string interpolation with `esc()` (single-quote doubling) for strings, `parseInt` for IDs, hex literals `x'${buffer.toString('hex')}'` for blobs.
- **No `RETURNING *`**: use follow-up `SELECT` after INSERT/UPDATE.
- **Booleans are `0`/`1`**: in React always `!!value &&` to avoid rendering `0` as text.
- **Accented identifiers are platform-specific**: Linux bridge rejects them entirely (use `sf.*` + ASCII-truncated column names); Windows silently returns 0 rows on `alias.*` in JOINs (use explicit `alias.terminé AS termine`). Branch on `process.platform === 'win32'` via `IS_WINDOWS`. Canonical pattern in `apps/api/src/routes/stock.ts`. Truncation is **in the driver itself** (even a raw Latin-1 `0xE9` is dropped) — the "Latin-1 bridge" idea is a dead end (`project_hfsql_bridge_accent_fix`). Resolve accent-mangled `SELECT *` keys with a `/^prefix/i` regex (`pickKey`), not hardcoded fallbacks. **Writing accented columns on Linux** (e.g. `asso_fil_matiere`): never name them — positional `INSERT … VALUES(...)` in column order (PK isn't auto-assigned; compute `max+1`), edit/delete via delete-by-ASCII-key + reinsert. Canonical: `references-fil.ts` composition (`project_matiere_premiere_unreachable_pk`). When the table has an **ASCII PK** but accented data columns (`dossier_qualite`), the cheaper shape is a **full-row positional rewrite keyed on the PK**: split writes so ASCII columns take a normal named `UPDATE` and only a change to an accented column triggers read-`queryB64Text` → `DELETE … WHERE <ascii PK>` → positional `INSERT` (same PK, so child FKs survive), with a best-effort restore on failure. Canonical: `dossiers-qualite.ts` `patchAccented()`; round-trip guard `apps/api/src/scripts/test-dq-positional-rewrite.ts`. Reading accented-NAMED columns (`prénom`/`société`): bridge `queryB64Text()` (base64-text → Latin-1); `project_hfsql_accented_column_b64text`.
- **A query naming a non-existent column = prod outage on Linux**: silently caught on Windows ODBC, but on the bridge it triggers a respawn storm that floods the shared HFSQL server (`mps.malterre`=`10.10.20.2`, shared with mfprod) and hangs both apps. Any helper building `WHERE <col>=<id>` from a row property MUST use the target table's real PK. **`WHERE col = NaN` storms identically**: `fixEncoding`/`repairAliased`'s `idField` MUST be selected by the feeding query — `SELECT nom FROM x` + `fixEncoding(…,'IDx',['nom'])` reads `undefined`→`NaN` (helpers now skip non-integer ids as backstop; `project_fixencoding_nan_storm`). Verify prod via `https://mpsng.malterre` (NOT `localhost:8081` — IPv6 false 000s); don't hammer-restart. Naming an accented column in SQL storms the same way — never name `invalidé`/`société`/etc.; `SELECT *` + prune in JS. `isConnectionLostError` now excludes SQL errors so bad columns throw, not storm. Memories: `project_hfsql_bridge_storm`, `feedback_prod_health_check`.
- **Encoding (reads)**: ODBC corrupts accents (é→U+FFFD). Use `fixEncoding()` / `CONVERT(field USING 'UTF-8')` per affected field. **On large lists, batch the repair** — one `CONVERT … WHERE id IN (…)` per source column, not per row (per-row CONVERT is an N+1 that floods the bridge). Batched pattern in `stock-fini.ts repairAliased`.
- **Encoding (writes)**: raw multi-byte UTF-8 in a SQL string corrupts the Linux bridge (→ `[HY090]` / "string without end" / 500). HFSQL text columns are Latin-1 — emit accented values as a hex literal of their Latin-1 bytes (`x'${Buffer.from(v,'latin1').toString('hex')}'`), not `'${esc(v)}'`; ASCII values keep the normal quoted literal. Helper: `sqlText()` in `commandes-sous-traitant.ts`. ⚠️ **The helper is lossy above Latin-1 by design** — em-dash → `-`, curly quotes → `'`/`"`, `…` → `...`, NBSP → space, anything else → `?`. Accents round-trip verbatim, typography does not: a test that asserts a byte-identical round trip on a string containing an em-dash reports a false failure (happened writing `check-retour-client-trm.ts`). Assert on Latin-1-only text, or on the transliterated expectation.
  - ⚠️ **A user-typed search term is a write into a SQL string too — `LIKE '%${esc(q)}%'` with an accented `q` is the same bridge hazard.** A hex literal is not an option inside a `LIKE` pattern, so the answer is to map every non-ASCII character to the single-char wildcard `_` (`likePattern()` in `routes/transferts.ts`): nothing but ASCII reaches the server, and the pattern becomes accent-insensitive in the direction users need — `ecru` and `écru` both match `%_cru%`, which matters because coloris values carry accents inconsistently. It widens the match (`%_cru%` also matches `ancru`), so the **client re-applies the exact, accent-folded test** on the rows that come back; the widening never reaches the user. ⚠️ `stock-ecru.ts`, `stock-fini.ts` and `stock.ts` still interpolate `esc(q)` raw into their list-search `LIKE` — a latent bridge hazard the day someone types an accent into a stock toolbar. Port `likePattern` there when you next touch them.
- **BinMemo `IS NOT NULL`**: unreliable — empty blobs pass. File-serving endpoints return 404 if buffer is empty; UI does HEAD pre-check before rendering iframes.
- **Windows driver + memo-binary columns = 0 rows**: any `SELECT` that names a blob column (`certif_bio`, `certif_recyclé`, `CleComp`…), or `SELECT *` on a table holding one (`stock_fil`, `client`), silently returns **zero rows** on Windows ODBC (`query` *and* `queryRaw`). Probe presence with `LENGTH(col)` there; the Linux bridge takes `SELECT *`. **MEMO text columns cost per row**: over 1.7k `stock_fil` rows the two memos (`commentaire`, `observation_freinte`) are ~0.9 s of a 1.4 s select — select them only for the rows you will return (chunked `IN` lists), never in a full-table list. Canonical: `routes/stock-fil-trm.ts` `fetchBaseRows`.
  - ⚠️ **Not universal — `bonnetier.photo` reads fine on Windows** (`SELECT photo FROM bonnetier WHERE IDbonnetier = <id>` returns the JPEG, measured 2026-08-24), so the 0-rows behaviour is per-table, not a blanket ban. Probe the specific column before assuming either way, and keep the single-row/`WHERE`-scoped shape — the failures above were all wide or full-table selects.
- ⚠️ **When a binary read DOES work, it needs `queryRaw`, never `query`**: `query()` pipes every row through `cleanRow`, which decodes any `ArrayBuffer` as UTF-8 — the JPEG/PDF comes back as a mangled string that looks like data but isn't. Use `queryRaw()` (both platforms export it via `hfsql-auto`), `Buffer.from(...)`, then verify the magic bytes and 404 on anything else (empty memo, bridge text-mangling). Canonical: `prime-trm.ts` `/bonnetiers/:id/photo`. Stored images are full-size originals with EXIF rotation — resize server-side with `sharp` (`.rotate()` first) and cache, rather than shipping 300 KB per avatar.
- **Avoid accents in HFSQL table names and backup folder file names** — both cause "fichier de données est déjà décrit" errors at connection time.
- **JOIN + `CONVERT()` collapses result sets**: `SELECT a.col, CONVERT(b.text USING 'UTF-8') FROM a JOIN b WHERE …` returns **one row** instead of all matches. Split into two flat queries and merge in JS. Same shape kills `CONVERT(tel)` even single-table when `tel` is empty on some rows — read phone-like cols raw. Reference: `commandes-sous-traitant.ts` `/lookups/sous-traitants`.
- ⚠️ **The `.xdd` column order is NOT what a positional INSERT needs — trust the runtime `SELECT *` and nothing else.** The analysis listing and the driver disagree on some tables, and the mismatch fails **silently**: `piece_production` comes back as `IDpiece_production, IDordre_fabrication, bonnetier_debut, bonnetier_controle, bonnetier_fin, date_debut, date_controle, date_fin, observations, poids, visiteur, date_visitage, bonnetier_interruption, date_interruption, numero`, while the `.xdd` puts `numero` third and groups the dates — so a positional INSERT built from the `.xdd` writes the piece number into `bonnetier_debut` and a date into `date_controle`, on live production rows, with no error anywhere. Same trap already recorded for `controle_titrage` and `retour_client`. Two rules follow: **only reach for a positional INSERT when a reserved word or an accent actually forces it** (`piece_production` has neither, so `routes/atelier.ts` inserts it with a named column list), and **probe the runtime order before writing one** — `scripts/probe-atelier-trm.ts` §1 prints it for the three tables the atelier writes.
- **Reserved-word columns return uppercased**: `SELECT lcs.type FROM ligne_commande_sous_traitant lcs` returns the column key as `TYPE`, not `type`; likewise `date` comes back as `DATE` (seen on `prospect`). Always alias (`lcs.type AS type_kind`) or read case-insensitively. Affected anywhere a reserved-word column exists.
- **`commande_sous_traitant`: `commentaire` is RTF, `journal` is plain text**: `commentaire` round-trips via `stripRtf()`/`wrapRtf()` (legacy still reads it); `journal` writes via `sqlText()` (RTF rows migrated to plain text 2026-05-26, reads keep `stripRtf()` defensively). The app surfaces `journal` where legacy wrongly bound the "journal" UI to per-line `lcsst.commentaire`.
- **Empty FK columns store `0`, not `NULL`**: HFSQL keeps integer FK columns at `0` when there's no foreign key (not NULL). Predicates like `WHERE IDligne_expedition IS NULL` silently match zero rows. Use `(col IS NULL OR col = 0)`. Bit the `stock-fini.ts` default filter; same shape on `IDligne_commande_client`, `IDcommande_donation`, `IDProprietaire`, etc.
- ⚠️ **"A roll is shipped" is TWO facts, and un-shipping must undo both.** `stock_fini.IDligne_expedition > 0` (on a shipment slip) *and* `IDetat_stock_fini = 4` ("Expédié"), the latter stamped by the legacy WinDev expedition routine on virtually every shipped roll — **42 944 of the 43 391** rolls sitting on a shipment line in the dev copy. Every "is it still in stock" predicate in the app tests both (`stock-fini.ts` list filter, `commandes-client.ts` available-rolls pool, the `expedie` flag on a line's rolls), so clearing only the expedition line drops a roll into a hole with **no screen at all**: gone from Clients › Gestion › Marchandise (its INNER JOIN needs the expedition line), still hidden from Finis › Stock (état 4), and out of every order's free pool. That was ticket #1086 — three returned pieces « n'apparaissent dans aucun stock ». A return must clear `IDligne_expedition` → 0, demote `IDetat_stock_fini` 4 → 3 ("Validé", where the roll sat before shipping — and *only* when it is 4, so another état is the warehouse's own classification), and release `IDligne_commande_client` → 0, without which the roll can never be offered to another line and nothing in the UI can unlink it. Releasing it makes the original order read as under-delivered again, which is correct: the goods came back. Note the écru side gives no fallback — `stock-ecru.ts` excludes any écru that has a `stock_fini` child. Canonical: `clients.ts` `POST /:id/marchandise/retour-stock`; guard `check-retour-marchandise.ts` (audit + `--repair` for rolls returned before the fix + `--roundtrip`).
- **`IDsociete` partitioning**: shared tables (`client`, `commande_client`, `facture`/`facture_prov` [confirmed], `devis` — verify per table) are partitioned across the 3 companies via `IDsociete` (1=ETM, 2=TRM, 3=Confection). Legacy filters on it — `IDsociete = 0` rows are **invisible** in the legacy app. Every ETM INSERT must set it (= 1 for ETM; TRM-view writes set 2). Memory: `project_societe_multi_company.md`. **`stock_fil` is NOT partitioned** (no `IDsociete`): the yarn sits at TRM and `IDclient` names its owner — ETM's Fils › Stock and TRM's (`routes/stock-fil-trm.ts`) read the same rows, different flavors.
  - **Two shapes for serving a partitioned table — pick by whether the halves are the same object.** Different objects → two route files (`stock_ecru`, see its bullet below). Same object, same lifecycle, same screen → **one router factory mounted twice** (`createFacturesRouter(scope)` in `factures.ts` → `/api/factures` + `/api/factures-trm`), with every société-dependent value in a single `FacturesScope` record. Never fork the file in that case; never add a `?societe=` param in the other. Second instance of the same shape: **`lib/finance-common.ts`** — `createFinanceRouter(scope)`, mounted on `rapportsRouter` at `/` (so ETM's `/api/rapports/finance`, `/ca-clients`, `/ca-evolution`, `/ca-mensuel` keep their URLs) and at **`/api/rapports-trm`** for the sister app's four finance widgets. Its `FinanceScope` also carries **which permission store answers** (`userHasPermission` vs `trmUserHasPermission`), because the two apps' grants live in separate files — copy that when a future factory spans both apps. `editComptesKey: ''` makes a mount read-only by not registering the compte write routes at all, which 404s rather than 403s — the honest answer for a screen that does not exist. (TRM used that until its Rapports › Finance screen landed on 2026-08-25; landing it was two edits to `FINANCE_SCOPE_TRM` and none to the handlers, which is the shape working as intended.) ⚠️ **A factory reached by an `:id` from the URL must check that row's partition in every handler**: `releve_compta` has no `id_societe`, so `/finance/comptes/:id/historique` was cross-readable the moment a second scope mounted it — free while one mount existed, a leak the day it did not. The PATCH had the check; the GET did not. ⚠️ **Typing gotcha for any scope record that holds a permission checker**: `userHasPermission` / `trmUserHasPermission` are typed on their own key *union*, so an arrow-typed `hasPermission: (…, key: string) => …` field rejects both under `strictFunctionTypes`. Declare it as a **method** (`hasPermission(…): Promise<boolean>` — methods are bivariant) and keep the typo protection with `satisfies PermissionKey` / `satisfies TrmPermissionKey` on each scope literal, which checks every key name against the *right* catalog. Casting the function instead silently drops that check.
  - ⚠️ **A per-société router MUST scope-check every id-addressed route.** PKs are ONE sequence shared by all sociétés, so an ETM id is a valid-looking id in TRM's URL space: `GET /api/factures-trm/def/<etm id>` returned ETM's invoice, and a `PUT` would have rewritten it with TRM reference data. Harmless while one router exists, a live cross-ledger hole the moment a second is mounted. Guard with an `inScope(scope, kind, id)` helper on GET/PUT/DELETE/lines/pdf/email/historique and **404** (not 403 — the other ledger's existence isn't ours to disclose). Canonical: `factures.ts`.
  - ⚠️ **`client` has ONE `IDtva` / `IDcode_comptable` column for all three companies**, but `tva` and `code_comptable` are themselves partitioned (live: 627 clients point at ETM rows, 27 at TRM, 4 at Confection). Copying the client's id verbatim onto a document books it against **another** société's TVA/sales account, and XImport posts that straight into accounting. Re-home into the writing société: TVA by matching the **rate** (the rate is the business fact, the row id is just where that rate lives), code comptable by keeping the client's only when it is already ours else the société default. Canonical: `clientBillingDefaults()`.
- ⚠️ **Money: round the unit price to the centime BEFORE multiplying.** `prix` columns are 4-byte REALs and carry full float noise when the price came from the tarif engine (`2.100738048553467`), but every document PRINTS the unit price at 2 decimals and the client checks qty × printed price = printed line = printed total. Legacy WinDev rounds price → multiplies → rounds the line; so must we, on every surface (list, detail, PDF, accounting export) via one shared helper. Measured against the 14 legible legacy TRM invoices: this reproduces 13 (14th off by 1 centime on a half-cent tie), while summing raw `quantite * prix` reproduced only 4 and was wrong by up to €6.71 on a single invoice. Canonical: `lineMontant()` / `round2()` in `factures.ts`.
- **Per-table polymorphism / FK quirks** (`ged` multi-parent, `asso_colorisfil_frs`, lcsst `IDreference` × 3 catalogs, fini `IDColoris` by `ref_fini.avec_teinture` [`0`=wash `colori_ecru` / `1`,`2`=dye `ref_fini_colori`; memory `project_avec_teinture_coloris_rule.md`], `defaut_qualite` `Type_Reference`, `envoi_email.IDreference` by `IDtype_doc`): see `claude_doc/hfsql_odbc.md`.
- ⚠️ **`ligne_commande_sous_traitant.sstatut`: never compare it to `'Terminé'` — neither in SQL nor in JS.** ODBC returns the value as `Termin�`, so `isLineDone()` (which compares to the literal) is **false for genuinely finished lines** unless the feeding query ran `fixEncoding`. And naming the accented literal in SQL pushes raw UTF-8 through the Linux bridge. Match the **ASCII prefix** instead: `(sstatut IS NULL OR sstatut NOT LIKE 'Termin%')` — canonical in `commandes-client.ts` `SUPPLY_NOT_DONE`, which also derives its French labels by ASCII prefix so accented statuts don't render as mojibake. ✅ **Fixed 2026-08-25**: `isLineDone()` now matches the **ASCII prefix** (`startsWith('Termin')`) instead of `=== 'Terminé'`, so it is correct whether or not the feeding query ran `fixEncoding`. Safe because exactly one of the 12 live values starts with "Termin" (measured: 4 619 of 7 257 rows). Before the fix a raw `SELECT sstatut` recognised **0** finished lines; `commandes-sous-traitant.ts:860` therefore computed each order's "earliest open deadline" from lines that were already done — 4 228 of 7 247 orders were affected and the red "en retard" liseré (§30) fired on 6 651 orders instead of 2 423. (`:264` turned out to be dead code: auto-close was retired for the manual Clôturer button.) Unit test: `lib/sst-shared.test.ts` pins the 12 live values. Also: **filter sst lines by "not done", never by an allowlist of open statuts** — there are 12 legacy values and a fresh order starts `Non_Envoye`, so an allowlist silently hides live orders (that bug hid 5 of them from the Clients › Commandes supply tables).
- ⚠️ **`defaut_qualite.reference` is NOT disambiguated by `Type_Reference`.** Under `Type_Reference = 2` the `reference` holds a bare id that resolves in **both** `stock_ecru` and `stock_fini` — measured on a 900-ref sample: 881 are valid écru ids **and** 810 are valid fini ids (a real case: ref `'49103'` is the fini roll of piece 3367/7). Existing readers (`fetchDefectsByEcru`, `commandes-sous-traitant.ts`) assume écru, which is safe **only because they filter by a list of écru ids they already hold** — never query `defaut_qualite` by `Type_Reference` alone and never join it to a fini roll, or you'll attribute another roll's defect. Fini-roll defects live on the roll itself (`stock_fini.observation_sst` + `second_choix`), which is what the Finis screens read. A defect is *either* measured *or* counted — `taille_cm > 0` (→ "Maille 25 cm") xor `nombre > 0` (→ "Trou x1"); `defautSummary` renders only the size, so a document that must show counts (the TRM avis) formats the pair itself.
- **Ennoblisseur lines (sst, `type=2`)**: `quantite=Ml`, `prix=€/Kg` — never multiply directly; € total = `Σ(stock_ecru.poids) × prix`. `prix` auto via `pricing-sst.ts` (ports legacy `CalculTarifSST` with MATEL/ESAT multipliers). Manual entry for out-of-catalog ssts (`auto_pricing_enabled` gates). Algo: memory `project_pricing_calcultarifsst.md`.
- **Tricoteur lines (sst, `type=1`)**: `quantite=kg` (output écru), `prix=€/Kg`, € total = `qty × prix`. `prix` auto via `pricing-trm.ts trmLinePrix = max(PrixDeRevientTRM(IDref_ecru, qty) / 0.7, ref_ecru.prix)`. Gate on `line.type=1` (ALL tricoteurs). Yarn affectations: `asso_fil_lignecmdsst`. Algo: memory `project_pricing_prixderevient_trm.md`.
- **ETM↔TRM cross-ledger bridge** (TRM = Tricotage Malterre, IDsous_traitant=1): auto-mirrors tricoteur sst as TRM `commande_client` (`IDcommande_ETM` back-pointer). Gate via `isTricotageMalterreSst(sstId)` — external tricoteurs (37/10/66) get NO mirror. TRM-side rolls surface via `stock_ecru.IDref_commande_source`. Detail: memory `project_etm_trm_bridge.md`.
- ⚠️ **The mirror is one-way: a TRM `commande_client` with `IDcommande_ETM > 0` is READ-ONLY from the TRM side.** ETM owns its header and lines and syncs them down; there is no reverse sync, so a TRM-side write silently diverges from the sst that owns it. 93 % of the TRM ledger is mirrors, so this is the common case, not the edge case — every write path in `commandes-trm.ts` gates on `refuseIfMirror` (409 `commande_miroir_etm`) and only native orders (`IDcommande_ETM = 0`) are editable. Same rule in the UI: no Modifier, no line editing, no clôture.
- **`commande_client` has TWO route families like `stock_ecru` — same "don't unify" rule.** `commandes-client.ts` (`/api/commandes-client`, `IDsociete = 1 AND IDcommande_ETM = 0`) serves ETM; `commandes-trm.ts` (`/api/commandes-trm`, `IDsociete = 2`) serves TRM's screen. They aren't a `?societe=` param apart: ETM reserves existing rolls to a line, TRM *knits* the line (`ordre_fabrication.IDligne_commande_client` → pieces on `stock_ecru.IDLigne_Commande_TRM` → `ligne_expedition` → `IDligne_expedition_TRM`). Each router keeps its own `/lookups/modes-paiement`+`/echeances` copies — that duplication is the existing convention (`commandes-client.ts` does it too), not drift.
- ⚠️ **`pricing-trm.ts` carries TWO retained-price rules, and `ref_ecru.prix` means something different in each.** `prixDeRevientTRMDetail(ref, qty, baseRole)` takes a `TrmBaseRole`: **`'price-floor'` (the default)** = `max(cost / 0.7, base)` — the base is a floor on the *sale* price and is retained **flat** when it wins; **`'cost-floor'`** = `max(cost, base) / 0.7` — the base is a floor on the *cost*, so the winning assiette carries the 30 %. `trmLinePrix` stays on the default because it prices the **ETM → TRM sous-traitance lines**, which must keep matching the WinDev app that still writes them (verified 15/15 on recent mirrors — ref 4 @500 kg is stored at 2,07 €, the bare base). Only `/commandes-trm/lookups/line-price` passes `'cost-floor'` (user decision, 2026-08-26). **Do not unify them**: the two differ by ~+39 % in value, so flipping the default silently reprices the intercompany transfer. Pinned by `pricing-trm.test.ts`.
- **`prixDeRevientTRM` is the *cost*, not a price** — use it for the margin display (the legacy line card's "37 %" chip is `(prix − cost) / prix`), never as a line's `prix`.
- ⚠️ **The legacy TRM client-order window computes no price at all.** `FEN_Gestion_d_une_référence_de_commande_client`'s `COMBO_Reference` selection event reads `ref_ecru.prix` and stops there (recovered from WinDev's compile cache, `MPS.cpl/<user>/00000000/<Window>.<hash>.wdw.wcw` — string literals + identifiers survive there even when the `.wdw` is PCS-compressed). So the legacy proposes a visibly lower number than our screen; that gap is expected, not a regression. Historical native lines are negotiated anyway: of 491 priced type-1 lines, 315 sit *below* the catalog price and 158 above.
- **`stock_ecru` has TWO route families, one per company — don't "unify" them.** `stock-ecru.ts` (`/api/stock/ecru`) hardcodes `se.IDsociete = 1` and serves ETM's screen; `stock-ecru-trm.ts` (`/api/stock/ecru-trm`) serves TRM's, scoped `IDsociete = 2`. They are not a `?societe=` param apart: an ETM écru is bought from a tricoteur, sits in an `IDmagasin`, and is affected to a dyer (`IDref_commande_affectation`) before becoming a `stock_fini`; a TRM écru is knitted in-house (`IDordre_fabrication` → `ordre_fabrication.IDmachine` → the métier, `IDpiece_production` for visitage timings), has `IDmagasin = 0` / empty `lot` / `metrage = 0`, and has no teinture step at all. **"Still in stock" differs too**: ETM = `IDligne_expedition_ETM = 0` + no `stock_fini` child; TRM = `IDligne_expedition_TRM = 0`. ⚠️ **The client reservation hangs off a different column per company**: ETM rows use `IDligne_commande_client`, TRM rows use **`IDLigne_Commande_TRM`** (the mirror-ledger back-pointer) and leave `IDligne_commande_client` at 0 — reading the ETM column on a TRM row silently yields "no client" on every row. The genuinely shared parts (`fetchDefectsByEcru`, `defautSummary`, `resolveClientReservations`) are **exported** from `stock-ecru.ts` and imported, not duplicated.
- **`expedition` splits the same way — `expeditions.ts` (société 1) vs `expeditions-trm.ts` (société 2, `/api/expeditions-trm`).** Same tables (`expedition` / `ligne_expedition`), different merchandise: an ETM avis carries finished rolls (`stock_fini.IDligne_expedition`) or bought écru (`stock_ecru.IDligne_expedition_ETM`) and the line's `TYPE` decides which; a TRM avis only ever carries tombé de métier via **`stock_ecru.IDligne_expedition_TRM`**, whose free-stock pool hangs off `IDLigne_Commande_TRM` (see the bullet above). `expedition_divers` has **no `IDsociete` column** — misc shipments are ETM-only, never filter or insert it. Shared helpers (`resolveClientNames`, `loadAdresse`, `attachedFactures`, `newIdAfterInsert`, `logEnvoiEmails`, …) are **exported** from `expeditions.ts`.
- ⚠️ **Shipping to ETS Malterre CHANGES a TRM piece's owner.** When TRM delivers, ETM's reception takes ownership: the legacy flow flips `stock_ecru.IDsociete` from 2 to 1 and stamps `lot = 'trm<IDexpedition>'`, keeping `IDligne_expedition_TRM` as the provenance link. So the pieces of a delivered TRM avis are **société-1 rows**. Any query listing "what was shipped" must therefore **not** filter on `IDsociete` (filtering makes every delivered avis read "0 pièces"), while any write must **require `IDsociete = 2`** — reassigning or releasing a piece ETM now owns would orphan their reception. `expeditions-trm.ts` enforces both and 409s on the write path. Shipments to a third-party client keep their pieces at `IDsociete = 2`.
- ⚠️ **Counting TRM production means `IDordre_fabrication > 0`, NOT `IDsociete = 2`.** Direct consequence of the handover above: most of a semester's pieces have already flipped to société 1, so scoping production sums by société silently drops them (measured: 46 833 kg of 50 091 would vanish from a semester). `prime-trm.ts` (`/api/prime-trm`, the TRM production prime) therefore sums `stock_ecru.poids` over `date_saisie` with **no `IDsociete` filter**, and identifies TRM-knitted pieces by their production order — which also excludes ETM's manual `lot='fictif'` rows that the legacy prime screen wrongly counted. Applies to any future TRM production/TRS/rapport query, not just the prime.
- ⚠️ **Les taux de la prime TRM sont datés** — `lib/bareme-prime-trm.ts`, `BAREMES_PRIME` (+0,05 / −0,20 €/Kg jusqu'à S1 2026, **+0,055 / −0,40 à partir de S2 2026**). C'étaient trois constantes de module appliquées à *toute* période navigable : les éditer recalculait l'historique et l'écran affichait des primes jamais versées. Une révision s'ajoute en **ligne datée** dont le `from` tombe sur une frontière de semestre (15/06 ou 15/12) — la prime est *une* somme sur la période × *un* taux — et **on ne touche jamais une ligne passée**. Même remède pour tout autre barème rétroactif (le seuil du rouloir de Maintenance, p. ex.). Garde : `bareme-prime-trm.test.ts`.
- **Prime rates are module constants (`TAUX_PREMIER_CHOIX` +0,05 / `TAUX_SECOND_CHOIX` −0,20 €/kg).** They apply to *every* period the screen can browse, so editing them recomputes the whole history and the app would display primes that were never paid. A barème revision must introduce **date-effective rates** (rate applicable per semester) before the new values land.
- **The prime répartition includes the régleurs.** The legacy screen filtered `regleur = 0`, which silently dropped the only two (Nicolas Antonino id 16, Mickaël Grivelet id 15 — both still employed) from every split. They share the **same pot** on a bonnetier's per-day weight, so the semester total is untouched and every other share shrinks. Applies to all browsable periods, so historical splits no longer match what was paid at the time (user decision, 2026-08-25). `buildRepartition` in `prime-trm.ts` therefore has no regleur predicate — do not « restore » one from the legacy spec.
- ⚠️ **`defaut_qualite.taille_cm` is NOT centimetres** — the visitage writes 25 for « Moins de 50 cm » but 1500 for « 1m - 3m » and 200 for « Autre Barrure 1m - 3m »: the units are per-vocabulary and unrecoverable. Never render, sum or compare it as a length. The size qualifier that IS reliable lives in `description`, prefixed by `type_defaut` (« Maille Moins de 50 cm ») — strip the prefix. Count-shaped defects (Trou, Démaillage) leave `taille_cm` at 0 and use `nombre` instead.

- **`ordre_fabrication` & friends are TRM-only and have NO `IDsociete` — two route families reach them, over one shared lib** — `of-trm.ts` (`/api/of-trm`, Gestion des OF) and `visitage-trm.ts` (`/api/visitage-trm`, the visitage poste, the **only writer** of TRM `stock_ecru`), both over **`lib/production-trm.ts`** (machines, bonnetiers, défauts, `loadOf`, date helpers, `TYPES_DEFAUT`). Improve the lib; never re-port a helper into a third file. **Both routers gate their writes with a TRM permission key** — `edit_of` on of-trm's nine write routes, `saisie_visitage` on visitage's `/valider`; reads stay open. ⚠️ There is **no global auth middleware** (`attachUser()` is best-effort), so a TRM write route without its own guard is reachable **anonymously** — which is exactly what of-trm was until 2026-08-26. Scope guard goes through the commande chain (`IDligne_commande_client` → `commande_client.IDsociete = 2` → else 404). Queue semantics recovered from live data: `priorite` ranks OFs **within one `IDmachine`** (1 = the running OF, 0 once terminé), at most one `est_actif` per métier, and **`POST /:id/terminer` owns the auto-activation flip** (re-rank, then activate the new head if `auto_activation = 1`). Never name the four accented `productivité*` columns (dead, all 0 — recompute instead). ⚠️ **Never SELECT `ordre_fabrication.interruption_prod` (by name or via `SELECT *`)** — it is the **only HFSQL *Durée* column in the whole MPS analysis** (xdd type 35): ODBC types it numeric but returns the text `0000000000`, so the Linux bridge emits it unquoted → invalid JSON → every OF list/detail 500s in prod while Windows dev passes (shipped that way 2026-08-24, caught at deploy). `message_of` / `evenement_piece` / `evenement_machine` / `defaut_qualite` carry the reserved `date` column: write it uppercase `DATE` in SELECT *and* WHERE/ORDER BY, and `message_of` INSERTs are positional (desiderata shape). Réalisé = `Σ stock_ecru.poids` per OF — never IDsociete-filtered (handover rule above). Per-piece % and the 120 s faux-arrêts filter are **flagged approximations** (legacy formulas are PCS-compressed); the write cycle is guarded by `scripts/check-of-trm.ts`.

- **`machine` & `operation_maintenance` are TRM-only and have NO `IDsociete` — `maintenance-trm.ts` (`/api/maintenance-trm`) is their one route family** (Atelier › Maintenance in the TRM app; the knitting machines *are* Tricotage Malterre, same reasoning as `ordre_fabrication`). Three accented columns — **`connecté` / `archivé` / `diamètre`** — so reads are `SELECT *` + key folding (`queryB64Text` on Linux) and `archivé = 0` filters in JS. ✅ **`SELECT *` on `machine` is safe on Windows too** (no memo-binary column) — a confirmed counterexample to the 0-rows quirk above, and the reason this table needs no `LENGTH()` probing. Writes are the *easy* half: every maintenance column is ASCII, so a **plain named `UPDATE` is legal** — no positional reinsert. ⚠️ **But the `SET` must name only the maintenance columns**: `nom`, `Jauge`, `diamètre`, `nb_chutes*`, `vitesse`, `elasthanne`, `adresse_automate`, `connecté`, `archivé` belong to `FEN_Gestion_des_machines` (not ported), and unnamed keeps the stored value while named would zero it. Two schema typos are the **real** column names: **`observation_maintenace`** and **`comm_pulsonque`**. And the screen's "Description" field is **`machine.commentaire`**, not `machine.nom` (métier 2E: `nom`='2E', `commentaire`='Terrot') — do not "fix" it toward `nom`. Rouloir counter = `Σ ordre_fabrication.quantite` of finished OFs created after `machine.date_maintenance`, against a **15 000 Kg** module constant that applies to all history (Prime-barème class of caveat).
- **A DATETIME's TEXT SHAPE differs per driver — never do positional string surgery on one.** Windows ODBC renders `piece_production.date_fin` as `'2025-11-24 19:58:40.412'`, the Linux bridge as the compact `'20251124195840'`. So any legacy `SUBSTR(<date>, 9, 2)` — WinDev's own DATETIME is the compact `AAAAMMJJHHMMSS`, where positions 9-10 really are the hour — reads the **day of the month** on Windows, silently and with no error. Always `parseDtMs()` (lib/production-trm.ts, handles both shapes) and compute on the parsed value. Measured 0/8 on Windows by `scripts/probe-pieces-a-visiter-trm.ts` §5; the widget it belongs to derives its « équipe » from the parsed hour for exactly this reason.
- **Recovering a PCS-compressed WinDev window: try the compile cache FIRST, not the Android build.** `C:\Mes Projets\MPS\MPS.cpl\<user>\00000000\<Window>.<hash>.wdw.{wcw,wbw}` — `.wcw` yields string literals, identifiers and **embedded SQL**; `.wbw` yields the **full field inventory** (every `SAI_*`/`LIB_*`/`JAUGE_*` and the window's procedures), which is effectively the form's spec. The Android `GWDF*.java` route that recovered `FI_Prime` is **not universal** — `FI_Maintenance` has no Android twin at all. ⚠️ **Integer literals and function names do NOT survive either route**, so every threshold has to be *measured*: solve it from live data against a screenshot of the legacy window, and pin the reconciliation in a probe script with the observed values hard-coded so the test can't go circular (`scripts/probe-maintenance-trm.ts` — 14/14 métiers, worst delta 0 Kg, is what proved the 15 000 Kg above). **Cheaper first move: ASK THE USER.** They have the WinDev project open and can paste the event's WLanguage verbatim — that is how the « Pièces à visiter » colour ladder (3 h / 2 h) was recovered in one turn, after the cache had yielded the SQL but stripped both thresholds. Measure only when asking is not an option; do not spend a session inferring a number someone can read off a screen.

## React / frontend rules

- **Hooks before early returns**: all `use*` hooks must come before any conditional `return` — violating this crashes production builds (minified React error #310).
- **`useElementSize` returns a CALLBACK ref, deliberately.** A `useRef` + `useEffect([])` pair never attaches its ResizeObserver when the target is rendered *conditionally* (`{data && <div ref={…}>}`): the ref is null on the mount the effect runs on, the size stays `{0,0}` forever, and a chart guarding on `w > 0 && h > 0` then silently never paints. Don't "simplify" it back to a RefObject.
- **A guard must never decide while its permission fetch is in flight.** `/auth/me` and `/permissions/me` are two round trips: a redirect computed on the intermediate state sends *everyone* away on a cold load, and it only looks fine when you reach the page by clicking (permissions already cached). Render nothing / a spinner until `usePermissions().isLoading` is false, then decide. Bit both the `AppShell` screen guard and `SettingsUtilisateurs`' admin guard (the latter silently broke every bookmark and refresh of `/settings/utilisateurs`).
- **Shared `apiFetch`**: all fetch calls go through `apps/web/src/lib/api.ts` (sets `credentials: 'include'` for cookie auth). **Never duplicate per page** — the cookie won't be sent without `credentials: 'include'`.
- ⚠️ **A screen that MOVES stock must invalidate the stock caches, and none of them is a stock screen.** The global `staleTime` is 5 minutes (`main.tsx`), so a stock screen keeps serving its pre-change list long after the write landed — which reads as "the operation didn't work", then as "it fixed itself" once the cache expires. That was **ticket #1089**: three pieces transferred MATEL → Ets Malterre still showed the old magasin on Finis › Stock. Two halves, both required:
  - **Writers call `invalidateStockCaches(queryClient)`** (`lib/cache-sync.ts`, beside `invalidateLotQualityCaches`). Wired into Transferts (add/remove piece, delete bon — `est_valide` does **not** gate the movement, stock moves the moment a piece joins the bon), Clients › Expéditions (roll ↔ shipment line, avis delete, divers items), Clients › Commandes (roll reservation), Clients › Gestion › Marchandise (retour stock), Sous-traitants › Commandes (réception **creates** `stock_ecru`/`stock_fini` rows, écru affectation, fil affectation). Call it unconditionally and for every family — `invalidateQueries` only refetches queries with a mounted observer, so naming one no screen is showing costs nothing, and one bon carries écru **and** fini.
  - **The four stock screens spread `STOCK_QUERY_FRESHNESS`** (`staleTime: 0` + `refetchOnMount: 'always'`) into their list and detail queries — not their lookups. This is the half invalidation *cannot* cover: **the legacy WinDev app writes these tables live** and so do other users' sessions, and nothing in this browser can invalidate that. Costs one query per arrival (measured: fini 1.1 s/1 MB, écru 2.2 s, fil 1.3 s, divers 0.2 s) but never blanks the screen — all four render on `isLoading`, never `isFetching`, so the cached table paints instantly and corrects itself behind it. Don't "optimise" that back to a non-zero staleTime.
  - Guard: `apps/web/src/lib/cache-sync.test.ts` diffs `STOCK_QUERY_ROOTS` against every `['stock-…']` key in the app (a new stock family can't escape the helper), and pins the remount behaviour against a real `QueryClient` carrying the 5-minute default — asserting both that the default replays the stale list and that the freshness options re-read.
- **SW denylist for `/api/`**: the PWA SW has `navigateFallbackDenylist` for `/api/`. Never remove — without it, the SW intercepts `/api/` navigations and serves `index.html`, breaking React Router.
- **Modifier button = `variant="gold"`**: the view-mode "Modifier" CTA on every detail screen MUST use `<Button variant="gold">`. Never `outline` or `default`. Canonical "enter edit mode" affordance.
- **Stale `.js` build artifacts**: `apps/web/src/**/*.js` is gitignored; web `build` is `tsc --noEmit && vite build` — **never revert to `tsc -b`** (composite tsconfig emits `.js`/`.d.ts` into `src/`). Vite resolves `.js` before `.tsx`, so stray emitted `.js` shadow source and serve stale code (symptom: white screen / edits not showing). Fix: delete the `.js`/`.d.ts` AND restart Vite (clearing `node_modules/.vite` isn't enough — old module graph lives in memory until restart).
- **"The page loads forever" in dev is almost never your code — it's a wedged HFSQL connection.** The API stays *listening* (`/api/health` → 200, instant) while every data route 500s after **exactly 15 s**. Run `node scripts/worktree/status.mjs` FIRST: it probes `/api/health?db=1` per slot and reports `DEGRADED` + the remedy. Cause: a burst of `apps/api/src` edits, each restarting `tsx watch` and leaving its ODBC connection dangling — so it strikes right after you finish editing, just as you ask the user to look. **Batch API edits and restart the slot yourself before handing back**: `node scripts/worktree/up.mjs <feature> --restart`. Post-mortem lives in `.dev-logs/api.err.prev.log` (the restart rotates the logs instead of truncating them). Detail: `claude_doc/worktrees.md` § "The browser loads forever".
- **A `503` on `/api/*` in dev means the worktree's API is down, not that your code is wrong.** Vite proxies `/api` to `localhost:808N` and answers `503` — on the `OPTIONS` preflight too — when that target is unreachable, so a brand-new call looks like it "doesn't work" while the request is in fact perfect. Check `node scripts/worktree/status.mjs` (or `netstat`) *before* debugging the caller; fix with `node scripts/worktree/up.mjs <feature> --restart`.
  - ⚠️ **The same stale-module failure happens with NO stray `.js` at all**, after a burst of rapid edits to one file: the browser gets a transform where a newly-added import is missing, and the component dies at runtime with `ReferenceError: <Import> is not defined` even though the import is right there in source and `tsc` is clean. Don't hunt for a phantom shadowing file — if source, the named export, and typecheck all agree, it IS the dev server. Restart it (`node scripts/worktree/up.mjs <feature> --restart`). Symptom to recognise: a component that renders fine until the code path using the new import is reached, then unmounts the whole route.

## Design system rule

**Before building or modifying any user-facing screen, component, button, tab, card, dialog, or interaction pattern, you MUST invoke the `mps_designer` skill (`Skill(skill: "mps_designer")`).** Not optional. It encodes every UI/UX convention — colors, layouts, detail-header button trios, placeholder dialogs, drawers, deadline indicators, status footers, etc.

**Invoke the skill when**: building a new screen; adding a button/tab/card/dialog to an existing screen; touching anything the user describes in visual terms ("add a print button", "make it red", "slide a drawer in"); deciding a color/icon/size/spacing/shape.

**Before inventing a pattern, grep the gold-standard reference screens**: `Entreprises.tsx`, `FilsGestion.tsx`, `FilsStock.tsx`, `FilsCommandes.tsx`, `EtudesColoris.tsx`. Existing screens almost always have the pattern — use the exact same icon, strings, and dialog structure. See `claude_doc/implemented_screens.md` for what each reference covers.

**Core visual language**: panel backgrounds `bg-zinc-100/80` (list/sidebar) / `bg-zinc-200/50` (header/footer) / `bg-white` (cards), `scrollbar-transparent` on scrollable panels. **Never hardcode hex values** — use Tailwind CSS variable classes (`text-accent`, `bg-primary`, `border-gold/30`). Colors in §Branding above.

**Typography**: OS system stack via `system-ui` (`font-sans` = `font-heading`). **No web fonts** — no `@import`/`<link>`/`@font-face`. Heading: `<h1 className="text-3xl font-heading font-bold tracking-tight">`. Header gradient: `bg-gradient-to-r from-gold/40 via-gold/15 to-transparent`. **Do not re-add Google Fonts `@import`** (earlier Anton/Lato attempts silently broke). See `mps_designer §2`.

**Edit mode pattern** (follow `Entreprises.tsx`): `isEditing` toggle, gold "Mode edition" badge, `border-l-4 border-l-accent/70 bg-accent/[0.03]` on editable cards, hover-reveal actions (`opacity-0 group-hover:opacity-100`), `LabeledInput` + `InlineForm` components.

**Layout**: 3-panel `MasterDetailLayout` for master-detail screens (left `w-72`, right `w-96`, responsive full/compact/stacked). Table-centric screens do NOT use `MasterDetailLayout` — see `FilsStock.tsx`.

**Status management**: user-controlled primary state goes to the **sidebar footer pill** (not a header badge), regardless of how many values it can take. Binary → split toggle button (`FilsCommandes`); 3+ values → menu button + popover (`EtudesColoris`). See `mps_designer §29`.

**"+ Nouveau" button**: bottom of every master-detail left list, **view mode only** (`{!isEditing && ...}`). Either inline-creates a placeholder row or opens a small initial-data modal (pick per whether the row needs data up front). After save: `setSelectedId(newId)` + auto-enter edit. `FilsStock` exempt (table layout). Full rules: `mps_designer §5`.

**Sidebar logo**: `public/logo-full.png` (expanded, `h-10 mx-auto`) / `public/logo-small.png` (collapsed, `h-8 mx-auto`).
