# Tableau de bord — widgets (reference)

> Moved verbatim from `CLAUDE.md` on 2026-09-07 to keep the root file small. Every fact, date and measurement here is authoritative; `CLAUDE.md` § Navigation keeps only a one-line pointer per widget. Add new widget notes HERE, not in `CLAUDE.md`.

## Tableau de bord (`/`) — layout, tabs, CA, Analyse financière

**Tableau de bord** (`/`) — widgets per-user permission-gated (`dashboard_*` keys); toggled in Paramètres › Utilisateurs. **Several dashboards per user**: they are the submenu tabs of "Tableau de bord" and come from the user's profile, not from `navigation.ts` — "Principal" always exists and is routed at `/`, the ones the user creates live at `/tableau-de-bord/<id>` (`Header.tsx` reads them via `useDashboardTabs`, sharing the layout query's cache). Create / rename / delete sit in the edit-mode "Tableaux" menu; the primary can be renamed but never deleted, and creating one carries the in-progress draft into the same write. Each dashboard holds its own layout, and the merge rule differs by tab: a widget the layout doesn't mention is appended **visible on the primary** (a stale layout must never hide a newly granted widget) and **hidden on the others** (a new widget must not gate-crash a curated dashboard) — so a new dashboard starts empty, every widget in the tray. Storage is `dashboards: [{id, name, layout}]` in `data/user-profiles.json`; profiles written before tabs carry a bare `dashboard` array, migrated read-time into the primary tab and rewritten on the first save. **The endpoint is scoped per app** (`?app=etm|trm`, default `etm`): the sister TRM app renders this very screen (`@etm/pages/Dashboard`) with its own registry, so a user's TRM arrangements live in a separate `dashboards_trm` field — the two catalogs share no key. That sharing is why `useDashboardLayout.ts` imports the registry and types through `@/components/dashboard/…` (in TRM that resolves to TRM's registry, `DASHBOARD_APP = 'trm'`) and why `WidgetDef` is defined in `types.ts`, not `registry.tsx`; keep both that way. **Permission decides availability, the user's layout decides display**: "Personnaliser" enters an edit mode with **direct manipulation only — no per-widget control panel**. The desktop grid is **`react-grid-layout` v2** (`GridLayout` + `verticalCompactor`): every widget has a real **(x, y) position** plus size (`width` 1-12 cols, `heightPx`), the whole card is the drag handle (`dragConfig.cancel: '.widget-no-drag'` exempts the hide-eye), edges/corner resize (`resizeConfig.handles: ['e','s','se']`, gold bars styled in `index.css` under `.dashboard-grid`), and dragging shows the library's live placeholder while vertical gravity compacts everything upward — which is what lets a widget sit in the right column under a short neighbour while a tall one fills the left (the earlier order-based flow model could NOT express that; don't regress to it). Hide via the hover-revealed eye; re-show by clicking the tray chip. Below `lg` the grid is bypassed: plain single-column stack ordered by (y, x) with **definite** pixel heights (with `auto` a scrolling widget body never engages and the card grows to its full content). Persistence: `x`/`y` stored per widget (optional in the API schema — pre-positional layouts are shelf-packed at load); saved layouts are normalised through the same vertical compaction so loading isn't already "dirty". **Vite gotcha**: react-draggable inside RGL reads `process.env.DRAGGABLE_DEBUG` — `vite.config.ts` defines it, else the browser throws "process is not defined" on first drag. The trigger and the edit-mode buttons live in the **app header** via the screen-actions slot (`contexts/HeaderActionsContext.tsx`, `mps_designer §3`) — zero vertical cost, and the header is sticky so Enregistrer survives scrolling; right-click on the dashboard background is a secondary accelerator (gated to the background so widget text stays copyable). Saved per user in `data/user-profiles.json` (`GET`/`PUT /api/user-profiles/me/dashboard`); a layout equal to the defaults is stored as `null` so the user keeps tracking future default changes. Adding a widget = **one entry** in `apps/web/src/components/dashboard/registry.tsx` — a widget the saved layout doesn't mention is appended visible, so a stale layout can never hide a newly granted one. Widgets render `<WidgetFrame>` (shared gold header + edit strip) and read `useWidgetChrome()` for their height preset. **Chiffre d'affaires** (`dashboard_ca`, gated on the API too — confidential): ports legacy *Comparatif CA* + *Rapport CA/Client*. Formula reverse-engineered from the data (WinDev sources are PCS-compressed): `CA = Σ round2(ligne_facture.quantite × prix)` over `facture` with `IDsociete = 1`, **`facture.TYPE = 2` (avoir) negated**, accumulated in integer centimes. Route `apps/api/src/routes/rapports.ts` (`/ca-clients`, `/ca-mensuel`); regression check `apps/api/src/scripts/check-ca-legacy-parity.ts`. The widget adds two controls the legacy screen had no equivalent for: a **comparison period** (`period=full|ytd` — `ytd` cuts BOTH years at today's MM-DD so a partial year isn't compared against a full one, and is the **default since 2026-08-26** at the user's request; « Année complète » stays one click away and is the right read on a closed exercise, where the two coincide anyway) and a **view** picker over the client table (classement CA / progressions / baisses / nouveaux / perdus). Progressions and baisses rank on movement in the **ranking**, each dropping the category that has its own view (nouveaux have no rank to climb, perdus left the ranking). **Analyse financière** (`dashboard_finance`, own permission, gated on the API): ports legacy *Analyse Financière*. Cumulative curves (CA, marge brute, charges fixes, charges variables) + the figures of the last upload. ⚠️ **Tout est borné au périmètre de l'EXPLOITATION** — charges = PCG classes **60 à 64**, produits = classes **70 à 74** (`isChargeExploitation` / `isProduitExploitation` dans `finance-common.ts`) : l'EBE se calcule avant le financier, l'exceptionnel et les dotations, donc découper le plan sur « classe 6 = charge / classe 7 = produit » est trop large et fait entrer dans le calcul des postes qui n'y ont rien à faire. Corrigé 2026-08-26 en confrontant le widget au bilan : l'EBE 2025 était gonflé de **6 100 €** (escomptes obtenus 8 011 €, escomptes accordés 1 562 €, dons 350 €) et celui de 2024 de **40 040 €** (compte 768000, 33 896 € de produits financiers). Le périmètre s'applique **aux deux surfaces**, série ET balance de Rapports › Finance, pour que l'invariant « le widget suit l'écran » tienne : les comptes hors exploitation ont donc aussi quitté le tableau du rapport (ETM 665000 / 670000 / 671200 / 671300, TRM 661000 / 670000 / 671200 — 1 914 € et 146 € sur 2025). Le CA n'est plus `upload_compta.produits` (qui somme toute la classe 7) mais un recalcul sur `releve_compta`, ce dernier ne servant plus que de repli quand aucune balance n'est déposée à la date de l'arrêté ; vérifié que le recalcul, borne relâchée, reproduit `upload_compta.produits` au centime sur les 57 arrêtés ETM et les 58 de TRM. Le **fixe/variable split est recomputed** from `releve_compta` bucketed by `compte_compta.frais_variable` — the same arithmetic as the Rapports › Finance screen — and NOT read from `upload_compta.frais_fixe`/`.frais_variable`. ⚠️ Those two columns are a snapshot the accountant's WinDev routine **freezes at write time**, so they encode the classification in force that week: reclassifying a compte restated the report instantly and never reached the chart, while the next upload adopted the new split and stepped the curve mid-year (measured on the dev copy: 7 of ETM's 57 uploads and 30 of TRM's 58 carry a stale split, up to 531 k€). `marge brute = produits − charges variables`, `EBE = marge brute − charges fixes` (provisions stay out); EBE is untouched by a reclassification, since total charges are. Guard: `check-finance-analyse-buckets.ts`, which pins the widget's charges to the report's own `lignes` totals on every société × year, **plus le périmètre** (aucune ligne hors 60-64 dans le rapport, CA de l'analyse strictement égal aux comptes 70-74 de la balance). Uploads are cumulative YTD, so a month's point is the **last upload of that month**, never a sum; the year's first upload is dropped when it's the accountant's close of the previous exercise (early January, dwarfs the next one).

⚠️ **Le point de fin d'année reste un solde d'AVANT CLÔTURE, et ce n'est pas rattrapable.** Le dernier arrêté d'un exercice est celui de fin décembre (22/12/2025 pour 2025) ; les écritures de clôture de l'expert-comptable — cut-off, régularisations, variation de stock définitive, subventions — ne remontent **jamais** dans l'ERP, et l'upload de début janvier porte encore les mêmes chiffres. Sur 2025 cela laisse **32 944 €** d'écart avec le compte de résultat (CA ERP +10 360, charges d'exploitation −26 584, subventions 4 000 absentes). Limite acceptée (décision Vincent, 2026-08-26) : le widget estime en continu, le bilan fait foi. **Calage de référence** : sur l'exercice 2024, clos et donc comparable, l'EBE calculé donne **269 613 €** contre **269 982 €** au compte de résultat — 369 € de résidu. C'est ce calage qui valide le périmètre ; toute retouche de la formule doit le refaire.

⚠️ **Ces figures excluent les provisions** — `upload_compta` ne les porte pas — tandis que **la variation de stock, elle, y EST incluse par estimation** (§Variation de stock estimée). Une mention permanente disait les deux sous les tuiles ; **retirée le 2026-08-26 à la demande de l'utilisateur** — elle annonçait un montant (« variation de stock estimée à 57 622 € et intégrée ») que rien d'autre sur la carte ne permettait de recouper, et coûtait une ligne sur un widget déjà dense. Le calcul est intact et porte toujours l'EBE affiché ; ne pas réintroduire la mention sans lui donner une surface où le chiffre se lit vraiment. Voir §Valorisation du stock widget pour le chiffre manquant. ⚠️ **Ne jamais y réintroduire la « production stockée » : ETM n'en a pas.** La case **FM** du 2052 est vide en 2023, 2024 **et** 2025 (vérifié sur les liasses). Les 178 359 € de 2024 que ce document et le libellé du widget lui attribuaient sont en réalité la case **FP, reprises sur amortissements et provisions** — mention retirée de l'écran le 2026-08-26. Ce qui manquait réellement à l'EBE intermédiaire, c'est la variation de stock du compte de charge **603700**, pas un compte 71, et elle est désormais estimée (voir §Variation de stock estimée). Route `/rapports/finance/analyse`; the hand-rolled SVG chart's palette is validated with the `dataviz` skill's `validate_palette.js` (solid = produits, dashed = charges, the second channel its CVD WARN requires). **Notifications** (`dashboard_notifications`, gated on the API — the cards name client orders and stock levels): ports legacy *FI_Notifications.wdw* + its gear window *FEN_Abonnement.wdw*. See §Notifications widget below

### Notifications widget (tableau de bord)

Legacy model, reverse-engineered from the data (the `.wdw` sources are PCS-compressed): **`abonnement_notif`** is the catalog of subscription types (`nom`/`description`/`icone`), partitioned by `IDsociete` — which is why the société-2 "FNC" entry never appears in an ETM user's list; **`abonnement_user`** is `IDutilisateur × IDabonnement`; **`notifutilisateur`** holds the generated alerts (`hash`/`Titre`/`Description`/`icone`/`visible`), rebuilt periodically by a WinDev routine that deletes rows whose condition has cleared. (`notif_token` is unrelated — FCM push tokens for the Android terminals.)

ETM **shares the catalog and the subscriptions** (same tables, so subscribing here subscribes in the WinDev app) but **computes the alert list live** on every read instead of persisting rows: legacy's `hash` is an opaque SHA-1 whose formula could not be recovered, so any row we inserted would show twice in the legacy app — and the WinDev routine rebuilds that table anyway. Consequences:
- `visible = 0` has no row to live on, so **hiding a card is per user** in `data/notification-hidden.json` (an improvement — legacy's flag hid a card for the whole company). Stale entries are pruned on read, scoped to the detectors that actually ran, mirroring legacy deleting the row outright. The per-card control is an **eye** (`EyeOff` = hide, `Eye` = restore, icon shows the action like `WidgetFrame`'s own hide button), and legacy's "Afficher tout" checkbox is the §41 counter pill in the body toolbar — kept off the navy band so the eye means exactly one thing in this widget.
- **Subscriptions outside this app's catalog are carried over untouched on write.** An ETM user can be subscribed to a société-2 row (real case: user 1 → "FNC") that the dialog never shows and therefore never sends back; rewriting from the payload alone silently unsubscribes them in WinDev. Guarded by `check-abonnements.ts --write`.
- The 8 detectors live in `apps/api/src/lib/abonnements.ts`, keyed by `IDabonnement_notif`; routes `abonnements.ts` (`/api/abonnements*` — **not** `/api/notifications`, which is the unrelated *email*-subscription feature); widget `components/dashboard/NotificationsWidget.tsx`. The header icon is **Tricobot**, not a bell — `components/icons/TricobotMascot.tsx` renders `/tricobot/tricobot-mascot.png` frameless, straight on the navy band (`WidgetFrame` gained an optional `iconBleed`: no gold plate, no ring, for icons that are background-free artwork). That asset is prepared from the **official transparent render** on the shared drive (`Malterre Drive/ETM/Eléments Graphique/TricoBot/3D/no bg better res.png`, 1024², no glow or shadow baked into the alpha) by trimming to its alpha bbox, squaring and downscaling to 512². **Do not** try to key him out of the older opaque `tricobot-wave.png` (still used full-size by the Clients › Commandes pricing nudge) — that was tried and it is a trap: he is a *white* yarn cone on near-white, so only connectivity separates them, the yarn texture lets any gradient fill walk through his silhouette, and his cast shadow cannot come off without eating the cone. Detector 5 is validated exactly against the legacy rows ("Lot de fil N° 10430" is `stock_fil.lot`, **not** the PK; predicate `IDref_fil_commande = 0 AND stock > 0`), and detector 7 keys on the **client order line**, not the ennoblisseur affectation (legacy notified a roll carrying `IDref_commande_affectation = 143`). Both TM detectors scope to the canonical "écru rolls in stock" population from `stock-ecru.ts`, or they would walk ~52k historical rows.
- Volumes are legitimately four-figure (~1k unaffected écru rolls), so the widget caps rendering at 150 cards and **says what it dropped** plus offers a per-type filter. Detection is memoised for 60 s; the header refresh button clears it. Guard: `apps/api/src/scripts/check-abonnements.ts`

### Évolution du CA widget (tableau de bord)

Monthly CA as one line per year with the last 5 years as toggleable pills, plus an **Annuel** bar mode. Permission `dashboard_ca` (same confidential figure as the CA table, enforced on the API); endpoint `GET /api/rapports/ca-evolution?years=N`; widget `components/dashboard/EvolutionCaWidget.tsx`.
- Its own endpoint rather than N calls to `/ca-mensuel`, which returns the whole per-client matrix when the chart needs twelve totals. Same `caForYear` aggregation underneath, so it agrees with the CA table to the centime (cross-checked: 2026 = 663 818,60 € in both). Years are fetched **sequentially** — each is a full-year scan of `facture` on the shared HFSQL server and firing five at once is the burst that upsets the bridge.
- ⚠️ **`caAvailableYears()` counts DOWN from the newest year.** Assuming ascending and taking `.slice(-5)` silently served the five *oldest* years (2020-2024 instead of 2022-2026). The endpoint now sorts explicitly instead of trusting the helper's order.
- For the **current year only**, months after the last invoiced one are emitted as `null`, not `0` — otherwise the line crashes to the axis for the rest of the calendar. Past years keep real zeros (2020's empty first nine months are a fact).
- Chart work follows the `dataviz` skill. Palette **validated, not eyeballed**: `node scripts/validate_palette.js "#3B7DC9,#C2410C,#17915B,#B8860B,#7C3AED" --mode light --pairs all` → all pass with one WARN (`#B8860B↔#17915B` ΔE 6.5 protan) in the 6–8 band, which is legal **only with secondary encoding**; four alternative palettes were validated and all scored worse. So each year also carries a distinct **dash pattern** and the **year pills above the chart** name every year next to its colour — identity is never colour-alone. Colour is keyed on the year's **recency** inside the *full* list (newest = style 0), never on its rank among the *visible* ones, so toggling one off never repaints the survivors.
- **The running year leads the chart** (2026-08-26): newest year = style 0, solid accent blue, `STROKE_LEAD` 3.25 against `STROKE_BACK` 1.75 at 0.72 opacity for the others, and drawn last so it sits on top. Before that it took whatever style the ascending list had left over — a dashed violet, the least legible of the five — and the reader had to hunt for the line that matters most.
- **No legend under the chart** (2026-08-26, user request): it restated what the pills already say and cost a whole row on a 420 px card. Hovering a month opens a **tooltip** listing every visible year's CA for that month, **ranked** — the read becomes « ce mois-ci, qui fait quoi » instead of « voici les couleurs ». It is positioned in the plot's own pixel space (the SVG is drawn at real size, so SVG units *are* CSS pixels), flips side past the middle and clamps vertically, so it never leaves the card at any width. "Annuel" has no pills, so each bar now carries its total above it — the number the legend used to hold — and hovering gives the exact centime over a full-height hit target.
- Axis ticks come from the shared `lib/chart-scale.ts` (`niceScale`, extracted from `AnalyseFinanciereWidget`) so both charts tick at round numbers rather than the raw maximum.
- The SVG is drawn at the container's **measured pixel size**, never a `viewBox` + `preserveAspectRatio="none"` — that stretches month labels horizontally as the card is resized.

### Valorisation du stock — calcul ACTIF, widget EN SOMMEIL

Valeur d'achat et valeur dépréciée du stock, taux de provision, détail par type. Permission `dashboard_stock_valorisation` (**gated on the API** — c'est un poste de bilan) ; endpoint `GET /api/rapports/stock/valorisation` ; calcul `apps/api/src/lib/valorisation-stock.ts` ; composant `components/dashboard/ValorisationStockWidget.tsx`.

⚠️ **`valorisation-stock.ts` N'EST PAS DU CODE MORT, malgré l'absence d'écran.** `variation-stock.ts` l'appelle (`valoriserStockCache()`) pour estimer la variation de stock injectée dans l'**EBE** — Analyse financière **et** rapport Finance. Le supprimer ferait retomber l'estimation à zéro **sans erreur**, et l'EBE intermédiaire redeviendrait faux de plusieurs dizaines de milliers d'euros. Garde : `check-valorisation-stock.ts`.

⚠️ **Le widget a été retiré du tableau de bord le 2026-08-26** (une entrée commentée dans `registry.tsx`, rien d'autre supprimé). Il répondait à « combien vaut mon stock » — question de **bilan**, à cadence annuelle — et affichait un taux de provision **sans point de comparaison**, donc ininterprétable au quotidien. Décision Vincent : « j'attends que le besoin s'exprime vraiment ». **Le rétablir = rétablir cette seule entrée** ; endpoint, permission, composant et guard sont intacts. La clé de permission reste (elle garde l'endpoint) mais son libellé dit « widget retiré », sinon un admin la coche et ne voit rien apparaître. **Si le besoin revient, viser la « falaise », pas le niveau** : `valoriserStock(asOf)` accepte une date et vieillit le stock courant, donc « à périmètre constant » se calcule sans requête nouvelle — mesuré au 26/08/2026 : **−108 597 € de valeur nette à 6 mois, −182 103 € à 12 mois** si rien ne bouge, ce qui est une liste de priorités de vente et non un chiffre de bilan.

**Pourquoi il existe.** `upload_compta` ne porte pas les **provisions**, donc l'Analyse financière ne les voit structurellement pas — un stock passé de 37 % à 49 % de provision entre 2024 et 2025 n'apparaissait nulle part. (Une version antérieure de ce document invoquait aussi la « production stockée » : ETM n'en a pas, la case FM du 2052 est vide sur les trois derniers exercices — voir §Analyse financière.) Le mécanisme légataire, **`inventaire_compta`** (un arrêté mensuel par type, `prix_achat` brut + `valeur_deprecie` net), **a cessé d'être écrit le 28/06/2025**.

**Quatre types, deux barèmes.** Les quatre inventaires imprimés au 27/12/2024 reproduisent EXACTEMENT la ligne `inventaire_compta` du 28/12/2024 (Fil 199 090/122 891 · TM dispo 56 372/27 937 · TM en cours 44 236/43 469 · Fini 331 978/179 142), et la boucle se ferme jusqu'au bilan 2025.

| | Fini · TM dispo · TM en cours | Fil (ordre signifiant) |
|---|---|---|
| | 2ᵉ choix −90 % | 100 % élasthanne **0 %** (prime sur tout) |
| | < 1 an 0 % | < 100 kg **et** > 1 an −90 % |
| | 1-2 ans −50 % | < 1 an 0 % · 1-2 −50 % · 2-3 −75 % · > 3 −90 % |
| | > 2 ans −90 % | |

**Populations** (toutes en état courant) : fil = `stock_fil.stock > 0` **et `IDclient = 1`** (Ets Malterre — le fil confié est dans nos murs mais pas à notre bilan : 46 lots / 8 201 kg exclus) ; TM = écru ETM non expédié et sans enfant `stock_fini`, scindé par **`IDref_commande_affectation`** (≠ 0 → en ennoblissement) — ⚠️ **pas** par magasin, MATEL apparaît dans les deux inventaires imprimés ; fini = `IDligne_expedition = 0 AND IDetat_stock_fini = 3`.

**Coûts** : fil = `ref_fil_commande.prix_unitaire` (prix réellement payé), repli `ref_fil.prix_kg` ; écru = fil + façon tricotage (`ligne_commande_sous_traitant.prix`, repli `ref_ecru.prix`) ; fini = + ennoblissement (prix réel commandé, sinon forfait `tranche_tarif_ennoblissement` à 200 kg). Le poids vient de **`stock_ecru.poids`**, pas de `stock_fini.poids`.

- ⚠️ **L'escrime n'est pas couvert** — pas d'inventaire dans l'ERP. Fin 2025 : **57 600 € brut / 13 935 € net**, soit l'écart exact entre le total des quatre types et le bilan. Manque chiffré, pas inconnu ; le widget l'affiche.
- ⚠️ **Ne peut décrire que MAINTENANT** : colonnes d'état courant + dépréciation depuis la date du jour. Un arrêté passé n'est pas rejouable, donc les 14 mois manquants d'`inventaire_compta` ne sont pas récupérables.
- ⚠️ **`asso_fil_matiere` et `matiere_premiere` ont des identifiants ACCENTUÉS** (`IDMatière`, `IDmatière_première`) que le pont Linux refuse → `SELECT *` + résolution par préfixe (`pickKey`), jamais nommés en SQL. À l'inverse `stock_fil` porte des memos binaires → colonnes nommées explicitement (`SELECT *` y renvoie 0 ligne sur Windows). Vérifié en exécution sur le serveur de prod.
- ⚠️ **`asso_fil_matiere.pourcentage` est une FRACTION** (0,31 = 31 %), pas 0-100 — contrairement à `composition_ecru.pourcentage`. Une ref est « 100 % élasthanne » si toutes ses matières le sont et que la somme fait 1.
- ⚠️ **`date_saisie` / `date_entree` reviennent en TIMESTAMP** (`"2020-10-04 00:00:00.000"`). `sst-shared.dateDigits` exige `/^d{8}$/` et renvoie donc `''` sur **toutes** les lignes ; une chaîne vide perd toute comparaison `>` et range l'intégralité du stock dans la tranche la plus vieille à 90 % — un chiffre plausible, pas un plantage. Le module a son propre `d8()`. Garde : `check-valorisation-stock.ts`, qui échoue si un type n'a qu'une tranche peuplée.

### Variation de stock estimée (compte 603700)

L'écriture de variation de stock est **annuelle**. Onze mois sur douze le compte reste à zéro, le compte de résultat porte donc le coût complet de la production *y compris ce qui dort en magasin*, et l'EBE intermédiaire est amputé d'autant — c'est ce qui a fait lire l'EBE de juillet 2026 (88 k€) comme un effondrement alors que 59 k€ de stockage l'expliquaient. Calcul `apps/api/src/lib/variation-stock.ts`, injecté dans `finance-common.ts` (les deux surfaces à la fois).

- **Le compte est `603700`, seul compte de variation de stock du plan ERP, et c'est une charge VARIABLE** — un montant négatif y remonte donc marge brute et EBE. Historique : 81 083 € (2024), 59 092 € (2025), 0 € (2026).
- ⚠️ **L'estimation ne s'applique QUE si la valeur comptabilisée est à zéro.** Le jour où l'expert-comptable passe l'écriture, le vrai chiffre reprend la main tout seul et le badge disparaît — rien à nettoyer, aucun risque d'écraser une écriture réelle. C'est la propriété de sûreté centrale du dispositif.
- **Niveau exact, forme approchée.** Le montant vient de deux photos réelles du stock (dernier arrêté `inventaire_compta` de N-1, et `valoriserStockCache()` aujourd'hui) : les deux bouts sont justes. La répartition mensuelle suit les kilos physiques accumulés (écru produit − écru/finis expédiés), **bornée à [0, montant]** — la forme brute ignore les achats de fil et la valeur ajoutée écru → fini, donc son pic dépassait le point d'arrivée de moitié (−178 538 € au mois 2 pour un total de −114 556 €). Assumé comme outil de pilotage, pas comme écriture (décision Vincent, 2026-08-25).
- ⚠️ **La base DOIT être une clôture d'exercice** (décembre de N-1), jamais le dernier arrêté venu : une série arrêtée en juin ferait porter à l'année suivante une variation de quatorze mois — un chiffre faux qui a l'air juste. Sans clôture, aucune estimation et l'écran montre le vrai zéro (cas de la copie dev, qui n'a pas l'arrêté 2025).
- ⚠️ **Le dernier mois actif se lit sur les MOUVEMENTS, pas sur le cumul** : un cumul reste non nul une fois démarré, donc le chercher là-dedans renvoie toujours décembre et l'estimation s'étalait sur des mois qui n'ont pas encore eu lieu.
- **ETM seulement** (`scope.societe === 1`) : `inventaire_compta` et la valorisation n'existent que pour cette société ; TRM lit son compte tel quel.
- **Amorçage de la série** : `seed-inventaire-compta.ts` (`--write` / `--revert`, idempotent) a posé l'arrêté du 31/12/2025 depuis les quatre inventaires imprimés ; celui du 28/12/2024 était déjà en base. Contrôle bilan **avant** écriture, sinon refus. ⚠️ Déviation assumée : le type Fini était stocké en **métrage** (`unite = 3`) par WinDev ; ce métrage est irrécupérable au 31/12/2025 (reconstitution depuis les numéros de pièce : 17 570 kg retrouvés sur 21 039), donc l'arrêté amorcé est **en kilos pour les quatre types**.
- Garde : `check-valorisation-stock.ts` (base = clôture, deux bouts justes, interpolation bornée, signe constant, pas de mois futur) et `check-finance-analyse-buckets.ts`, qui prouve que l'estimation atteint le rapport ET le widget avec la même valeur.

### Charges widget (tableau de bord)

Charges fixes and charges variables for the current exercice, each read as a **rythme**: how much of last year's whole envelope is already spent, against how much of the year has actually been lived. Widget `components/dashboard/ChargesWidget.tsx`.
- **No new endpoint and no new permission**: it calls the report's own `GET /api/rapports/finance` (82 comptes ≈ 15 KB — small enough that a dedicated endpoint would only add a second place for the aggregation to drift) on the **same React Query key** `['rapport-finance', null]`, and is gated on **`view_rapport_finance`**, which that endpoint already enforces. A separate `dashboard_*` key could only produce a state where the widget shows and the data 403s.
- It sums the endpoint's `lignes` by `variable` **exactly as the report's totals bar does**, not the pre-computed `totaux.frais_fixe`/`frais_variable` buckets. They agree today, but the screen is what users read, so the widget follows the screen. Verified against the report: fixes 111 604,54 / 478 967,27 → 23 %, variables 610 431,35 / 2 175 473,81 → 28 %.
- ⚠️ **The card no longer shows the raw N/N-1 ratio as its verdict** (2026-08-26). The user's own framing: « si les charges fixes sont à 50 % à la moitié de l'année, on est bon ; moins, c'est encore mieux ; plus, il y a un problème à investiguer ». So the number that matters is the ratio **minus the share of the year elapsed**, in points — because a raw « 23 % » in March means nothing on its own. That écart is the pill; the gauge draws both quantities at once (fill = consumed share of the N-1 envelope, vertical navy tick = the repère), so everything left of the tick is money not yet spent. Scale is fixed 0→100 % of N-1 on both cards, or they would stop comparing to each other; an overrun fills the gauge and the pill carries the amplitude.
- ⚠️ **The repère is measured at the ARRÊTÉ date, not at today.** The last upload can be months old (23/03 while today is 26/08), and it is the date of the *amounts* that must bound the comparison — using today would make the rythme look falsely good. UTC arithmetic throughout: a local-midnight `Date` slips a day around a DST boundary, and the repère with it.
- ⚠️ **Fixes and variables do NOT share a verdict scale, on purpose.** Charges *fixes* carry the alert ladder (±3 pts tolerance = « au rythme », up to +10 amber « à surveiller », beyond red « à investiguer », below green « sous le rythme »). Charges *variables* carry **none**: they follow activity, so above the pace means the company produced more — the user said as much — and they wear an informative sky blue. Painting both red would teach the reader to ignore the colour on both cards. Thresholds are in points of percentage, not euros, so they read the same on a 600 k€ poste and on a 10 k€ one.
- The report's own per-compte pill **stays** the raw N/N-1 traffic light (`lib/depassement.tsx`, `<100 %` emerald / `≤120 %` amber / `>120 %` red, nothing when N-1 is empty) — « ce compte a-t-il dépassé l'an dernier ? » is a different question from « sommes-nous dans les clous à cette date ? ». Two readings of the same two numbers: do not unify them without deciding which one the report should be asking. TRM's dashboard has the same widget over its own partition — the component and `depassement.tsx` are verbatim mirrors there, so improve them **here** and re-copy.
- The footer names the tick and carries the **arrêté date**, not just the year: `upload_compta` rows are cumulative YTD, so an amount only means something alongside the date it was stopped at.

### BFR / bilan — hors de portée, et pourquoi (constat 2026-08-26)

Question posée : un widget **BFR** (besoin en fonds de roulement) pour ETM. Réponse
mesurée sur la base vivante, pas déduite : **non, pas en l'état**, et le raccourci
évident est fermé. Consigné ici pour qu'une prochaine session ne refasse pas l'enquête.

BFR = stocks + créances d'exploitation − dettes d'exploitation. Chaque terme demande un
compte de **BILAN** (classes PCG 3, 4, 5), alors que toutes les surfaces finance
construites jusqu'ici ne touchent que les classes 6 et 7.

- ⚠️ **`compte_compta` ne contient AUCUN compte sous 600000**, ni pour la société 1 ni pour
  la société 2. Les sous-classes présentes sont 60-64, 66, 67, 70, 75, 76, 77 — et rien
  d'autre. Les 84 lignes de `releve_compta` au dernier arrêté ETM (20260323) sont toutes en
  classe 6 ou 7. **Ce que l'expert-comptable dépose est un compte de résultat, pas un
  bilan** : pas de 411 clients, pas de 401 fournisseurs, pas de 3x stocks, pas de 512.
  C'est le même constat qui explique pourquoi l'EBE s'arrête où il s'arrête.
- ⚠️ **L'ERP n'enregistre aucun règlement.** `facture` a exactement 14 colonnes —
  `IDadresse, IDfacture, IDclient, date, IDmode_paiement, IDtva, num_tva, IDecheance, type,
  IDsociete, numero, IDcode_comptable, IDexpedition_divers, IDcommande_client` — et pas une
  n'est un paiement. Un encours client ne peut donc être que **théorique** (« si chaque
  client paie pile à l'échéance »), ce qui sous-estime précisément les mauvais payeurs.
  Matière première disponible pour ce calcul : `echeance` est structurée
  (`TYPE` / `nb_jours` / `jour`, 26 lignes, T1 = à réception ou acompte, T2 = net à N jours
  date de facture, T3/T4/T5 = variantes fin de mois) et `facture.IDecheance` est renseigné.
- ⚠️ **Aucune facture fournisseur dans les 204 tables**, et `fournisseur` n'a que 7 colonnes
  (`IDfournisseur, nom, tel, fax, commentaire, est_visible, IDsociete`) — même pas de
  conditions de paiement ; `sous_traitant` non plus. Le poste dettes fournisseurs n'a
  **aucune source**, et ce n'est pas un arrondi : les achats et services extérieurs
  (comptes 60→62) pèsent 669 857 € au 23/03/2026.
- Seul terme réellement **mesuré** : les stocks, par `lib/valorisation-stock.ts` (brut ET net
  après dépréciation) — voir §Valorisation du stock, y compris son trou connu de
  13 935 € net d'escrime hors ERP.

**Conséquence : ne pas publier un widget étiqueté « BFR ».** Il afficherait un nombre qui
n'en est pas un, et faux dans le sens dangereux — gonflé, puisqu'il manquerait tout le
financement fournisseur.

Trois sorties possibles le jour où le sujet revient, de la meilleure à la moins bonne :
1. **Demander à l'expert-comptable d'inclure les classes 3/4/5 dans son export.** Le BFR
   devient exact, chaque terme mesuré, sur la machinerie `finance-common.ts` déjà en place.
   C'est une demande à une personne, pas du code — et de loin le meilleur rapport.
2. **« BFR estimé » calibré sur le dernier bilan** : stocks mesurés + créances = run-rate CA
   × DSO + dettes = run-rate achats (60→62, déjà dans `releve_compta`) × DPO, les deux
   constantes venant de la liasse du dernier exercice clos et rafraîchies à chaque clôture.
   Le widget devrait alors afficher les paramètres ET leur millésime.
3. **« Encours d'exploitation »** — stock net + encours client théorique, deux tuiles, mention
   explicite « hors dettes fournisseurs ». Constructible sans intrant extérieur, mais ne
   répond qu'à la moitié de la question.

⚠️ Note de méthode : la **copie dev s'arrête au 24/03/2026 pour `facture`** (et au 23/03 pour
`upload_compta`), alors que les commandes y vont jusqu'au 24/08. Un encours théorique calculé
sur la copie dev sort donc à **0 €** — artefact du jeu de données, pas du calcul. Toute
vérification de ce genre doit se faire sur la prod.

### Commandes du jour widget (tableau de bord)

The client orders taken today plus the CA they represent. Permission `dashboard_commandes_jour` — **gated on the API too**, like the CA/finance widgets, since it exposes per-client order values. Endpoint `GET /api/commandes-client/du-jour?date=YYYYMMDD` (**declared before `/:id`**; `?date=` exists for testability and a future "hier" control, defaulting to today); widget `components/dashboard/CommandesDuJourWidget.tsx`.
- An order's value is **Σ(quantite × prix)** over `ligne_commande_client` — the same plain product the screen already uses for a line's `montant` (`commandes-client.ts`). The sst caveat (ennoblisseur lines where quantite is Ml and prix €/Kg) does **not** apply: client lines price their own unit.
- Scope is the file's canonical ETM clause `IDsociete = 1 AND IDcommande_ETM = 0`, so TRM mirrors never inflate the day.
- **Donations are listed and flagged but excluded from the CA** (a don isn't revenue). In practice they carry no priced lines, so today it changes nothing — it stops a priced donation from ever inflating the figure, and the widget says "dont N don(s), hors chiffre d'affaires" when any are present.
- **Freshness is the point**: `staleTime: 0` + `refetchOnMount: 'always'`. Dashboard widgets unmount when you navigate away, so arriving on the tableau de bord *is* the remount — verified: 1 request on first load, 2 after leaving and returning.
- When the day is empty the widget reports the **last order date**, so "nothing today" can't be mistaken for a broken widget. Guard: `apps/api/src/scripts/check-commandes-du-jour.ts` (pins 2026-03-23 → 6 orders, 273 180,32 € HT, 1 donation excluded)

### Utilisation fil widget (tableau de bord)

Ports legacy *FI_Utilisation_fil.wdw*: pick a fil (+ optionally one of its coloris) → the écru références whose composition uses it. Permission `dashboard_utilisation_fil`; endpoint `GET /api/references-fil/:id/utilisation?colori=<id>`; widget `components/dashboard/UtilisationFilWidget.tsx`. Two facts about `composition_ecru` (`IDref_ecru × IDcolori_ecru × IDref_fil × IDcolori_fil × pourcentage`) drive it:
- A ref's composition is stored per écru coloris **plus a base row at `IDcolori_ecru = 0`**, and those base rows generally carry `IDcolori_fil = 0`. So filtering by a yarn coloris legitimately returns **fewer** refs than the unfiltered list — not a bug (validated: 28 refs for `1/28 COTON PEIGNE BIO Z`, 23 once "ecru" is picked). The widget states the delta ("23 références sur 28 pour ce fil") rather than letting the count silently shrink.
- **`colori_fil` reuses names across ids** — that one fil has NINE coloris called "ecru", only one of which any composition references (`project_coloris_id_spaces_collide` territory). Picking by id would return nothing, so the coloris list is grouped **by name** and the filter expands the chosen name back to every id carrying it; the dropdown shows each group's ref count so the user sees the yield before clicking.
- Archived références are **included**, as legacy does (its list shows archived 181/183), but flagged with a badge. `ref_ecru.archivé` is accented → `SELECT *` + tolerant key read, never named in SQL.
- Legacy's "Filtre" box + "Filtrer" button existed because a WinDev combo can't search; `SearchableCombobox` can, so that round trip is gone. Guard: `apps/api/src/scripts/check-utilisation-fil.ts` (pins 28/23 and every row legible in the legacy screenshots)

### Suivi pièce widget (tableau de bord)

Ports legacy *FI_Suivi_pièce.wdw*: type a piece number → its life story (écru → transferts → rouleaux finis). Permission `dashboard_suivi_piece`; endpoint `GET /api/stock/ecru/suivi?numero=…` (**declared before `/ecru/:id`** or "suivi" is captured as an id); widget `components/dashboard/SuiviPieceWidget.tsx`. Field mapping validated against the legacy screen for piece 3397/30:
- **`stock_ecru.IDref_commande_source` / `IDref_commande_affectation` hold a `ligne_commande_sous_traitant` id, NOT a commande id.** Legacy prints the parent commande — the piece stores ligne 8437 and the screen says "Commande source : 8461 - Tricotage Malterre" — so both are resolved up through `ligne_commande_sous_traitant` → `commande_sous_traitant` → `sous_traitant`.
- Transfers come from `piece_transfert` (`IDpiece_ecru` / `IDpiece_fini`) joined to `bon_transfert`; "Transfert n° 4165 le 03/03/2026" is the bon's own PK and its `DATE` — a **reserved word, always alias it** (`DATE AS dtransfert`).
- **A numero is not unique** (dev data has 903 écru rows numbered "fictif") and fini rolls carry their own numero including the `-1`/`-2` suffixes of a cut roll. The search covers `stock_ecru.numero` AND `stock_fini.numero` (walking a fini back to its écru), returns every match capped at 20, and the widget says when there are several.
- Fini coloris uses the same polymorphic rule as `stock-fini.ts` (`avec_teinture` 0 → `colori_ecru`, 1/2 → `ref_fini_colori`) **plus a cross-space fallback**: real rolls exist whose `IDColoris` is an écru-coloris id despite `avec_teinture = 1`, and the id spaces collide numerically (`project_coloris_id_spaces_collide`), so a miss in the expected catalog retries the other rather than showing nothing.
- ⚠️ **Divergence:** legacy's Suivi Pièce labels magasin `0` "Tricotage Malterre"; ETM labels it **"Ets Malterre"**, matching `routes/transferts.ts`. One label for magasin 0 across the app beats reproducing a per-screen inconsistency — revisit if the users read it as wrong.
- The widget goes **beyond legacy's text block**: the yarns the piece was knitted from, the ordre de fabrication, and the expéditions. Sourcing notes:
  - **Yarns come from `asso_fil_of` (via `stock_ecru.IDordre_fabrication`), NOT `asso_fil_lignecmdsst`.** The latter records what was *sent to* an external knitter and is empty for in-house production (0 rows for the reference piece); `asso_fil_of` is what the machine actually consumed, and it carries the percentage. Each lot then walks `stock_fil` → `ref_fil_commande` → `commande_fil` for the purchase order + its dates — absent on older lots (`IDref_fil_commande = 0`), so that line is conditional.
  - `ordre_fabrication` gives the knitting date + machine (`productivité*` etc. are accented — name ASCII columns only, same for `machine.connecté`, `commande_client.archivé/expedié/envoyé_client`, `expedition.envoyé_*`).
  - A piece has **two** expedition paths: `stock_fini.IDligne_expedition` (the client shipment) and `stock_ecru.IDligne_expedition_ETM/_TRM` (a TRM-knitted piece ships to ETM before dyeing).
- **Presentation is reverse-chronological** (newest at top) with a header strip answering "where is it now" (état pill pushed right), and it distinguishes **objects** (tombé de métier / rouleau fini — solid cards, coloured left edge) from **events** (transferts, expéditions, commandes — dashed frames). Order: expédition client → fini → commande ennoblissement → transferts → expédition écru → tombé de métier → commande tricotage (+ its OF/machine) → fils. The écru badge reads **"Tombé de métier"**, not "Écru". The two production orders share one `CommandeCard`, tinted to the stage they *produce* — **green dashed = ennoblissement**, **amber dashed = tricotage** — so each order sits with its output.
- Both roll cards carry the **défauts / observations hover icons** of Clients › Commandes (red triangle incl. "2e choix", blue speech bubble), read-only. Sources differ by stage and that matters: the écru side uses `stock_ecru.observations` + structured defects via the file's own `fetchDefectsByEcru`/`defautSummary`; the **fini side uses the roll's own `observations` + `observation_sst` + `second_choix`** and deliberately does NOT touch `defaut_qualite` — see the ambiguity note in §HFSQL rules. Both stage cards use the same shape: **reference as the title, designation as the subtitle**. The tricotage card deliberately shows neither OF nor machine (noise beside the order itself) — the OF is still what the yarn list is read through, just not displayed.
- A shipped roll's **location is its customer**, not `IDmagasin`: once expédié, `stock_fini.IDmagasin` still points at the last internal depot (often `0` = Ets Malterre) and would claim a delivered roll is still in the building — the header takes `expedition.client` instead. Transferts show **no "non validé" tag**: `bon_transfert.est_valide` doesn't gate the movement (legacy applies a bon to stock immediately), so flagging it read as a problem where there is none.
- Facts are placed by **which stage they're true of**, not by which table they live in: the écru card shows no magasin and no ennoblisseur (`stock_ecru.IDmagasin` is where the record sits *today* — a fact about the finished roll, already in the header; the ennoblissement order is the step that *ended* that stage, so it has its own card), and the fini card drops its magasin once shipped, since the expédition above already says where it went. Expéditions render **sender → recipient**, the sender coming from `expedition.IDsociete` (1 Ets Malterre / 2 Tricotage Malterre / 3 Confection) — printing only the client made the TRM→ETM écru leg look like it went nowhere. Guard: `apps/api/src/scripts/check-suivi-piece.ts` (pins the legacy screen's piece **and** the enrichment joins on a complete chain)
