# Authentication & Permissions

## Authentication (password login, since 2026-09-30)

Plan and decisions: `~/.claude/plans/user-management.md`. One account per PERSON (`utilisateur`, the per-PC rows of the WinDev era were folded by `scripts/comptes-import.ts` — old ids in `utilisateur_fusion`, resolved by `lib/utilisateur-fusion.ts`). Two ways in, nothing else:

- **A person** logs in with `identifiant` (or their email) + password. Passwords are scrypt (`lib/passwords.ts`), set by an ADMIN — no « mot de passe oublié » by decision. Vincent generates them (`scripts/mots-de-passe.ts --tous --fichier <usb> --write`, or « Réinitialiser » in Paramètres › Utilisateurs › Compte, shown once) and carries them to each person's Dashlane; « Provisoire » forces a change at the next login (`doit_changer_mdp`).
- **A station** (`type_compte = 'poste'`: Visitage #10, **Atelier** #14 — was « Regleur », renamed 2026-09-30, same id: the shared phones and the pointeuse are bound to it) has no password: an admin generates a one-time 6-digit code (`lib/postes.ts`, 10 min, in memory), the PC types it on the login screen (« Poste d'atelier ») and gets a `poste` session with no expiry. Who does the work is picked in the app. Atelier phones and the pointeuse keep their own enrolment (`mps_appareil` / `mps_pointeuse`, `lib/appareils-atelier.ts`).
- **A third kind, `type_compte = 'appareils'`** (migration `0005_comptes_appareils`, rules `lib/types-compte.ts`): devices that run their OWN app — atelier phones, pointeuses. No password, no login, member of NO app (`utilisateur_app` empty — the only kind allowed none), no `permission` row, never admin, never in « Voir comme » (`/auth/users` skips it, `/voir-comme` 404s), never a notification subscriber (membership filters them). **Why**: `attachUser` sets `req.userId` = the device's account when no user session is present, so an enrolled phone acts as its account on EVERY route; under a TRM poste (#14 until 2026-09-30) a shared phone carried that poste's TRM rights into the ERP. The atelier / pointage routes check no right (enrolment IS the right), so the account needs none. **#14 « Atelier »** is this kind since `scripts/comptes-appareils-fix.ts`. Listed in **TRM's** Utilisateurs screen only (it belongs to neither app, but every device under it is TRM's; ETM listed it too until 2026-10-01 — noise there, and a phone could be revoked from the wrong app), section « Appareils d'atelier », Appareils tab only; « + Nouveau » offers the kind in TRM only. If ETM ever enrolls devices of its own, give it its own appareils account and widen the filter in `SettingsUtilisateurs.tsx`. Enrolment (server-enforced in `POST /atelier/appareils/codes`, 409 `compte_inadapte`): PC → poste only; phone / pointeuse → appareils account, or a person member of TRM (the régleurs' own phones, until they move — see merge log 2026-09-30 feat/comptes-appareils). Never a phone under a poste.
- **`session.app`** (migration 0005): the app whose login screen enrolled a PC (`POST /auth/poste { code, app }`, `UserPickerGate` wraps the login screen in `AppCodeProvider`). The Appareils tab shows it (« ERP TRM »); NULL = enrolled before 2026-09-30, shown « Application non enregistrée » — never guessed from the account's membership.
- **Paramètres › Utilisateurs lists three sections, Personnes / Postes / Appareils d'atelier**, and every enrolled device of an account — PCs (`poste` sessions), phones, pointeuses — sits in ONE centre tab « Appareils » (`components/comptes/AppareilsTab.tsx`, read `GET /api/comptes/:id/appareils`, one « Enrôler » that asks PC / téléphone / pointeuse; rename `PATCH /comptes/:id/postes/:ref` or `/atelier/appareils/:id`; revoke by session ref or device id). A PC is offered only under a station account, a phone / pointeuse under an appareils account or a TRM member person (`enrolementsPossibles()`). A station account shows Écrans, Permissions, Appareils only (no Profil, no Notifications, no password). The Sessions panel lists BROWSER sessions only, and « Fermer toutes les sessions » never touches an enrolled PC. TRM's old `extraTabs` Appareils is ignored (a built-in key wins) — delete it in TRM.
- ⚠️ **A poste re-sends its cookie with the 10-year lifetime whenever its session is touched** (`renouvele` in `lib/sessions.ts`, `attach` in `lib/auth.ts`, at most every 5 min): a browser session turned into a poste IN PLACE (same token) otherwise keeps the 31-day cookie it was given. That is how the Visitage PC's picker-converted session became a poste without re-enrolment (`scripts/postes-appareils-fix.ts`, see below).

Mechanics:
- **Sessions** (`lib/sessions.ts`, table `session`): the cookie (`<AUTH_COOKIE_NAME>_session`, prod `mps_uid_session`) carries a random token, the table only its sha256. Browser sessions slide (30 days of inactivity = out), revocable per row (Paramètres › Utilisateurs › Sessions). Resolved on every request with a 15 s cache. Prod sets `AUTH_COOKIE_DOMAIN=.intra.etsmalterre.com`: ONE login for ETM and TRM.
- **`attachUser()`** sets `req.userId` (the account seen), `req.adminId` (the session owner when `est_admin`), `req.session`. `isEffectiveAdmin` = admin acting as themselves. The admin flag is the `est_admin` column — no name check any more (`isAdminUtilisateur` survives only in the import script and the pointage report).
- **« Voir comme »** (admins): `POST /auth/voir-comme` sets `session.voir_comme` — the app shows that account's menus and rights, a pill bottom-left brings the admin back; the page reloads on each switch so no query cached under the other identity survives.
- **Login journal + slow-down** (`lib/login-throttle.ts`, table `connexion`): after 5 failures per identifiant since its last success (or 20 per IP) within 15 min, logins answer 429 until the window passes. **Never a lock** — nobody can lock a colleague out.
- **Transition flags** (prod `.env`): `AUTH_LEGACY_COOKIES=1` turns a browser's old picker cookie (`mps_uid` + `mps_uid_admin`) into a session on its next request (one per page load — concurrent requests share the conversion), so nobody is logged out on deploy day; turn it off once everyone has a password. `AUTH_PICKER=1` re-enables the name picker (`POST /auth/login {IDutilisateur}`) — emergency only, it is the hole passwords close.
- **Each company has its own users** (since 2026-09-30, table `utilisateur_app`, `lib/utilisateur-apps.ts`, migration `0004_utilisateur_app`): an account belongs to ETM, TRM or both (Nicolas both; Mickaël, `Visitage`, `Regleur` TRM only — the seed). It is a LOCK, three places: the web gate (`UserPickerGate app="etm"|"trm"` in each `main.tsx`, `apps` of `GET /auth/me` — a non-member gets « Accès non autorisé »), the permission stores (`lib/permission-store.ts` reads members' rows only: a non-member holds no right of that app, admin bypass aside), the notification stores (`subscribersOf` skips non-members). Leaving an app keeps the `permission` rows — re-joining restores them. Managed from Paramètres › Utilisateurs — **one screen for both apps** (ETM's `pages/SettingsUtilisateurs.tsx`, mounted by TRM through `@etm` with props `permissionsPath` / `NotificationsTab` / `extraTabs`): the list shows this app's members, the account panel's « Applications » switches join / leave, « + Nouveau » › Compte existant brings in an account of the other app. Rules (`refusApps`, 409 `apps_refusees`): at least one app per account (deactivate to shut out), an admin never removes themself. `useAppCode()` (set by the gate) tells shared auth components which app they sit in (« Voir comme » lists members only).
- **RH** unlocks with the account password (`POST /rh/deverrouiller {motDePasse}`); the server-set code RH only remains for an account without a password.
- **Routes**: `routes/auth.ts` (config, login, poste, me, logout, mot-de-passe, users, voir-comme, sessions) and `routes/comptes.ts` (admin: list, create, patch — identifiant/email/actif/estAdmin —, password set/generate/remove, sessions, code-poste, connexions). **An account is never deleted**: deactivate it (`actif = false` refuses login and ends its sessions).
- **Web** (ETM, shared with TRM through `@etm` — TRM's `contexts/UserContext.tsx` and `components/auth/UserPickerGate.tsx` re-export ETM's): `contexts/UserContext.tsx`, `components/auth/` (`UserPickerGate` = the gate, `LoginScreen`, `ChangePasswordForm` + forced change, `VoirComme`, `UserMenuActions` → `useAccountMenu()` for both headers, `UserPicker` = transition fallback), `components/comptes/` (the Compte / Sessions panel and « + Nouveau » of Paramètres › Utilisateurs).
- **`PermissionsContext.isLoading` is bound to the user the permissions were loaded for** — right after a login the user is set one render before the refetch, and the Paramètres guard bounced the admin to `/`.

## Permissions (per-user, PostgreSQL `permission` table)

Per-user action permissions managed from the admin-only **Settings → Utilisateurs** screen. **Default closed** — non-admins with no permission record cannot perform gated actions. **Effective admins (Vincent acting as himself, NOT impersonating)** bypass all checks automatically.

- **Storage**: PostgreSQL table `permission (idutilisateur, app 'etm'|'trm', cle)` through `lib/permission-store.ts` (whole table cached in memory, dropped on write and after 30 s). Was `data/permissions.json` / `permissions-trm.json` until 2026-09-30 (imported by `scripts/comptes-import.ts`).
- **Catalog**: `apps/api/src/lib/permission-keys.ts` exports `PERMISSION_KEYS = [{ key, label, description, category }]`. **Adding a new gated action requires 3 edits**: (1) append to `PERMISSION_KEYS`, (2) gate the API route via `userHasPermission(req.userId, isEffectiveAdmin(req), 'key')`, (3) hide the UI element via `useHasPermission('key')`.
- **Sub-permissions**: a catalog entry may carry `parent: '<key>'`. The admin UI renders it indented under the parent toggle, visible only while the parent is granted; toggling the parent ON grants every child, OFF removes them. Storage stays flat (children are ordinary keys) — API routes must check parent AND child. Reference: `edit_stock_fini` + `edit_stock_fini_{stockage,etat,affectation,notes}` gating the four drawer sections of Finis > Stock (`PATCH /stock/fini/:id` and `/stock/fini/batch` enforce per-field-group; the drawer/batch dialog only render inputs for granted sections).
- **Currently gated**: `create_stock_fil` only. The **`POST /api/stock/fil`** endpoint and the **"Nouveau" button** in `FournisseursStock.tsx` are both gated.
- **Lib helpers**: `apps/api/src/lib/permissions.ts` — `loadPermissions`, `getUserPermissions`, `setUserPermissions`, `userHasPermission(userId, isEffectiveAdmin, key)` (admin bypass inside), `getAllPermissions`.
- **Routes**: `apps/api/src/routes/permissions.ts` — `GET /me` (returns `{ isAdmin, isEffectiveAdmin, granted }`), `GET /keys` (catalog), `GET /users` (admin-only), `PUT /users/:id` (admin-only).
- **Frontend context**: `apps/web/src/contexts/PermissionsContext.tsx` — `usePermissions()` exposes `granted`, `isAdmin`, `isEffectiveAdmin`, `has(key)`, `refresh()`. `useHasPermission('key')` is the convenience hook for gated UI. **`has()` uses `isEffectiveAdmin` for bypass — admins who impersonate lose their bypass**, matching the "see as user X" UX.
- **Admin guard**: `requireAdmin` middleware checks `isEffectiveAdmin(req)` (NOT just `req.adminId !== undefined`). Sidebar `visibleSettings` filter and the `SettingsUtilisateurs` page guard both use `isEffectiveAdmin` from `usePermissions()` — when Vincent impersonates someone, the Settings menu vanishes and direct URL hits redirect to `/`.
- **adminOnly submenu flag**: `SubMenuItem.adminOnly?: boolean` in `apps/web/src/config/navigation.ts`. Sidebar filters them out when `!isEffectiveAdmin`. Settings menu hides entirely when no submenus remain.

## Screen access (which menus/screens exist for a user)

A **second axis**, stored in the same per-user array as the action keys but with different defaults. Catalog + key derivation: `apps/api/src/lib/screen-keys.ts` (API side, for validation + seeding) and `apps/web/src/config/navigation.ts` (web side, derived from `mainNavigation` itself so the UI can never drift). Admin surface: the **Écrans** tab of Paramètres › Utilisateurs.

- **Two directions on purpose** — "you grant menus; inside a menu you can remove screens":
  - **menu = grant, default closed**: `screen_<menu>` (`screen_sous_traitants`). No key, no menu.
  - **screen = hide, inside a granted menu**: `hide_<menu>_<screen>` (`hide_clients_facturation`). Absent = visible.
  - Rationale: a pure allow-list would make every newly shipped screen invisible to the whole company until an admin ticked it per user — a weekly chore in this project. Granting the menu covers its future screens; a genuinely confidential new screen gets its own action key instead (`view_rapport_finance` is the precedent).
  - Keys derive from the href (`slug` = `/`→`_`, `-`→`_`), so neither manifest needs hand-maintained key strings.
- **A menu with no visible screen left disappears entirely**, same rule the Paramètres menu already followed when its only entry was admin-only. So hiding all of a menu's screens ≡ revoking the menu.
- **Granting a menu clears its screens' hide keys.** Re-granting therefore never resurrects an exclusion set months earlier, and the stored file stays free of inert keys.
- ⚠️ **Hide keys MUST be read through `hasRaw()`, never `has()`.** `has()` returns true for *every* key when the viewer is an effective admin — reading a negative key through it hides the whole app from the admin. `PermissionsContext` exposes `hasRaw` (raw set membership, no bypass) for exactly this, `GET /permissions/me` never reports hide keys for an effective admin, and `navigation.test.ts` pins the behaviour.
- **Enforcement is UI-only, deliberately**: `visibleMainNavigation` / `visibleSubmenus` for every nav surface (sidebar, header tabs, mobile) plus a single route guard in **`AppShell`** (`useScreenGuard`) — the shell is the parent of every page, so one place beats 40 route wrappers. The guard also owns the **menu index redirect** (`/clients` → the first screen the user can actually open; the router's static `<Navigate>` can't know), renders a spinner while `/permissions/me` is in flight (redirecting then would bounce everyone to `/` on a cold load), and never gates `/`, the other dashboards, or `/settings`.
- **It is a curtain, not a lock**: endpoints are shared across screens (client lookups, `/stock/ecru/suivi` feeding a dashboard widget…), so gating them per screen would break unrelated features. Confidential data stays gated by its own action key, server-side (`view_rapport_finance`, `dashboard_ca`, `dashboard_finance`, `dashboard_commandes_jour`). To make a screen genuinely unreadable, add such a key — `/api/rapports/*` and `/api/transferts/*` are the cheap candidates, being single-screen route families.
- **Grandfathering** (`apps/api/src/scripts/seed-screen-access.ts`, `--write` to persist): hands every existing user the menu keys they lack, so the day this ships nobody loses anything. Writes the `permission` table of the database `PG_CONNECTION_STRING` names — **run it on the API host for production**. Idempotent, and the intended way to hand a *newly added menu* to everyone at once. One row per person since the account merge.
- **Manifest guard**: `apps/api/src/scripts/check-screen-access.ts` diffs `screen-keys.ts` against `navigation.ts` (parsed textually — importing it would pull TSX icons into a node script). A menu/screen added to the nav but not here would be silently dropped by `PUT /permissions/users/:id`.
- **"Copier les droits de…"** (tab strip of the user detail) copies another user's whole key set — screens + actions — onto the selected user. This is the deliberate stand-in for roles/groups on a small team: nothing links the two accounts afterwards, so no shared object can drift. It also carries the onboarding load that default-closed creates, since users arrive from the WinDev `utilisateur` table with no menus.
- Unit tests: `apps/web/src/config/navigation.test.ts` (11 cases — default closed, grant/hide interaction, empty-menu collapse, admin bypass, the `view_rapport_finance` gate, index redirect).
- ⚠️ **Écrans decide what a user SEES, permissions what they can DO in what they see** (Vincent, 2026-09-25). A new screen is added to the Écrans manifests (nav + `screen-keys*.ts`) and gets **no action key** by default; a key only earns its place when several users see the same screen with different rights (or for data confidential across screens — `view_rapport_finance`). Counter-example that prompted the rule: Paramètres › Outils shipped behind an `import_compta_sage` key just so Isabelle could see it; removed the same day.
- **Paramètres is a menu of the axis** (`screen_settings`, screen `hide_settings_outils`) although the sidebar renders it apart (`settingsItem`; the web iterates `screenAccessMenus()` = `mainNavigation` + `settingsItem`). Utilisateurs stays `adminOnly` and is left out of the Écrans tree. `seed: false` on the manifest entry: the grandfathering scripts never hand Paramètres out, and the Écrans tab's « Tout » does not tick it — granted person by person. **Outils is where the curtain is also the lock**: `routes/import-sage.ts` checks `userCanOpenScreen` / `trmUserCanOpenScreen` (menu grant + no hide, admin bypass) — the same exception shape as TRM Pointage's `trmUserHasMenu`.
- **TRM has the same axis over its own tree and its own store.** Manifest `lib/screen-keys-trm.ts` (`TRM_SCREEN_MENUS`, `trmMenuAccessKey`/`trmScreenHideKey`/`isTrmScreenAccessKey`) mirrors the sibling repo's `TRM/apps/web/src/config/navigation.ts`; keys land in `data/permissions-trm.json` via `/api/permissions-trm` (catalog also exposed at `GET /permissions-trm/screens`). Guard `check-screen-access-trm.ts` (`--nav <abs path>` to diff against a TRM worktree instead of the `../TRM` sibling), grandfathering `seed-screen-access-trm.ts --write` (**run on the server**, same reasons). Some key strings coincide with ETM's (`screen_clients`, `hide_clients_facturation`) — harmless, the two stores never meet, and each `PUT` filters against its own catalog. The TRM web mirrors the whole enforcement path (`navigation.ts` helpers, `useSubmenuFilter.ts`, `AppShell` guard, its own `navigation.test.ts`).
