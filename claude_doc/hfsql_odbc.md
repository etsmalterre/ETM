# HFSQL ODBC Reference

Deep-dive reference for the HFSQL ODBC connection used by the MPS API. The *footguns* (rules you must follow) are summarised in `CLAUDE.md § HFSQL rules`; this file has the full explanation + platform-specific details.

## Connection

- **Driver**: `HFSQL` (installed from `C:\PC SOFT\WINDEV Suite 2026\Install\ODBC\WX310PACKODBC.exe`)
- **Connection string**: `DRIVER={HFSQL};Server Name=localhost;Server Port=4900;Database=MPS;UID=Admin;PWD=;`
- **npm package**: `odbc`
- **Helper**: `apps/api/src/lib/hfsql.ts` — singleton connection, `query()` wrapper, `queryRaw()` (preserves binary ArrayBuffers), `fixEncoding()`, `closeConnection()`, `getConnection()`

## Known issues

- Accented table names cause "fichier de données est déjà décrit" error — avoid accents in HFSQL table names.
- HFSQL backup folders with accented file names trigger the same error — delete backups before connecting.
- Empty memo fields return as `\x00` — cleaned automatically by `query()`.
- BigInt fields return with `n` suffix — converted to Number automatically by `query()`.
- **Encoding**: HFSQL ODBC driver corrupts accented characters (é→U+FFFD). Fix: use `fixEncoding()` which calls `CONVERT(field USING 'UTF-8')` per-row for affected fields. Returns ArrayBuffer decoded as UTF-8.
- **No parameterized queries**: `?` placeholders cause "SQLGetDescribeParam non supportée" error. Use string interpolation with `esc()` (single-quote doubling) for strings, `parseInt` for IDs. For binary blobs, use hex literals: `x'${buffer.toString('hex')}'`.
- **No `RETURNING *`**: HFSQL SQL doesn't support it. Use follow-up SELECT after INSERT/UPDATE.
- **Booleans as numbers**: HFSQL returns `0`/`1` not `true`/`false`. In React, always use `!!value &&` to avoid rendering `0` as text.
- **BinMemo `IS NOT NULL`**: Unreliable for checking if a document is attached — empty blobs pass the check. For file-serving endpoints, return 404 if the buffer is empty. For UI, use a HEAD pre-check before rendering iframes.

## Accented column names — PLATFORM-SPECIFIC SQL REQUIRED

The Linux iODBC bridge (`wd310hfo64.so`) completely **rejects any accented identifier token** in the SQL text — `sf.terminé`, `rf.recyclé`, `[terminé]`, `"terminé"`, UTF-8 bytes, Latin-1 bytes, `SELECT terminé AS x`, `UPDATE ... SET terminé = 0`, `WHERE terminé = 0` — all fail with tokenizer errors like `sf file not found in FROM statement` or `Unexpected word`. The HFSQL SQL parser on Linux simply cannot handle é/è/à/ç/etc. inside an identifier.

Meanwhile the **Windows ODBC driver** has the opposite problem: it silently returns zero rows when a JOIN uses `alias.*` expansion. So the two paths need different SQL:

- **Linux path**: `SELECT sf.*` — the bridge returns accented columns with their last char truncated (`terminé→termin`, `controlé→control`, `certif_recyclé→certif_recycl`, `recyclé→recycl`). Filter/update via non-accented fields only; any predicate or SET on an accented column must be done in JS or skipped.
- **Windows path**: list every column explicitly with `alias.terminé AS termine` style aliases — `alias.*` in a JOIN returns nothing.
- **Both paths**: post-process rows via a normaliser that maps both shapes to the same ASCII keys (`termine`/`controle`/`recycle`) so the HTTP response is platform-agnostic.
- **Source of truth**: `apps/api/src/routes/stock.ts` has the canonical pattern, branching on `process.platform === 'win32'` via an `IS_WINDOWS` constant. The route also fetches `ref_fil.recyclé` via a separate `SELECT * FROM ref_fil` call and joins it in JS, since neither platform can reference that column explicitly.
- **PATCH/UPDATE**: `UPDATE stock_fil SET terminé = …` works on Windows but not on Linux. `stock.ts`' PATCH silently skips those fields on Linux and returns a descriptive error if the user tries to set only those fields.

## Bridge (Linux only)

- **Binary blob support**: The C bridge (`hfsql_bridge`) outputs binary columns as base64 with `"b64:"` prefix. `hfsql-bridge.ts` has two decoders: `cleanRow()` decodes b64 to **UTF-8 strings** (used by `query()` for normal text/CONVERT results), while `cleanRowRaw()` decodes b64 to **raw Buffers** (used by `queryRaw()` for binary blob retrieval like PDFs). Without this split, JSON-serialized Buffers become `{type:"Buffer",data:[...]}` objects that crash React with error #31.
- **Recompile**: `gcc -o hfsql_bridge src/hfsql_bridge.c -I/usr/include/iodbc -liodbc -liodbcinst`
- **Auto-reconnect**: The bridge process holds a single ODBC connection that can die after long idle periods. `query()` and `queryRaw()` detect connection-lost errors (state `[01000]`, "Connection reset by peer", etc.), kill the bridge, and retry once — no manual restart needed.

## Per-table polymorphism / FK quirks

Per-table footguns that are NOT cross-cutting (each only applies to a specific table or polymorphic relationship). Summarised in `CLAUDE.md` as a single pointer line; the detail lives here.

### `ged` rows are polymorphic (multi-parent)

A single `ged` row can be linked to multiple parents at once — e.g. a GOTS cert is shared by the fournisseur / client / sous-traitant commandes in the same chain. The discriminator is `IDtype_doc`, **not** which `IDcommande_*` columns are zero. **Never** add an `IDcommande_<other> = 0` clause to scope a query to one parent type — that silently hides shared rows (e.g. an sst-doc whose parent commande also has a sibling client commande filled in). Whitelist by `IDtype_doc` instead. Per-screen whitelists live in the route files (`commandes-fil.ts`, `commandes-sous-traitant.ts`).

### Fournisseur ↔ coloris is `asso_colorisfil_frs`, NOT `colori_fil.IDfournisseur`

`colori_fil` is the global catalog (ref_fil, coloris-reference); one coloris can be sold by many fournisseurs via the M:N join `asso_colorisfil_frs (IDfournisseur, IDcolori_fil)`. The legacy `colori_fil.IDfournisseur` is misleading — never read or write it. Pattern in `references-fil.ts` / `fournisseurs.ts`.

### `ligne_commande_sous_traitant.IDreference` is polymorphic across 3 catalogs

Same numeric ID can exist in `ref_fini`, `ref_ecru`, or another catalog. ALWAYS route by `type` SMALLINT (alias `type_kind` — `type` is a reserved word). The line stores the **output** the sst produces, NOT the input:

| `type_kind` | `IDreference` resolves to | `IDColoris` resolves to | Inputs read separately |
|---|---|---|---|
| `2` (ennoblisseur) | `ref_fini` | `ref_fini_colori` | écru affectations on `stock_ecru.IDref_commande_affectation` |
| `1` (tricoteur) | `ref_ecru` | `colori_ecru` | yarn via `composition_ecru WHERE IDref_ecru = …` |
| `0` | `ref_ecru` | `colori_ecru` | — |

Reference `resolveRef` in `commandes-sous-traitant.ts`. Memory [[project-sst-line-polymorphic]] has the legacy commande 8582 evidence.

### `stock_fini.IDColoris` references `ref_fini_colori`, NOT `colori_fini`

`colori_fini` is a junction (`IDcolori_fini`, `IDgamme_coloris`, `IDcolori_ecru`, `IDref_fini_colori`) with NO `IDColoris` column and NO `reference` column. The actual fini-coloris catalog is `ref_fini_colori` (PK `IDref_fini_colori`, label `reference`, FK `IDref_fini`) — that's what `stock_fini.IDColoris` and `ligne_commande_sous_traitant.IDColoris` reference for fini lines.

### `stock_fil.IDref_fil_commande` is the order-LINE PK, NOT the commande N°

A yarn-stock roll links to its purchase order via `stock_fil.IDref_fil_commande`, which is the PK of the **order line** in `ref_fil_commande` — *not* the commande number. The commande N° (what the UI/legacy calls "Commande N°") is `ref_fil_commande.IDcommande_fil`, the FK to the `commande_fil` header. To show the commande number for a roll: `stock_fil.IDref_fil_commande` → `SELECT IDcommande_fil FROM ref_fil_commande WHERE IDref_fil_commande = …`. (e.g. lot 10471 → line 920 → commande 646.) Displaying `IDref_fil_commande` directly = wrong number on every roll. Resolved in `stock.ts` `GET /fil/:id`; surfaced in `FilsStock.tsx` provenance card.

### `defaut_qualite` polymorphic via `Type_Reference` + `reference`

Integer discriminator (`1`=piece_production, `2`=stock_ecru) with the parent id **stringified** in `reference` (varchar-typed FK). Écru defects: `WHERE Type_Reference = 2 AND reference IN ('id1','id2',...)`. Coexists with `stock_ecru.second_choix` + `observations` — rendered together in the red `RollNotes` banner. Pattern in `commandes-sous-traitant.ts` `fetchPiecesPayload`.

### `envoi_email.IDreference` polymorphic by `IDtype_doc`

- `13`/`15` → `commande_sous_traitant` (bon de commande / soumission lot client)
- `14` → `expedition`
- `27` → étude soumission

**Never** query without an `IDtype_doc IN (...)` whitelist — sst commande and expedition IDs collide. Sst-soumission convention: `IDtype_doc=15`, `notes=lot id`. More in `claude_doc/sous_traitants_status_model.md`.

## Footguns — full case histories (moved from `CLAUDE.md` on 2026-09-07)

> `CLAUDE.md` § HFSQL rules keeps each rule in one or two lines and points here. This section is the verbatim long form: the incident, the measurement, the canonical file, the guard script. Add the story of a new footgun HERE and the one-liner in `CLAUDE.md`.

- **No parameterized queries**: `?` placeholders fail. Use string interpolation with `esc()` (single-quote doubling) for strings, `parseInt` for IDs, hex literals `x'${buffer.toString('hex')}'` for blobs.
- **No `RETURNING *`**: use follow-up `SELECT` after INSERT/UPDATE.
- **Booleans are `0`/`1`**: in React always `!!value &&` to avoid rendering `0` as text.
- **Accented identifiers are platform-specific**: Linux bridge rejects them entirely (use `sf.*` + ASCII-truncated column names); Windows silently returns 0 rows on `alias.*` in JOINs (use explicit `alias.terminé AS termine`). Branch on `process.platform === 'win32'` via `IS_WINDOWS`. Canonical pattern in `apps/api/src/routes/stock.ts`. Truncation is **in the driver itself** (even a raw Latin-1 `0xE9` is dropped) — the "Latin-1 bridge" idea is a dead end (`project_hfsql_bridge_accent_fix`). ⚠️ **Resolve accent-mangled `SELECT *` keys with a `/^prefix/i` regex, never a hardcoded fallback list** — `pickVal` / `stripKeys` in **`apps/api/src/lib/accented-keys.ts`** (re-exported by `routes/stock.ts`, their historical address). The truncated key carries a **non-deterministic garbage trailing byte** from a reused buffer, so `terminé` arrives as `termin` / `termint` / `termini` … depending on server load: a `row.termin ?? row['terminé']` fallback reads correctly on Windows and **misses the key in production**, leaving the flag at 0 for every row — a silent wrong number, never an error. That has shipped three times (« Masquer les lots terminés » on Fils › Stock; the stock total *and* the recyclé badge of Fils › Références — **ticket #1090**, 113 of 130 references wrong and 4 showing a negative stock; the lots offered when affecting stock to a yarn order line). Read by prefix, **then** strip by prefix, **then** assign the canonical ASCII key — stripping last also deletes the answer, since `/^recycl/i` matches `recycle`. **Writing accented columns on Linux** (e.g. `asso_fil_matiere`): never name them — positional `INSERT … VALUES(...)` in column order (PK isn't auto-assigned; compute `max+1`), edit/delete via delete-by-ASCII-key + reinsert. Canonical: `references-fil.ts` composition (`project_matiere_premiere_unreachable_pk`). When the table has an **ASCII PK** but accented data columns (`dossier_qualite`), the cheaper shape is a **full-row positional rewrite keyed on the PK**: split writes so ASCII columns take a normal named `UPDATE` and only a change to an accented column triggers read-`queryB64Text` → `DELETE … WHERE <ascii PK>` → positional `INSERT` (same PK, so child FKs survive), with a best-effort restore on failure. Canonical: `dossiers-qualite.ts` `patchAccented()`; round-trip guard `apps/api/src/scripts/test-dq-positional-rewrite.ts`. Reading accented-NAMED columns (`prénom`/`société`): bridge `queryB64Text()` (base64-text → Latin-1); `project_hfsql_accented_column_b64text`.
- **A query naming a non-existent column = prod outage on Linux**: silently caught on Windows ODBC, but on the bridge it triggers a respawn storm that floods the shared HFSQL server (`mps.malterre`=`10.10.20.2`, shared with mfprod) and hangs both apps. Any helper building `WHERE <col>=<id>` from a row property MUST use the target table's real PK. **`WHERE col = NaN` storms identically**: `fixEncoding`/`repairAliased`'s `idField` MUST be selected by the feeding query — `SELECT nom FROM x` + `fixEncoding(…,'IDx',['nom'])` reads `undefined`→`NaN` (helpers now skip non-integer ids as backstop; `project_fixencoding_nan_storm`). Verify prod via `https://etm.intra.etsmalterre.com` (NOT `localhost:8081` — IPv6 false 000s); don't hammer-restart. Naming an accented column in SQL storms the same way — never name `invalidé`/`société`/etc.; `SELECT *` + prune in JS. `isConnectionLostError` now excludes SQL errors so bad columns throw, not storm. Memories: `project_hfsql_bridge_storm`, `feedback_prod_health_check`.
  - ⚠️ **The same missing `idField` also corrupts accents, silently** (#1137, #1145, #1146 — 2026-09-10). With the id absent, the NaN backstop skips the CONVERT and the value keeps its U+FFFD glyph. On screen that is a cosmetic `�`; but `sqlText()` maps U+FFFD (> 0xFF) to `?`, so any handler that READS a value this way and WRITES it back stores a literal `?` — the études coloris acceptance did exactly that (`SELECT libelle, IDref_fini … FROM etude_col` + `fixEncoding(…, 'IDetude_col', …)`): « 3006 rose poudré 63842/2 » became « 3006 rose poudr? 63842/2 » in BOTH the étude and the freshly created `ref_fini_colori`. The PDF/email builders that read `SELECT prenom, nom FROM utilisateur`, `SELECT libelle FROM mode_paiement / echeance`, `SELECT designation_interne, designation_externe FROM teinture`, `SELECT reference FROM ref_fini` had the same shape — hence « é » printing as « ? » on BL / commandes / études (#1145). 28 call sites fixed by selecting the id column; both `fixEncoding` implementations now `console.warn` when `row[idField]` is undefined; static guard `node --import tsx src/scripts/check-fixencoding-idfield.ts` (exit 1 on a miss). Verified on the local server that `x'e9'` round-trips on INSERT and UPDATE alike — hex literals were never the culprit. Prod rows `ref_fini_colori` 5303/5304 and `etude_col` 1386 repaired by hand the same day.
- **Encoding (reads)**: ODBC corrupts accents (é→U+FFFD). Use `fixEncoding()` / `CONVERT(field USING 'UTF-8')` per affected field. **On large lists, batch the repair** — one `CONVERT … WHERE id IN (…)` per source column, not per row (per-row CONVERT is an N+1 that floods the bridge). Batched pattern in `stock-fini.ts repairAliased`.
- **Encoding (writes)**: raw multi-byte UTF-8 in a SQL string corrupts the Linux bridge (→ `[HY090]` / "string without end" / 500). HFSQL text columns are Latin-1 — emit accented values as a hex literal of their Latin-1 bytes (`x'${Buffer.from(v,'latin1').toString('hex')}'`), not `'${esc(v)}'`; ASCII values keep the normal quoted literal. Helper: `sqlText()` in `commandes-sous-traitant.ts`. ⚠️ **The helper is lossy above Latin-1 by design** — em-dash → `-`, curly quotes → `'`/`"`, `…` → `...`, NBSP → space, anything else → `?`. Accents round-trip verbatim, typography does not: a test that asserts a byte-identical round trip on a string containing an em-dash reports a false failure (happened writing `check-retour-client-trm.ts`). Assert on Latin-1-only text, or on the transliterated expectation.
  - ⚠️ **A user-typed search term is a write into a SQL string too — `LIKE '%${esc(q)}%'` with an accented `q` is the same bridge hazard.** A hex literal is not an option inside a `LIKE` pattern, so the answer is to map every non-ASCII character to the single-char wildcard `_` (`likePattern()` in `routes/transferts.ts`): nothing but ASCII reaches the server, and the pattern becomes accent-insensitive in the direction users need — `ecru` and `écru` both match `%_cru%`, which matters because coloris values carry accents inconsistently. It widens the match (`%_cru%` also matches `ancru`), so the **client re-applies the exact, accent-folded test** on the rows that come back; the widening never reaches the user. ⚠️ `stock-ecru.ts`, `stock-fini.ts` and `stock.ts` still interpolate `esc(q)` raw into their list-search `LIKE` — a latent bridge hazard the day someone types an accent into a stock toolbar. Port `likePattern` there when you next touch them.
- **BinMemo `IS NOT NULL`**: unreliable — empty blobs pass. File-serving endpoints return 404 if buffer is empty; UI does HEAD pre-check before rendering iframes.
- **Windows driver + memo-binary columns = 0 rows**: any `SELECT` that names a blob column (`certif_bio`, `certif_recyclé`, `CleComp`…), or `SELECT *` on a table holding one (`stock_fil`, `client`), silently returns **zero rows** on Windows ODBC (`query` *and* `queryRaw`). Probe presence with `LENGTH(col)` there; the Linux bridge takes `SELECT *`. **MEMO text columns cost per row**: over 1.7k `stock_fil` rows the two memos (`commentaire`, `observation_freinte`) are ~0.9 s of a 1.4 s select — select them only for the rows you will return (chunked `IN` lists), never in a full-table list. Canonical: `routes/stock-fil-trm.ts` `fetchBaseRows`.
  - ⚠️ **Not universal — `bonnetier.photo` reads fine on Windows** (`SELECT photo FROM bonnetier WHERE IDbonnetier = <id>` returns the JPEG, measured 2026-08-24), so the 0-rows behaviour is per-table, not a blanket ban. Probe the specific column before assuming either way, and keep the single-row/`WHERE`-scoped shape — the failures above were all wide or full-table selects.
- ⚠️ **When a binary read DOES work, it needs `queryRaw`, never `query`**: `query()` pipes every row through `cleanRow`, which decodes any `ArrayBuffer` as UTF-8 — the JPEG/PDF comes back as a mangled string that looks like data but isn't. Use `queryRaw()` (both platforms export it via `hfsql-auto`), `Buffer.from(...)`, then verify the magic bytes and 404 on anything else (empty memo, bridge text-mangling). Canonical: `prime-trm.ts` `/bonnetiers/:id/photo`. Stored images are full-size originals with EXIF rotation — resize server-side with `sharp` (`.rotate()` first) and cache, rather than shipping 300 KB per avatar.
- **Avoid accents in HFSQL table names and backup folder file names** — both cause "fichier de données est déjà décrit" errors at connection time.
- **JOIN + `CONVERT()` collapses result sets**: `SELECT a.col, CONVERT(b.text USING 'UTF-8') FROM a JOIN b WHERE …` returns **one row** instead of all matches. Split into two flat queries and merge in JS. Same shape kills `CONVERT(tel)` even single-table when `tel` is empty on some rows — read phone-like cols raw. Reference: `commandes-sous-traitant.ts` `/lookups/sous-traitants`.
- ⚠️ **The `.xdd` column order is NOT what a positional INSERT needs — trust the runtime `SELECT *` and nothing else.** The analysis listing and the driver disagree on some tables, and the mismatch fails **silently**: `piece_production` comes back as `IDpiece_production, IDordre_fabrication, bonnetier_debut, bonnetier_controle, bonnetier_fin, date_debut, date_controle, date_fin, observations, poids, visiteur, date_visitage, bonnetier_interruption, date_interruption, numero`, while the `.xdd` puts `numero` third and groups the dates — so a positional INSERT built from the `.xdd` writes the piece number into `bonnetier_debut` and a date into `date_controle`, on live production rows, with no error anywhere. Same trap already recorded for `controle_titrage` and `retour_client`. Two rules follow: **only reach for a positional INSERT when a reserved word or an accent actually forces it** (`piece_production` has neither, so `routes/atelier.ts` inserts it with a named column list), and **probe the runtime order before writing one** — `scripts/probe-atelier-trm.ts` §1 prints it for the three tables the atelier writes.
- **Reserved-word columns return uppercased**: `SELECT lcs.type FROM ligne_commande_sous_traitant lcs` returns the column key as `TYPE`, not `type`; likewise `date` comes back as `DATE` (seen on `prospect`). Always alias (`lcs.type AS type_kind`) or read case-insensitively. Affected anywhere a reserved-word column exists.
- **`commande_sous_traitant`: `commentaire` is RTF, `journal` is plain text**: `commentaire` round-trips via `stripRtf()`/`wrapRtf()` (legacy still reads it); `journal` writes via `sqlText()` (RTF rows migrated to plain text 2026-05-26, reads keep `stripRtf()` defensively). The app surfaces `journal` where legacy wrongly bound the "journal" UI to per-line `lcsst.commentaire`.
- **Empty FK columns store `0`, not `NULL`**: HFSQL keeps integer FK columns at `0` when there's no foreign key (not NULL). Predicates like `WHERE IDligne_expedition IS NULL` silently match zero rows. Use `(col IS NULL OR col = 0)`. Bit the `stock-fini.ts` default filter; same shape on `IDligne_commande_client`, `IDcommande_donation`, `IDProprietaire`, etc.
- ⚠️ **"A roll is shipped" is TWO facts, and un-shipping must undo both.** `stock_fini.IDligne_expedition > 0` (on a shipment slip) *and* `IDetat_stock_fini = 4` ("Expédié"), the latter stamped by the legacy WinDev expedition routine on virtually every shipped roll — **42 944 of the 43 391** rolls sitting on a shipment line in the dev copy. Every "is it still in stock" predicate in the app tests both (`stock-fini.ts` list filter, `commandes-client.ts` available-rolls pool, the `expedie` flag on a line's rolls), so clearing only the expedition line drops a roll into a hole with **no screen at all**: gone from Clients › Gestion › Marchandise (its INNER JOIN needs the expedition line), still hidden from Finis › Stock (état 4), and out of every order's free pool. That was ticket #1086 — three returned pieces « n'apparaissent dans aucun stock ». A return must clear `IDligne_expedition` → 0, demote `IDetat_stock_fini` 4 → 3 ("Validé", where the roll sat before shipping — and *only* when it is 4, so another état is the warehouse's own classification), and release `IDligne_commande_client` → 0, without which the roll can never be offered to another line and nothing in the UI can unlink it. Releasing it makes the original order read as under-delivered again, which is correct: the goods came back. Note the écru side gives no fallback — `stock-ecru.ts` excludes any écru that has a `stock_fini` child. Canonical: `clients.ts` `POST /:id/marchandise/retour-stock`; guard `check-retour-marchandise.ts` (audit + `--repair` for rolls returned before the fix + `--roundtrip`).
- **`IDsociete` partitioning**: shared tables (`client`, `commande_client`, `facture`/`facture_prov` [confirmed], `devis` — verify per table) are partitioned across the 3 companies via `IDsociete` (1=ETM, 2=TRM, 3=Confection). Legacy filters on it — `IDsociete = 0` rows are **invisible** in the legacy app. Every ETM INSERT must set it (= 1 for ETM; TRM-view writes set 2). Memory: `project_societe_multi_company.md`. **`stock_fil` is NOT partitioned** (no `IDsociete`): the yarn sits at TRM and `IDclient` names its owner — ETM's Fils › Stock and TRM's (`routes/stock-fil-trm.ts`) read the same rows, different flavors.
  - **Two shapes for serving a partitioned table — pick by whether the halves are the same object.** Different objects → two route files (`stock_ecru`, see its bullet below). Same object, same lifecycle, same screen → **one router factory mounted twice** (`createFacturesRouter(scope)` in `factures.ts` → `/api/factures` + `/api/factures-trm`), with every société-dependent value in a single `FacturesScope` record. Never fork the file in that case; never add a `?societe=` param in the other. Second instance of the same shape: **`lib/finance-common.ts`** — `createFinanceRouter(scope)`, mounted on `rapportsRouter` at `/` (so ETM's `/api/rapports/finance`, `/ca-clients`, `/ca-evolution`, `/ca-mensuel` keep their URLs) and at **`/api/rapports-trm`** for the sister app's four finance widgets. Its `FinanceScope` also carries **which permission store answers** (`userHasPermission` vs `trmUserHasPermission`), because the two apps' grants live in separate files — copy that when a future factory spans both apps. `editComptesKey: ''` makes a mount read-only by not registering the compte write routes at all, which 404s rather than 403s — the honest answer for a screen that does not exist. (TRM used that until its Rapports › Finance screen landed on 2026-08-25; landing it was two edits to `FINANCE_SCOPE_TRM` and none to the handlers, which is the shape working as intended.) ⚠️ **A factory reached by an `:id` from the URL must check that row's partition in every handler**: `releve_compta` has no `id_societe`, so `/finance/comptes/:id/historique` was cross-readable the moment a second scope mounted it — free while one mount existed, a leak the day it did not. The PATCH had the check; the GET did not. ⚠️ **Typing gotcha for any scope record that holds a permission checker**: `userHasPermission` / `trmUserHasPermission` are typed on their own key *union*, so an arrow-typed `hasPermission: (…, key: string) => …` field rejects both under `strictFunctionTypes`. Declare it as a **method** (`hasPermission(…): Promise<boolean>` — methods are bivariant) and keep the typo protection with `satisfies PermissionKey` / `satisfies TrmPermissionKey` on each scope literal, which checks every key name against the *right* catalog. Casting the function instead silently drops that check.
  - ⚠️ **A per-société router MUST scope-check every id-addressed route.** PKs are ONE sequence shared by all sociétés, so an ETM id is a valid-looking id in TRM's URL space: `GET /api/factures-trm/def/<etm id>` returned ETM's invoice, and a `PUT` would have rewritten it with TRM reference data. Harmless while one router exists, a live cross-ledger hole the moment a second is mounted. Guard with an `inScope(scope, kind, id)` helper on GET/PUT/DELETE/lines/pdf/email/historique and **404** (not 403 — the other ledger's existence isn't ours to disclose). Canonical: `factures.ts`.

- ⚠️ **The mirror is one-way: a TRM `commande_client` with `IDcommande_ETM > 0` is READ-ONLY from the TRM side.** ETM owns its header and lines and syncs them down; there is no reverse sync, so a TRM-side write silently diverges from the sst that owns it. 93 % of the TRM ledger is mirrors, so this is the common case, not the edge case — every write path in `commandes-trm.ts` gates on `refuseIfMirror` (409 `commande_miroir_etm`) and only native orders (`IDcommande_ETM = 0`) are editable. Same rule in the UI: no Modifier, no line editing. **The one exception is the état** (LIVA #1100, decided with the atelier on 2026-09-02): a mirror's `est_soldee` is TRM's own — « the knitting for this order is done » — so `PUT /commandes-trm/:id/etat` accepts a mirror, but solders it only once **every OF of its lines is `est_termine = 1` and every roll (`stock_ecru.IDLigne_Commande_TRM`, no IDsociete filter) has `IDligne_expedition_TRM > 0`** (409 `commande_non_terminee` with the two counts; `checkCloture()`, also returned as `cloture` on the detail so the screen names what blocks). Reopening is free. **It never closes the sst**: the sst's `computePhase` reads the mirror's `est_soldee` and shows **`trm_soldee` « Soldée par TRM »** (priority right after `terminee`, teal pill, search keyword « soldee »), and the ETM user clôtures their own order after checking reception and deadlines — two companies each closing their own ledger, nothing writes the other side's flag. Before that, a mirror could not be soldée from anywhere (ETM's clôture only writes `commande_sous_traitant`, and the header sync deliberately leaves `est_soldee` alone), so every sst clôturé since go-live left its mirror « En cours »: `scripts/probe-cloture-miroir-trm.ts` counts those and says which TRM can now close in one click. **The second exception is the délai** (LIVA #1123, 2026-09-07): the knitting date is TRM's answer to « Attente délai », so `PUT /commandes-trm/lignes/:id/delai` accepts a mirror and writes **both ledgers** — `ligne_commande_client.date_livraison` and, through `IDligne_commande_ETM`, `ligne_commande_sous_traitant.date_livraison` with the same capture-once `date_delai` + `Attente_Delai → En_Cours` rules as this route family's own `PUT /lignes/:id` (`sstDelaiSets` in `lib/sst-shared.ts`, the one place both call). Its own route, not a hole in `refuseIfMirror`. Guard: `scripts/check-commandes-trm-delai.ts` (writes, localhost only, restores).
- **`commande_client` has TWO route families like `stock_ecru` — same "don't unify" rule.** `commandes-client.ts` (`/api/commandes-client`, `IDsociete = 1 AND IDcommande_ETM = 0`) serves ETM; `commandes-trm.ts` (`/api/commandes-trm`, `IDsociete = 2`) serves TRM's screen. Each router keeps its own `/lookups/modes-paiement`+`/echeances` copies — that duplication is the existing convention (`commandes-client.ts` does it too), not drift.
- ⚠️ **`pricing-trm.ts` carries TWO retained-price rules, and `ref_ecru.prix` means something different in each.** `prixDeRevientTRMDetail(ref, qty, baseRole)` takes a `TrmBaseRole`: **`'price-floor'` (the default)** = `max(cost / 0.7, base)` — the base is a floor on the *sale* price and is retained **flat** when it wins; **`'cost-floor'`** = `max(cost, base) / 0.7` — the base is a floor on the *cost*, so the winning assiette carries the 30 %. `trmLinePrix` stays on the default because it prices the **ETM → TRM sous-traitance lines**, which must keep matching the WinDev app that still writes them (verified 15/15 on recent mirrors — ref 4 @500 kg is stored at 2,07 €, the bare base). Only `/commandes-trm/lookups/line-price` passes `'cost-floor'` (user decision, 2026-08-26). **Do not unify them**: the two differ by ~+39 % in value, so flipping the default silently reprices the intercompany transfer. Pinned by `pricing-trm.test.ts`.
