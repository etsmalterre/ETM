## Tickets widget (header, LIVA issue tracker)

LIVA issue tracker via server-side proxy `apps/api/src/routes/tickets.ts` — one router factory mounted twice, factures.ts-style: `/api/tickets/*` (product `etm-erp`, this app) and `/api/tickets-trm/*` (product `trm-erp`, the sister TRM app's widget). Env `ISSUE_TRACKER_URL/_API_KEY/_PRODUCT_SLUG/_PRODUCT_SLUG_TRM` — required in prod env too; widget `apps/web/src/components/tickets/` + header trigger, screenshot via lazy `html-to-image`. **Widget feature version 1.3.0** (spec + upgrade path: `issue_tracker_integration` skill) — "Mes tickets" collapses closed tickets into a drawer, and the header trigger carries a red unread badge computed from `localStorage` signatures per user (`useTicketNotifications.ts`, **no DB change**). Two scoping rules: `resolu` counts as **open** (fixed but its release hasn't shipped — the tracker flips it to `ferme` on publish, and only then does it belong in the drawer), and every read is pinned to `product_slug` because the tracker API key is *company*-scoped (without it a reporter using the same email in MFProd sees MFProd tickets here). v1.2.0 adds the **follow-up opt-in**: a checkbox on the form (unticked by default) and a §35 toggle in the ticket detail set the tracker’s `bugs.follow_up`, and the tracker then emails the reporter on every **status change** of that ticket — proxy route `PATCH /:id/follow` (owner-checked like detail/attachments), guard script `src/scripts/check-tickets-follow.ts`. Needs a tracker at least at the `follow_up` migration, or the toggle 404s. v1.3.0: **an account without a mapped email still reports** — the proxy files it under a stable synthetic identity `utilisateur-<id>@mps.malterre.invalid` (`lib/tickets-reporter.ts`; the tracker keys reporters by email but only *sends* to it for follow-up), forces `follow_up` off, refuses `PATCH /:id/follow`, and `GET /reporter` → `{ name, can_follow }` lets the widget hide the follow-up controls. Until then those accounts got a 400 — that was the visitage compte-poste and Mickael Grivelet. A shared station may send `reporter_name` (who is at the keyboard), honoured only for a synthetic reporter and appended to the account name. ⚠️ Mapping an email later moves the account to a new tracker identity (earlier tickets leave « Mes tickets ») — accepted


## 2. Prospects

**Prospects** (renamed from legacy "Marketing") — **Demandes** (`/prospects/demandes`; catalogue requests from the `prospect` table; master-detail, implemented)

    **Prospects › Demandes — devis prospect** (LIVA #1112, ports legacy `FEN_devis_prospect.wdw`): « Créer un devis » (header button + Devis sidebar tab) creates a `devis_etm` row with **`IDprospect > 0` and `IDclient = 0`**, prefilled from the demande, and jumps to **Clients › Devis** (`?devis=<id>` deep link) — the devis editor is NOT forked; the shared screen serves both populations with a violet « Prospect » chip. Legacy conventions kept for WinDev compatibility: both address FKs pinned to **adresse 795 « A Définir »** (the detail/PDF/email override the display with the prospect's own fields), `IDmode_paiement = 3`, `IDecheance = 11`, expiration = date + 1 mois, and the **numero sequence is shared** with client devis. A prospect devis can NEVER become a commande (`/convert` 400s) — **converting the prospect to a client re-homes its OPEN devis** (`IDclient` set, `IDprospect` cleared, addresses moved onto the new client's default adresse), after which they transform normally; soldé devis stay on the prospect as history. **Two permission keys, category « Prospects », both default-closed (no seed — user decision 2026-09-02)**: `edit_prospects` gates every write of `routes/prospects.ts` (create/edit/delete/statut/convert — the router was fully ungated before), `devis_prospect` gates prospect-devis writes in `routes/devis.ts` (create/edit/lignes/état/delete/email/documents; client-devis writes stay ungated as before, and reads + PDF stay open to all). Guard: `check-devis-prospect.ts` (`--roundtrip`) — pins the 17 legacy rows, the 795 placeholder, and the PDF element-tree carrying the prospect's name/address.
## 3. Clients

**Clients** — Commandes, Devis, Facturation, Gestion

    **Clients › Gestion — compte client** (`client.compte`, the chart-of-accounts code): mandatory and format-checked. "+ Nouveau" opens a **création dialog** (nom / secteur / activité) rather than inserting a `Nouveau client` placeholder — knowing the name before the INSERT is what lets the code be derived from it. Generation lives in `apps/api/src/lib/compte-client.ts` (`pickCompte`), mirrored client-side by `apps/web/src/lib/compte-client.ts` for live validation; guard `apps/api/src/scripts/check-compte-client.ts` replays it over all 654 clients. **Generation emits `411` + 3 alphanumerics, validation accepts `411` + 3-or-more** — the legacy table holds 388 four-char codes that must stay editable (225 are three-char, 36 are other shapes). Mnemonic candidates come from the name's significant words, skipping legal forms (SARL/SAS/SOCIETE…) and industry-generic words (BONNETERIE/TRANSPORTS/ATELIER…) exactly as the accountant did — "Bonneterie Gautier" → `411GAU`; collisions fall through consonant squeezes then numeric variants (`411SO2`), with an exhaustive base-36 sweep as the guaranteed last resort. Uniqueness is **not** scoped by `IDsociete` (the code identifies the company in the ledger) and is enforced **only on values that change** — 10 duplicate codes already exist in legacy data and must stay saveable. The duplicate check runs **live as the user types**, on both the dialog and the Info tab: `GET /clients/comptes` returns every code in use and `useComptesPris()` caches it under one query key (React Query dedupes, so the InfoTab call costs nothing extra), which greys out Créer / Enregistrer instead of ambushing the user after the click. Server-side re-validation on POST/PUT stays the authority — the cached set can go stale if someone else creates a client meanwhile. Entering edit mode on a client whose compte is empty or malformed auto-fills a suggestion (snapshot updated too, so the pre-fill alone isn't "dirty"); an invalid value blocks the save and the exit via `useUnsavedGuard`'s `shouldBlockExit` (`mps_designer §28.5b`). Only the `edit_client_info` scope writes the column, so validation is gated on that permission — a user who cannot edit it is never blocked by it.
    **Clients › Gestion — SIREN** (`client.siren`, ticket #1088): 9 chiffres, dans la carte Facturation sous le N° TVA. **Facultatif** — la colonne se remplit client par client, donc seule une valeur non vide est contrôlée (sinon 400 `siren_invalide` + exit bloqué via le même `infoIssue` que le compte). ⚠️ **La clé de Luhn est un AVERTISSEMENT, jamais un refus** : le registre a porté des identifiants qui ne la vérifient pas, et bloquer une saisie légitime coûte plus cher que la faute de frappe qu'on attrape. **Colonne détenue par la fiche ETM seule** — `clients-trm.ts` ne la nomme pas (invariant ci-dessous), l'ajouter côté TRM demandera de la nommer là-bas. **Elle s'imprime sur la facture, l'avoir et le proforma** (LIVA #1130, 2026-09-07) : ligne « SIREN · 123 456 789 » en tête de la carte des conditions, avant le N° TVA, **lue sur `client` au moment du rendu et jamais recopiée sur `facture`** — un SIREN identifie l'entité pour toute sa vie, un autre SIREN serait un autre client, donc il n'y a pas de valeur « à l'émission » à figer comme pour le `num_tva` ; un client sans SIREN n'a simplement pas la ligne. Les deux bâtisseurs (`buildFacturePdfData` dans `factures.ts`, les deux montages ETM/TRM, et `buildProformaPdfData` dans `commandes-client.ts`) passent par `formatSirenForDocument` / `loadClientSirenForDocument` de `lib/siren.ts`. La facturation électronique proprement dite reste à faire. Helpers `lib/siren.ts` (API + miroir web), garde `check-siren.ts` (`--roundtrip`, + section arbre d'éléments du PDF).
    **TVA — the rate belongs to the CLIENT, never to the société.** Every customer-facing document takes it from `client.IDtva` → `tva.valeur` via `apps/api/src/lib/tva.ts` (`loadClientTvaRate`, falling back to the société-1 `est_defaut` row **only** when the client has no row). Each société has an "Exonération" row at `valeur = 0` used for export customers (Maroc, hors UE): a 0 rate is a real value, not "unset", so it must never fall through to the default. A 0 rate also **collapses the totals block** — no TVA line, no TTC line, the document ends on `TOTAL HT` (the sub-total row survives only when a remise or frais de port makes it differ). Applies to the confirmation de commande, the devis, the proforma and the facture; a `facture` additionally **stores its own `IDtva`** copied from the client at creation, so an old invoice keeps the rate it was issued with. Guard: `check-tva-exoneration.ts`.
    **Clients › Gestion — the `client` table has TWO ledgers.** `client` is partitioned by `IDsociete` (1 ETM / 2 Tricotage Malterre / 3 Confection), so this API serves two fiches: `routes/clients.ts` (`/api/clients`, ETM) and `routes/clients-trm.ts` (`/api/clients-trm`, consumed by the TRM app — its screen lives in the sibling repo and is deliberately NOT an `@etm` shared screen: the two fiches show different fields). Shared plumbing lives in **`lib/clients-common.ts`** — SQL/format helpers, `requirePermission`, `repairNames`, `countClientActivity`, the accented-flag helpers `setClientFlag`/`readClientFlag` (`archivé` + `bloqué`, delete + positional reinsert on Linux), and `registerContactAdresseRoutes()` (`contact`/`adresse` are polymorphic on `IDclient` and NOT partitioned, so both mounts register them verbatim). **The invariant that keeps the two fiches from wrecking each other: a router must never NAME a column the other fiche owns** — an unnamed column keeps its stored value on `UPDATE`, a named one is zeroed on every save. ETM owns `client_interne` / `IDsecteur_activite` / `IDactivite` / `journal_commercial` / `dernier_contact` / `inclureRapportQualite` / `pct_ajeol`; TRM owns `rib` / `domiciliation` / `IDtransporteur` / `bloqué` (its « Attente paiement facture » checkbox). **`tva` and `code_comptable` are partitioned too** — serving ETM's rows to a TRM screen would silently rewrite a client's VAT to another company's row on the next save. Full detail: `claude_doc/implemented_screens.md` § Clients TRM.
    **Clients › Commandes — le prix d'une ligne écru/fini dépend du CLIENT, jamais du seul catalogue.** `lib/tarif-client.ts` (extrait de `routes/clients.ts`, partagé avec la fiche client) résout le mode tarifaire de la paire (référence × coloris) via `designation_client` → `ref_client_colori`, et `calcLignePriceClient` en tient compte : **contrat actif** → le `prix_saisi` négocié (€/Ml, converti en €/Kg par le rendement pour une ligne Kg) et un nudge Tricobot restreint aux tranches que ce contrat cote ; **coefficient fixe** → la marge du client à la place de la dégressive ; **standard** sinon. ⚠️ **Un contrat expiré ne retombe PAS sur la grille standard** — la référence n'est plus vendable tant qu'un nouveau contrat n'est pas établi (même règle que la fiche client) : l'endpoint renvoie `blocked` + `blocked_reason` dès le choix du coloris, le dialogue affiche le bandeau rouge et grise Enregistrer, et POST/PUT `/lignes` répondent **409 `contrat_expire`**. Le PUT ne bloque que sur un changement **commercial** (référence, coloris, quantité, prix) : une ligne prise quand le contrat était valide reste modifiable pour sa date et son commentaire. Bug d'origine (30/07/2026) : l'auto-pricer ne recevait pas le client, donc une commande C2TEC est passée un mois après l'expiration du contrat #475, sans rien à l'écran — et un client sous contrat actif était coté 12,00 €/Ml au lieu de 3,81 €/Ml négociés. Garde : `apps/api/src/scripts/check-contrat-tarif-ligne.ts` (épingle le cas C2TEC + rejoue tous les contrats actifs et coefficients de la base).

    **Clients › Gestion / Commandes — un contrat sur un tombé de métier est en €/Kg, jamais converti par le rendement** (LIVA #1144, 2026-09-10). Le tombé de métier se vend **toujours au Kg** (Vincent) ; la règle « `prix_saisi` négocié en €/Ml, converti en €/Kg par le rendement » de #1068 venait d'un cas fini (C2TEC) et s'appliquait aussi aux lignes écru : le contrat 479 de Gant Maille sur la réf 254 (1 rouleau à 10,01, désignation en Kg, rendement 2,82) était proposé à 28,23 €/Kg sur la commande n° 3869, qu'Isabelle a corrigée à la main. Mesure sur la base : 8 contrats écru en Kg, 8 fois les lignes au `prix_saisi` tel quel ; 165 contrats fini sur 192 aux lignes au `prix_saisi` en Ml. Correctif : `contratPriceFn` prend le `kind` de la référence (`'ecru'` → €/Kg, `'fini'` → €/Ml, l'autre unité convertie par le rendement) ; le chemin écru du pricer passe par le nouveau `calcTarifRefEcru` (`lib/pricing-fini-tarif.ts`, réduction nType_Ref = 1 : fil + tricotage, `qte_kg` sur chaque tranche, `kind` sur le résultat). **Deuxième défaut du ticket : la fiche client refusait l'onglet Tarifs et le clic coloris dès que `IDref_fini = 0`** (« réservé aux références ennoblies ») alors que 9 contrats écru existent en base — Isabelle ne pouvait ni voir ni renouveler le contrat. `GET /clients/:id/coloris/:rccId/tarif` répond désormais pour une désignation tombé de métier via `calcTarifRefEcru` et porte `prix_unit` (`'Kg'`/`'Ml'`) ; `TarifDialog` affiche Qté/Prix dans cette unité (pas de section Traitement, ligne Ml seulement si rendement) et `TarifModeDialog` libelle les prix négociés en €/Kg (`prixUnit` sur la cible, `prixUnitOf(ref)`). Le sélecteur d'impression des tarifs (`TarifsSelectionDialog`) reste fini seulement — le PDF n'a pas de rendu écru. Garde : `check-contrat-tarif-ligne.ts` §4bis (Gant Maille : 320 kg → 10,01 €/Kg) et le balayage §5 rejoue aussi les paires écru en Kg ; sondes en lecture seule `probe-1144-gant-maille.ts` (ligne, contrat, commandes — se lance aussi sur l'hôte API prod avec `--env-file=.env`) et `probe-1144-contrat-units.ts` (unité des `prix_saisi` vs lignes). ⚠️ En base locale (laptop), la colonne `client.siren` manquait (ajoutée le 2026-09-10 par `ALTER TABLE client ADD siren VARCHAR(20)`, APIs arrêtées d'abord : « fichier en cours d'utilisation ») — sans elle `GET /clients/:id` répond 500 et la fiche reste vide.

    **Clients › Commandes — le sélecteur de coloris est limité au catalogue du client.** `/lookups/colori-ecru|colori-fini` acceptent `client` (+ `current`) et ne proposent alors que les coloris enregistrés en Gestion pour cette (client × référence) via `ref_client_colori` — une référence teinte pour des dizaines de clients offrait sinon **389 coloris là où le client en achète 71**. Trois états, et les deux derniers **retombent sur la liste complète** (jamais de sélecteur vide, qui rendrait la référence non commandable), chaque ligne portant alors `hors_catalogue: true` pour que l'UI le dise : catalogue exploitable → liste restreinte ; aucun `ref_client_colori` (13 des 2 025 entrées fini actives) → repli ; **catalogue disjoint de la liste affichée** → repli aussi (cas réel client 202 / ref 1426 : les rcc pointent des `colori_ecru` d'un `ref_ecru` que le fini ne référence plus). `current` (le coloris d'une ligne existante) est toujours conservé et marqué — **381 des 7 062 lignes historiques sont hors catalogue** et perdraient sinon leur coloris à l'ouverture du dialogue. ⚠️ **Sans `client` la liste reste complète** : c'est ce dont Clients › Gestion a besoin, puisque c'est l'écran où le catalogue se construit. Garde : `apps/api/src/scripts/check-coloris-client-scope.ts`. Le même angle mort existe encore sur **Devis** (`/devis/lookups/colori-*`).

    **Clients › Commandes — lancer une commande ennoblisseur depuis la ligne : le lien à la commande client se choisit ROULEAU PAR ROULEAU** (LIVA #1115, port de `FEN_Ennoblir` : sa colonne « Lien » `lien_fermé.png` / `lien_cassé.png` et sa paire Tous / Aucun). Dans le dialogue « Nouvelle commande — <ennoblisseur> », chaque rouleau sélectionné porte une icône lien, **liée par défaut** (comme le `BTN_Suivant` legacy), et une bande « Réservés à la commande de <client> » compte `n / m` avec « Lier tout · Aucun » ; la jauge du pied ne compte que les rouleaux liés. Cas d'usage : « on me commande 1 rouleau, j'en lance 3 pour avoir du stock » — 147 lignes ennoblisseur de la base sont ainsi mixtes (liées + libres). Côté API, `POST …/supply/ennoblissement/orders` prend `linkStockEcruIds` (sous-ensemble de `stockEcruIds`, omis = tout lier, l'ancien comportement) ; un rouleau non lié reste affecté à la ligne teinture avec `IDligne_commande_client = 0`, apparaît en « disponible » sur l'onglet Ennoblissement et se lie plus tard par « Affecter le stock ». Un rouleau `reserved_elsewhere` n'a pas d'icône : il garde sa réservation quoi qu'il arrive. L'en-tête `commande_sous_traitant` reçoit désormais `IDcommande_client` / `IDligne_commande_client` comme le legacy (3 830 des 4 812 commandes ennoblisseur les portent ; rien dans ETM ne les lit, l'écran WinDev si). Mesures : `scripts/probe-1115-lien.ts`.
    **Clients › Commandes — lignes divers** (`ligne_commande_client.TYPE = 3`) price off the **`tarif_divers` grid**, never the roll-tranche tariff of écru/fini: the shared resolver `GET /expeditions/divers/lookups/prix?ref&v1&v2` (exact combo → `(v1,0)` → `(0,0)` → `ref_divers.prix_unitaire`), the same one the Expéditions article dialog uses. Two data facts drive the UX: a **two-axis reference has no `(0,0)` row** ("Tissu Voltige" = 533 cells keyed couleur × taille), so the price is legitimately undefined until *both* axes are picked — an empty field mid-form is not a bug; and ~417 of 1 836 existing divers lines point at refs with **no grid entry at all**, so manual entry must stay open — this field carries **no padlock and no `deverrouiller_tarifs` gate**, unlike écru/fini. A saved line keeps its own `prix` as an order-time snapshot (replaying the grid over legacy lines reproduces 1 346 exactly and differs on 59 that pre-date a price change) — never re-derive an existing line's price; only a stored `0` gets refilled.
    **Clients › Commandes — le contenu d'un carton se saisit en TABLEAU, jamais dans un sélecteur** (modale « Expédition groupée », tickets #1098/#1099). Bouton « Modifier le contenu » → mode édition listant **tous** les articles divers de la commande avec une quantité éditable, filtre + « Remplir » ; enregistrement en un appel `PUT /expeditions/divers/lignes/:id/contenu`. Reproduit le legacy `FEN_Expedition_Groupé` (`TABLE_RefExpedie` = les lignes divers de la commande LEFT JOIN le `ref_divers_expedie` du carton sélectionné). ⚠️ **La clé est le COMBO (ref × variation1 × variation2), pas `IDref_divers_expedie`** — c'est la ligne que l'utilisateur lit et celle que la facture regroupe. Trois faits mesurés le commandent : le tableau doit **unir** les lignes de commande **et** les articles déjà dans le carton (61 des 1 589 articles de cartons rattachés à une commande ne correspondent à aucune ligne — invisibles sinon, donc incorrigeables) ; 7 commandes portent le même combo sur deux lignes (quantités **sommées**, jamais affichées deux fois) ; un total inchangé **n'écrit rien**, ce qui protège l'unique carton qui détient deux lignes pour un même combo. ⚠️ **Ne jamais proposer de remplir depuis « Cmdé »** : 1 443 des 1 770 combos (81,5 %) sont déjà expédiés en tout ou partie, donc c'est **« Reste »** (= commandé − expédié ailleurs) qui remplit la ligne ; Cmdé reste un repère, non cliquable. ⚠️ **`stock_divers` est décrémenté à l'écriture**, donc le stock stocké exclut DÉJÀ le contenu courant du carton : la référence de comparaison est `stock + quantité déjà dans ce carton`, sinon un réenregistrement à l'identique signale un dépassement de stock. Stock et Reste s'affichent **après enregistrement** (ils décomptent pendant la saisie) et restent des **avertissements, jamais des blocages** — 584 des combos de lignes n'ont aucune ligne `stock_divers`. Garde : `check-divers-carton-contenu.ts` (`--roundtrip`).
    **Clients › Expéditions — l'avis d'expédition divers ne porte AUCUN prix** (LIVA #1127, Isabelle, 2026-09-07). C'est un document de livraison : le legacy `ETAT_Expédition_diverse` (modèle DIV632, Unicycle) imprime désignation + « N Pièce » et rien d'autre, et le client ne doit pas y lire un prix — l'argent est sur la facture. Jusqu'à #1127 `BonLivraisonDiversPdf.tsx` ajoutait les colonnes P.U. / TOTAL (€) et un total général en euros dès qu'un article avait un prix, donc sur toute expédition Unicycle facturable. Le type `BlDiversItem` n'a plus de champ `prix` du tout (un prix ne peut pas revenir par le builder sans erreur de compilation) ; la ligne de pied de chaque carton et la case dorée comptent désormais les **pièces par unité** (`quantiteParUnite`, « 13 unités · 2,50 Ml »), le chiffre que le client pointe contre le colis. Garde sans base : `check-bl-divers-sans-prix.ts` (`[id]` pour épingler aussi un document réel — 599 sur la copie dev en portait). Reste ouvert : l'unité 4 s'imprime « unité » quand le modèle legacy dit « Pièce » (`uniteLabel`, partagé avec l'écran).
    **Clients › Expéditions — supprimer un avis (ou en retirer un rouleau) DÉ-EXPÉDIE le rouleau** (suite de #1086, trouvé sur l'AE 9698 Save Futur, 2026-09-08). « Un rouleau est expédié » = deux faits, `stock_fini.IDligne_expedition > 0` ET `IDetat_stock_fini = 4` ; `DELETE /expeditions/formelle/:id` et `DELETE …/rolls/:stockId` ne remettaient à 0 que le premier, laissant un fantôme « Expédié » sans avis que Finis › Stock cache (`<> 4`), que Gestion › Marchandise ne voit plus (INNER JOIN sur la ligne d'avis) et que le sélecteur de rouleaux de la ligne ne repropose jamais. `unshipFiniRolls()` (`expeditions.ts`) remet `IDligne_expedition = 0` ET rétrograde l'état 4 → 3 « Validé » (un autre état est conservé, c'est le classement du magasin) ; ⚠️ **contrairement au retour-stock, `IDligne_commande_client` est GARDÉ** — supprimer un avis annule une expédition, pas la commande pour laquelle le rouleau avait été choisi, donc il revient exactement là où il était avant d'être coché (affecté à sa ligne, proposé de nouveau par le sélecteur). L'écru n'a pas de colonne d'état : son seul fait est `IDligne_expedition_ETM`. Garde avec écriture puis restauration, localhost seulement : `check-expedition-unship.ts` (rouleau seul avec voisin intact, autre état conservé, ligne entière). Contexte du ticket : l'AE 9698 (4 m de 186A recoupés sur 909/15, réexpédiés le 19/11/2024 sur une commande déjà facturée) ressortait à chaque « Générer les factures » ; réglé en la passant en **donation**, le générateur les saute — la suppression aurait produit ce fantôme.
    **Clients › Facturation — « Générer les factures » balaie DEUX registres d'expédition, avec deux groupements** (`POST /factures/prov/generate`). **Formelle** (`expedition`) : un proforma **par client × adresse de facturation de la commande × adresse de livraison de l'avis** (`lib/facturation-groupes.ts`, LIVA #1117 — deux avis d'un même client partis à deux adresses ne partagent jamais une facture ; le proforma est estampillé de l'adresse de facturation de la **commande**, règle legacy vérifiée sur 3 317 des 3 331 factures, le défaut client ne servant que si la commande n'en porte pas). ⚠️ Le legacy ne découpait PAS par livraison — 207 de ses factures en mêlent plusieurs — et Isabelle n'obtenait deux factures qu'en générant après chaque avis. Le dialogue de résultat nomme l'adresse sous le client quand celui-ci a été réparti. Garde : `check-facturation-adresses.ts` + `facturation-groupes.test.ts` ; bout-en-bout avec rollback : `e2e-formelle-generate.ts`. **Divers** (`expedition_divers`) : un proforma **par expédition** — groupement de legacy, imposé par le schéma, le lien retour étant la colonne d'en-tête `IDexpedition_divers` qui ne tient qu'un id (535 factures legacy, une expédition chacune, jamais mêlée à une ligne formelle). Ce back-pointer est écrit sur `facture_prov` puis recopié à la conversion, et `wipeOpenProformas` s'en sert pour rouvrir l'expédition ; ⚠️ **ce n'est PAS un « marqueur de conversion »** — un ancien commentaire l'affirmait, 0 ligne en base l'utilisait ainsi. Divers = ETM seulement (pas de colonne `IDsociete`) → passe **sautée sur le montage TRM**. ## 9. Divers

**Divers** — **Références** (`/divers/references`, implemented; `ref_divers` catalog with two variation axes + per-combination `tarif_divers` pricing — see `claude_doc/implemented_screens.md`), **Stock** (`/divers/stock`, implemented, table-centric; route `apps/api/src/routes/stock-divers.ts`)

    **Divers › Stock — `stock_divers` is SPARSE, and that drives the whole screen.** It is not a grid of every combination: it is a log of the combinations someone has touched (1 466 theoretical combos across the 505 references vs 276 rows stored — Tissu Voltige alone has 551 possible and 117 stored), and **214 of those 276 rows sit at quantité 0**. So the list **hides zero rows unconditionally** — no toggle, no filter control — leaving the ~62 lines that actually hold stock; a zeroed row is meant to be indistinguishable from a combination that was never created. A **negative** quantity is NOT hidden (data error, must stay visible). Consequence for writes: `POST /stock-divers` is an **upsert**, because 214 invisible rows would otherwise 409 "modifiez la ligne existante" for a line the user cannot find — it fills an **empty** row silently (the user's mental model is "I added a line"), but a combination that **already carries stock** still 409s and names the quantity, since silently overwriting a visible figure would destroy real data. `create_stock_divers` alone gates the upsert: it can only ever turn a 0 into a quantity. The create dialog therefore refuses quantité 0 (the line would vanish on creation), and the drawer says so when a row is zeroed. One duplicate combination exists in legacy data (ref 535 / variation 558, both rows at 0) — the upsert picks the lowest `IDstock_divers`, and refuses if *any* row of the combo carries stock.
## 10. Qualité

**Qualité** — **Suivi lots** (implemented), **Dossiers** (`/qualite/dossiers`, implemented; non-conformity dossiers over `dossier_qualite` + FNC round-trip + piece traceability — route `apps/api/src/routes/dossiers-qualite.ts`), **Actions** (`/qualite/actions`, implemented; see below), Analyse (placeholder)

    - **Matching rule** (validated: reproduces all 248 legacy `conformite_action` rows): a mention applies to a `ligne_commande_sous_traitant` when `lcs.type = IDtype_sst` AND `lcs.IDreference = mention.IDreference` AND (`mention.IDsous_traitant = 0` OR = the commande's sst) AND (`mention.IDColoris = 0` OR = `lcs.IDColoris`). `0` is legacy's "tous" **wildcard** here, not missing data. The mention's ref/coloris are polymorphic exactly like the line's (type 1 → `ref_ecru`/`colori_ecru`; type 2 → `ref_fini` + the `avec_teinture` coloris rule).
    - **Mentions are never persisted onto the commande** — legacy didn't either (no order `commentaire`/`journal` contains a mention's text). Resolved live so editing an action updates every future bon de commande. Single source: `GET /commandes-sous-traitant/:id/mentions-qualite`, shared by screen + PDF.
    - **`mention_qualite` has an accented PK *and* accented parent FK** (`IDmention_qualité`, `IDaction_qualité`) — no ASCII handle exists for a `WHERE`. Linux writes therefore rewrite the whole **`IDreference` bucket** (delete by the ASCII `IDreference`, positional re-insert preserving each row's PK and parent). `conformite_action`'s PK is ASCII thanks to the legacy typo **`IDconfomite_action`** (conf-**o**-mite, no `r`) — mis-reading that column name makes every PK parse as `0`, so `max+1` collapses to `1` and the next write silently overwrites real row 1. `assertPk()` guards every computed-PK site.
    - **Archiving is manual, by explicit product decision.** The per-action *objectif de conformités* (stored in `data/action-qualite-targets.json`, not HFSQL) only lights up an "objectif atteint" cue — it must never auto-close an action.
    - Guard: `apps/api/src/scripts/check-actions-qualite.ts` (`--write` for the round-trip). Its `--linux` flag **refuses to run off a Linux host**: `queryB64Text` is a passthrough on Windows, so simulating the bridge there reads mangled text and writes it back over neighbouring rows.

## 13. Paramètres

**Paramètres** — Utilisateurs (**admin-only**: per-user permissions + per-user email for Gmail impersonation). **TRM has its own permission catalog + store** on this API — `lib/permission-keys-trm.ts` / `lib/permissions-trm.ts` (`data/permissions-trm.json`) behind `/api/permissions-trm` — deliberately separate from `/api/permissions`: each admin screen saves by replacing the user's whole grant list filtered to its own catalog, so one shared file would let either app strip the other's grants. Gate TRM routes with `trmUserHasPermission`, never `userHasPermission`; key names may coincide with ETM's (`edit_commandes_client` exists in both). TRM likewise has its **own screen-access manifest** `lib/screen-keys-trm.ts` over its own nav tree (+ `check-screen-access-trm.ts` / `seed-screen-access-trm.ts`) — same two-direction model as ETM's, separate store. ⚠️ **The "never `userHasPermission` on a TRM route" rule breaks silently through a SHARED helper**, which is how it went unnoticed for six keys until 2026-08-27: `requirePermission()` in `lib/clients-common.ts` is imported by `clients.ts` (ETM) *and* `clients-trm.ts` / `stock-fil-trm.ts` (TRM), and it hardcoded ETM's store — so a grant made in TRM did nothing while a grant made in ETM opened the TRM route. It now takes an explicit **`PermissionScope`** (`ETM_PERMISSIONS` / `TRM_PERMISSIONS`) with **no default**, the third instance of the `FinanceScope` / `FacturesScope` shape: any guard or factory serving both companies must carry the store, and must never default it. ⚠️ **A key used by a TRM screen but absent from `TRM_PERMISSION_KEYS` fails silently and unrecoverably** — the admin tab renders no toggle (it is built from `GET /permissions-trm/keys`), the PUT drops it as unknown, `/me` never reports it, so the button is invisible to every non-admin with no way to grant it, and it reads as a deliberate restriction. Guard: **`check-permission-keys-trm.ts --web <abs path to TRM apps/web/src>`** — the mirror of `check-screen-access-trm.ts` (there the API manifest follows the web's nav; here the web's `useHasPermission` literals must all exist in the API catalog). Nothing in the type system can catch it: `requirePermission` types its key as the *union* of both catalogs, which stops a typo but not a key belonging to the other app.

**Menu / screen visibility is per user** (`claude_doc/auth_permissions.md` §Screen access). Second axis next to the action catalog, managed in the **Écrans** tab of Paramètres › Utilisateurs: a **menu is a grant, default closed** (`screen_<menu>`), a **screen inside a granted menu is a hide** (`hide_<menu>_<screen>`) — so a newly shipped screen appears for everyone who already has its menu instead of being invisible until an admin ticks it per user. A menu with no visible screen left disappears. Keys derive from the href; the API manifest `apps/api/src/lib/screen-keys.ts` mirrors `navigation.ts` and `check-screen-access.ts` diffs them. ⚠️ Hide keys are **negative** keys: read them via `hasRaw()` (no admin bypass), never `has()`, or the admin sees no menus. Enforcement is the nav surfaces + one route guard in `AppShell` — **a curtain, not a lock**: endpoints are shared across screens, so confidentiality stays with server-enforced action keys (`view_rapport_finance`, `dashboard_ca`…). Grandfathering script: `seed-screen-access.ts --write`, **run on the server** (`data/permissions.json` is gitignored and lives beside the running API), idempotent, and also the way to hand a new menu to everyone.
